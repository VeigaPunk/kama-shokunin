# vLLM Messages streaming: defaults lost at the wire

**Status:** Public-audience candidate for independent review. The source review is described below. This is not authorization to publish, a production incident finding, a deployment or release certification, or independently executed testing.

## Reported failure and precise boundary

[vLLM issue #45367](https://github.com/vllm-project/vllm/issues/45367) reports Claude Code retries on a particular pre-merge DiffusionGemma branch and environment despite the server logging HTTP 200 for `/v1/messages?beta=true`. The reporter's captured `message_start` SSE omitted the nested message's `type` and `role`; their non-streaming requests worked. That is an attributed report, not a live incident reproduced here. The issue discussion also records a maintainer initially seeing the default values in an object log, then reproducing their absence after JSON serialization on main. A healthy HTTP response or a reassuring object representation does not establish that a client accepted the emitted stream.

The mechanism is narrower than “defaults are broken.” The nested `AnthropicMessagesResponse` has default values for `type` and `role`, but the affected streaming constructor did not explicitly set them. The streaming event is serialized with `model_dump_json(exclude_unset=True)`, so defaulted-but-unset fields were left out of the nested wire object. The visible in-memory values and the transmitted JSON can therefore differ. The reporter and PR author describe the effect on strict clients; this does not imply that all clients reject the stream, that all 200/retry symptoms have this cause, or that every model or release was independently tested.

[PR #45376](https://github.com/vllm-project/vllm/pull/45376) was squash-merged on 2026-06-13 as [`17ee5b1ac5dd61fa89bc4321ef54b0a790a45db3`](https://github.com/vllm-project/vllm/commit/17ee5b1ac5dd61fa89bc4321ef54b0a790a45db3), distinct from PR head `fdb48ff06c168513b710ecdc074be87769d313a1`. The [commit API diff](https://api.github.com/repos/vllm-project/vllm/commits/17ee5b1ac5dd61fa89bc4321ef54b0a790a45db3) shows two changed files. In `vllm/entrypoints/anthropic/serving.py`, the change explicitly supplies `type="message"` and `role="assistant"` to the nested streaming response constructor. It does not globally disable `exclude_unset`, change all defaults, or change non-streaming serialization. This makes these fields explicitly set for that construction, preserving them under the described serializer. The other file adds a regression test. The issue lists alternative serialization approaches, but they are not the merged repair. A merge is not evidence that a particular release or deployment includes the fix.

## Tests, reports and limits

The added asynchronous conversion test supplies a content chunk, a stop chunk and an end marker to `message_stream_converter`; it parses the resulting events and asserts that the first event is `message_start` and that its nested message contains the expected `type` and `role`. It is a focused converter-level assertion, not an end-to-end HTTP, proxy, SDK or production test. The PR author reports a pre-fix failure and 34 passing tests in the conversion test file after the fix, plus pre-commit checks. The originally affected user reports a wire and Claude Code end-to-end retest of the PR head without their workaround; the maintainer reports running the new tests and checking before/after live-server wire output. These are upstream accounts, not observations made by us. We did not execute upstream tests, launch a model or server, capture endpoint traffic, inspect check logs, or independently reproduce the failure. Neither the reported retest nor these source observations establish universal client compatibility.

## Twelve adversarial hypothetical decisions

Each case is an invented paper exercise, not a run or observed outcome. Code-specific predictions assume the pinned change is in the deployed code, the relevant construction and serializer are reached, and bytes are delivered intact.

1. **Object log looks correct; SDK retries.** A log shows nested values `message` and `assistant`, but the client retries on HTTP 200. **Answer:** object defaults do not prove wire inclusion. Capture the serialized first event at the server and received bytes at the client, with redaction; compare them before choosing a cause.
2. **Missing both nested fields.** The received `message_start` lacks both `message.type` and `message.role` on an affected build. **Answer:** this matches the reported signature, not proof of the same root cause. Verify the exact constructor and serializer in the deployed build and rule out an intermediary rewriting the event.
3. **Outer type exists but nested type does not.** The event has outer `type=message_start` while its `message` lacks `type`. **Answer:** these are different fields; the outer discriminator does not supply the nested value. Inspect the complete parsed event and client validation error.
4. **One field survives.** The wire contains nested `type` but omits `role`. **Answer:** do not insist that both must be missing for a serialization or transformation problem. Inspect explicit-set state and the actual serialized payload, then compare both sides of any proxy.
5. **Values are present but wrong.** The nested fields are present with unexpected values. **Answer:** the merged change targets omission at this constructor, not every wrong value or later mutation. Check the exact generated event, transformations and schema/version mismatch.
6. **Non-streaming succeeds.** A non-streaming request works but streaming fails. **Answer:** this narrows investigation to differences between paths but does not prove this defect. Compare request, client version, response serialization, event framing and actual bytes; avoid claiming all non-streaming paths are immune.
7. **Lenient client succeeds.** One client accepts the same stream while another rejects it. **Answer:** different validation can explain different behavior, but capture the two clients' actual inputs and errors first. Success in one client does not establish schema compliance for another.
8. **Patched server, proxy omits fields.** Server-side serialized event includes both fields but the client-side capture lacks them. **Answer:** investigate the intermediary and framing rather than changing the constructor again. Correlate request IDs and authorized, redacted captures on each side; establish whether both captures refer to the same request.
9. **200 with a different malformed event.** The first event has both expected fields, yet a strict client rejects a later malformed delta. **Answer:** this patch does not validate the whole stream. Inspect ordered event framing, payloads and the client's exact validation failure; do not label the whole stream fixed from two fields alone.
10. **EOF or disconnect.** The client receives an incomplete frame or no terminal event. **Answer:** classify completion as uncertain and investigate transport, cancellation, buffering or other faults. Omitted initial fields cannot be inferred without the actual initial event.
11. **Retry after partial tool activity.** A retry follows a failed stream and a tool may already have run. **Answer:** do not automatically replay or execute partial tool arguments. First determine whether side effects occurred and whether the operation has appropriate idempotency and authorization.
12. **Merged PR cited as fleet proof.** A dashboard shows the merge and green checks but gives no deployed build. **Answer:** identify the running image/commit, endpoint, client and intermediary path before making a deployment claim. A reported PR-head test, merged source, deployed bytes and accepted end-to-end response are distinct evidence.

## Safe diagnostic approach

With authorization, record the exact server build, endpoint, streaming mode, SDK and version, correlation ID, response status and content type. Compare the first serialized `message_start` at the producer with the client's received event and validation error; inspect nested fields, framing and any transformations. Redact credentials, prompts, generated text and tool arguments, collecting only what is necessary. Distinguish “constructed,” “serialized,” “sent,” “received” and “accepted”; a log at one stage does not prove the next. If reproduction is appropriate, isolate a controlled request without side effects and preserve the exact version and configuration. Diagnose retries separately from authorization and idempotency; this lesson authorizes no live test, configuration change or retry.
