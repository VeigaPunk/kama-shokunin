## 3. Every difference between git-mode and dir-mode, explained

The two modes share `classify()`, `parse_ledger()` and the `--ledger` override verbatim; the only divergence is how `tokens` and `blobs` are collected (`scan_dir` L112-130 vs `scan_git` L140-166).

### D1 — `blob` 86 vs 79: seven cited digests are **history-only** blobs (expected)

Dir-mode's blob set is "every regular file under DIR" (`digest-ledger.py:17-18`), i.e. exactly the tree blobs of the commit. Git-mode's set is "every blob reachable from REV" (`digest-ledger.py:142`), i.e. tree blobs **plus every superseded blob in history**. Seven of the 96 cited digests exist only in history, so they classify `blob` in git mode and `unknown` in dir mode. All seven, with their historical path and the tracked document that cites them at tip:

|---|---|---|
| `493afecbd6dd` | `registry/history/DELTA.md` (older revision) | `LOG.md:122` |
| `fd98f07a2d84` | `registry/history/latest.tsv` (older revision) | `LOG.md:120` |
| `e9fbaa02b432` | `.ufo/round-10/SEAT-PROTOCOL.md` | `LOG.md:668` |
| `ce7dc79c9523` | `.ufo/waves/round-18/runs/commands.json` | `corpus/lessons/round-18.md:417` |
| `87cad1cad456` | `.ufo/waves/round-18/c2/survivors.py` | `corpus/lessons/round-20.md:81` |
| `ac934794af1e` | `.ufo/waves/round-18/c2/survivors.py` (second revision) | `corpus/lessons/round-20.md:81` |
| `dc036d7dcfe2` | `tools/kama-llamacpp-live.py` (round-18 revision) | `corpus/SOURCES.md:67` (S055 row: "tool sha256 …") |

Every one is an *intentionally* historical pin ("original SHA-256", "tool sha256 at round-18", history-file transition logs), so git-mode's `blob` verdict is right and dir-mode's `unknown` is a false alarm caused by the missing history — exactly the expected difference. The identity `86 = 79 + 7` holds at all three revs (`84 = 77 + 7` at base/freeze).

### D2 — `tokens` 96 vs 96: identical, and why that is not structural

Dir-mode reads whatever regular files are on disk; git-mode reads the tracked tree. They coincide here only because the export is a *complete* archive of the commit. Two demonstrations show the difference is real and not a property of the tool:

```
$ cp -al export/3d9bd8d export/stray-demo
$ printf 'untracked-bytes\n' > export/stray-demo/stray.bin
$ printf 'cites <sha256(stray.bin)> and 1111…1111\n' > export/stray-demo/stray.md
$ python3 <clone>/tools/digest-ledger.py scan --dir export/stray-demo --details ; echo rc=$?
tokens=98 blob=80 external_ok=4 external_absent=0 unverifiable=5 wrong_flagged=1 ledger_bad=0 wrong_unflagged=0 unknown=8
rc=1
$ cd clone && python3 tools/digest-ledger.py scan --repo . --rev 3d9bd8d ; echo rc=$?
tokens=96 blob=86 … unknown=0

```

(`…/out/R42B02/fixture-untracked.txt`.) Two untracked files move dir-mode's verdict (`tokens` 96→98, `blob` 79→80, `unknown` 7→8) with no change to the commit. Conversely, a *partial* export (a subdirectory) would drop tokens. So **dir-mode is content-addressed to a directory, not to a commit**; only git-mode is a revision gate.

### D3 — symlinks: 8 tree symlinks hashed by git-mode, skipped by dir-mode, zero count effect

`scan_dir` skips symlinks explicitly (`digest-ledger.py:118`); `scan_git` hashes them as blobs (they are blobs). ## 6. Findings (each with file:line, repro, proposed fix — none applied)

### F1 — dir-mode and git-mode disagree on the *same commit*: exit 0 vs exit 1, and the summary line names no mode

`tools/digest-ledger.py:17-18` documents the two blob sets; nothing in the output tells a consumer which one produced a line, and `render()` (`:169-170`) prints only the nine counters.

Repro: §2, `tip-git` vs `tip-dir`.

Why it matters beyond cosmetics: the C2 counter compares summary strings byte-exactly (`tools/round42-digest-audit.py:139` `summary()`, `:309` contract leg, `:320` live leg). Any downstream consumer doing the same cannot distinguish "clean tree, git mode" from "clean tree, dir mode with 7 history digests invisible". Today it is harmless because the counter never compares across modes — but the tool's own docstring invites the comparison ("The blob set is … REV (git mode) or … DIR").

Proposed fix (additive only, so the frozen summary line stays byte-identical):
1. In `scan_git`, split the blob set into tree blobs (`git ls-tree -r` object ids) and history-only blobs; classify a token that hits only the latter as a new `history` counter instead of `blob`. Then both modes report `blob=79` and the residual difference is named.
2. Print a second line, e.g. `mode=dir history=unavailable` / `mode=git history=7`, and in dir mode add `detail: unknown <tok> (dir mode: history blobs unavailable)`.
This keeps `render()` and the exit predicate intact for every fixture the counter builds (fixtures have no history, so `history=0` there).

### F2 — `--dir` on a nonexistent path prints a clean all-zero summary and exits 0

`scan_dir` (`tools/digest-ledger.py:112-119`) simply walks; a missing root yields no files, so `classify` returns all zeros and `main` (`:262`) exits 0.

```
$ python3 <clone>/tools/digest-ledger.py scan --dir /nonexistent-kama-r42 --details ; echo rc=$?
tokens=0 blob=0 external_ok=0 external_absent=0 unverifiable=0 wrong_flagged=0 ledger_bad=0 wrong_unflagged=0 unknown=0
rc=0
```

A typo in a gate script therefore reads as "no cited digest is unexplained" — a false-clean, the exact failure class this tool exists to prevent. (`--repo` with a bad rev already errors correctly: `git rev-parse` → `rc=2`.)

Proposed fix: in `main`, before dispatching, `if a.dir and not os.path.isdir(a.dir): print(f"digest-ledger: not a directory: {a.dir}", file=sys.stderr); return 2`. Optionally warn (rc 0 but a `note:`) for an empty directory.

### F3 — `external` ledger paths resolve against the process CWD, and `external_absent` never fails the run

`classify` (`tools/digest-ledger.py:86`) does `if p and os.path.isfile(p)` with the raw ledger string; the exit predicate (`:262`) counts only `ledger_bad + wrong_unflagged + unknown`.

Repro: §D5 fixture — same scanned directory, `external_ok=1` from one CWD and `external_absent=1` from another, both `rc=0`.

Consequence: a ledger row with a relative path (natural for a repo-relative artifact) gives a different verdict depending on where the operator stands, and a genuinely missing external artifact is silently non-fatal, so "all external artifacts present" cannot be gated.

Proposed fix: thread the scan root into `classify` and resolve `p` as `p if os.path.isabs(p) else os.path.join(root, p)` (dir mode: `a.dir`; git mode: the repo work tree / the export). Document the rule in the docstring, and add `--strict-external` that folds `external_absent` into the exit code for gate use.

### F4 — git-mode peak RSS is O(history): 458.8 MiB on a 214.6 MiB history

`scan_git` buffers the entire `git cat-file --batch` stream (`tools/digest-ledger.py:143-147`: `capture_output=True`, then `blobs, buf, i = set(), p.stdout, 0`), so peak RSS ≈ 2.1× total reachable blob bytes (measured: 214.6 MiB content → 469 860 KiB RSS; §5).

At the current history this is survivable (0.58 s); the tool is a per-round gate and the lane's history only grows. `[INFERENCE]` Extrapolating the measured 2.1× ratio, the next order of magnitude (≈2 GiB of reachable blobs) would put peak RSS at ≈4 GiB; that scaling was not run. It is also the reason git mode is *faster but fatter* than dir mode.

Proposed fix: stream instead of buffering — `Popen(..., stdout=PIPE)`, write all oids to stdin, then loop `readline()` for the header and `read(size)` (+1) for the body, hashing incrementally. Semantics unchanged, memory O(largest blob) instead of O(history). A cheaper alternative for the gate: hash only tree blobs plus blobs named by the ledger, and let the `history` class (F1 fix) fall back to a second, explicit pass.

### F5 — `blob` is membership-only, never path-bound: a stale anchor that matches *any* historical blob passes

`classify` (`tools/digest-ledger.py:79-80`) tests `t in blobs` and stops; it never asks whether the digest belongs to the file the sentence names. Evidence that membership is many-to-one:

```
9c5a6f2c… (S479 anchor) is the same bytes as
  .ufo/waves/round-16/sources/llama.cpp-704366d/server-models.cpp
  .ufo/waves/round-26/sources/llama.cpp-704366d/server-models.cpp
  .ufo/waves/round-27/sources/llama.cpp-704366d/server-models.cpp
  .ufo/waves/round-42/c3/llamacpp-704366d7-server-models.cpp
```

and the removed base token `dbb5f4f7…` (the old PROVINCE.md) would still classify `blob` if a document kept citing it, even though no current file hashes to it. So "unknown=0 at tip" certifies *"every cited digest names real bytes somewhere in this repository's history"*, not *"every cited digest names the artifact its sentence names"*.

Proposed fix (proposal, needs its own round and its own counter): for `blob` rows, bind the citation to a path — either require a `path` column for `blob` rows in `registry/digest-ledger.tsv` and verify `sha256(<rev>:<path>) == digest`, or, for inline anchors, resolve the nearest backticked path on the same line. The `history` split from F1 is the prerequisite that makes the distinction visible.

## 9. Residual risk / what I did not measure

- Portable determinism across hosts is untestable here; `external_ok` is host- and filesystem-state-dependent by design.
- I did not test a shallow or partial clone (git-mode blob set would shrink and approach dir mode) or a repo with submodules; the lane has neither.
- Memory figures are a single measurement per configuration on this host (plus a 5-run determinism sweep that shows the *output* is stable); the O(history) reading is from the measured object sizes, not from a scaling experiment.
- The `--details` line for `wrong_flagged` prints the flagged digest but not the `correct` digest it was validated against; I did not treat that as a defect, only as a readability note.
