# Declared versus served context capacity: what two engines' own source publishes

Ground: frontier item K05, declared-versus-served context capacity (`corpus/README.md` §Frontier). The lane's measured entry, `corpus/knowledge/context-capacity.md`, is llama.cpp b11755 on a lane-owned fixture: two capacity numbers (the KV pool and the per-slot ceiling), with the API reporting only the second. This entry adds what two engines' source says about *which numbers they compute and where they print them*. It is a source reading, not a measurement: no server was run for it, the lane still holds no vLLM runtime, and K05 across real registered consumers stays runtime-blocked.

## vLLM at v0.32.0: the served figure is the pool in units of the declared length, and it is not the pool for hybrid models

- The memory-derived quantity is a block count: `num_blocks = available_memory // bytes_per_block` (`kv_cache_utils.py:1627`), after which `may_override_num_blocks` replaces it with `num_gpu_blocks_override` when that option is set (`kv_cache_utils.py:1230-1236`). On the dense path the served pool can therefore be an operator override, not a measurement of memory. The HiSparse path returns earlier (`kv_cache_utils.py:1616-1620`), before lines 1627-1628, so this file does not show the override applied there.
- The token capacity the engine reports is `int(max_concurrency * max_model_len)` (`get_kv_cache_capacity`, `kv_cache_utils.py:2308`). `max_concurrency` is a float, the number of `max_model_len`-long requests whose blocks fit: each KV-cache group charges `cdiv(spec.max_memory_usage_bytes, spec.page_size_bytes)` blocks per request, the device groups' charges are summed against `num_blocks`, host-resident groups are charged against `hisparse_host_num_blocks`, and the smaller limit wins (`get_max_concurrency_for_kv_cache_config`, `kv_cache_utils.py:1195-1227`). It can be below 1.
- Consequence, worked from the code with `L = max_model_len` and `T_g` a group's own per-request token demand: for one full-attention group `T_g = L`, the length cancels and the figure is the block pool in tokens, rounded down to whole requests and whole blocks. For a hybrid model (full-attention plus sliding-window groups) the per-request demand is the sum of the groups' demands, so the figure is the pool scaled by `L / Σ T_g`, smaller than the physical pool; when a host pool is the smaller limit the figure comes from `hisparse_host_num_blocks`, not `num_blocks`. The exact per-group demand lives in `vllm/v1/kv_cache_interface.py`, which this entry does not hold; a worked example (seat R42C05's probe, `.ufo/waves/round-42/w1/out/R42C05/probe_capacity_identity.py`: L = 8192, window 2048, 16-token pages, 1000 blocks, the sliding-window demand assumed rather than read) puts the reported figure at 12800 for a 16000-token pool. It is an illustration of the formula, not a measurement of vLLM.
- `update_kv_cache_capacity` stores `kv_cache_size_tokens` and `kv_cache_max_concurrency` on the cache config (`kv_cache_utils.py:2321-2322`) and prints them in one line: `"%s KV cache size: %s tokens, Maximum concurrency for %s tokens per request: %.2fx"` (`kv_cache_utils.py:2328`). Nothing in this file reads those two fields back (`grep -n "kv_cache_size_tokens\|kv_cache_max_concurrency"` finds only the two writes), so what else consumes them, and whether any HTTP surface exposes them, is not established here and is not claimed.
- Three qualifiers on the log line: the printed `%.2fx` is rounded, so divide the stored fields instead; the `" + host"` label is gated on `hisparse_config is not None` (`kv_cache_utils.py:2325-2326`) while the number includes the host pool only when a host-resident group exists (`kv_cache_utils.py:1222`); and with `--max-model-len -1` the engine fits `max_model_len` to memory and writes it back (`kv_cache_utils.py:2476`), so the printed per-request length is then the fitted one, not the model's declared context.

Reading for an operator: on vLLM the startup log is the single place where a per-request length and the served pool meet, and the number to capture is the pair of stored fields or the log line, read with the qualifiers above. A tool that reads only a declared length (a model card or a config) sees one half, and a K05 comparison must not set a hybrid model's figure beside a full-attention pool without the `L / Σ T_g` factor.

## llama.cpp at 704366d7: the router's model listing publishes the declared (training) context as `context_length`

- The handler `get_router_models` (`server-models.cpp:2329`) builds one JSON object per model and adds `context_length` only when the loaded metadata reports a positive training context: `if (meta.n_ctx_train > 0) {` followed by `model_info["context_length"] = meta.n_ctx_train;` (`server-models.cpp:2378-2379`).
- The key is llama.cpp's own: `max_model_len` occurs 0 times in `server-models.cpp` (`grep -o max_model_len <copy> | wc -l` → 0, 2026-10-25). A client that reads only `max_model_len` finds no declared capacity in this listing; that is a statement about the key a client reads, not about the engine.
- The value is the GGUF *training* context (`n_ctx_train`), the same quantity the lane's fixture reports in its own measured cells (`corpus/knowledge/context-capacity.md`); it is not the per-slot ceiling and not the pool.
- Scope: this is the router-mode listing handler. The single-model server's `/v1/models` body is a different handler, not read in this file; the lane already holds that it carries `meta.n_ctx_train` (`corpus/knowledge/gguf-declared-identity.md:30`) next to the per-slot `meta.n_ctx`, so the declared training context is published in both modes, under different nesting and key names. That cross-mode equivalence is the lane's earlier reading, not something this file proves.

## What the two readings establish together

| engine | declared side | served side | where it is printed or returned |
|---|---|---|---|
| vLLM v0.32.0 | `max_model_len` (engine-fitted when set to -1) | `kv_cache_size_tokens = int(max_concurrency * max_model_len)`, from `min(num_blocks, hisparse_host_num_blocks)`; for hybrid models the declared-length share of the pool (`L / Σ T_g`), not the pool | one startup log line (`kv_cache_utils.py:2328`) |
| llama.cpp 704366d7 | `context_length = n_ctx_train` (router listing, only when > 0); `meta.n_ctx_train` in the single-model `/v1/models` (held, `gguf-declared-identity.md:30`) | the pool and per-slot numbers the lane measured in `context-capacity.md` | router listing (`server-models.cpp:2379`); pool in the server log |

A K05 comparison needs the declared value under each engine's own key name and the served value from the engine's own log, not from the OpenAI-shaped fields. Both sides are now documented for these two engines; the comparison on a live registered endpoint still needs an authorised serving runtime.
