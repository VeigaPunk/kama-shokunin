## 2. Counterexample A — hybrid model: the pool is full, the reported number is not the pool

`get_max_concurrency_for_kv_cache_config` sums per-group per-request blocks (`1212-1220`), and a group's per-request bytes are its own spec's, not `max_model_len`'s (`1200-1203`: "cdiv(per-request bytes, page bytes) **of the group's spec**"). For a `SlidingWindowSpec` that demand is window-bounded, not length-bounded — the file says so itself: disabling the hybrid manager loses "dropping the KV cache outside the sliding window" (`1816-1820`), SW specs are tagged with `extra_retained_tokens` *in the window* (`2584-2590`), and the padding example counts "9 full + 9 sliding window" groups separately (`2343-2347`). The exact `T_g` for SW lives in the unheld `kv_cache_interface.py`.

So, with `L = max_model_len`, `P` = page tokens, `N = num_blocks`, and `T_g` the group's per-request token demand:

```
num_tokens = int( L · min( N / Σ_device cdiv(T_g,P) , H / Σ_host cdiv(T_g,P) ) )
```

which equals `N·P` only when `Σ_g cdiv(T_g,P) = cdiv(L,P)`.

Probe (`R42C05/probe_capacity_identity.py`, re-implements `1210-1227`+`2304-2308` verbatim; run: `TMPDIR=/fast/scratch/kama-r42/seats/R42C05/tmp python3 probe_capacity_identity.py`, exit 0):

```
A uniform FA       layers=20 N= 1000 per_req_blocks= 512 conc=  1.9531 reported= 16000 pool_tokens= 16000 ratio=1.000000
B hybrid FA+SW     layers=20 N= 1000 per_req_blocks= 640 conc=  1.5625 reported= 12800 pool_tokens= 16000 ratio=0.800000  (L/sum(T_g)=0.8000)
   stored tokens at full admission = conc*(L+W) = 16000.0 == pool 16000
C promoted to FA   layers=30 N=  666 per_req_blocks= 512 conc=  1.3008 reported= 10656 pool_tokens= 10656 ratio=1.000000
```

`L=8192, W=2048, P=16`, 10 FA + 20 SW layers (the file's own `1370-1377` example). Case B is the defect: at full admission the pool **is** exactly full (`1.5625 × (8192+2048) = 16000`), yet the reported figure is 12800 = `N·P·L/ΣT_g`. The entry's sentence therefore mis-describes a hybrid engine in the direction that matters to an operator: the number is the **declared-length share** of the pool, not the pool. Case C shows the identity restored exactly when `--disable-hybrid-kv-cache-manager` promotes SW to FA (`1733`, `1737-1745`, `2173-2174`) — at the price of 334 blocks, i.e. the savings the warning at `1816-1820` describes. **The claim is true only in the configuration that throws the hybrid optimisation away.**

## 3. Counterexample B — host pool: reported number is a `min`, the log label reads additive

`1222-1226` appends the host limit only when a host-resident group exists, and the result is `min(device, host)`. Probe case D: device `N=1000`, host `H=500`, one FA group → `conc=0.9766`, `reported=8000`, device pool `16000`, ratio `0.5`. The reported token capacity is then the **host** pool's request count × `L`; it is not the device pool expressed in anything.

Two source-level defects fall out of this, both inside the file:

1. **The table cell is wrong.** Entry's table says `kv_cache_size_tokens = int(max_concurrency * max_model_len)` **from `num_blocks`**. When the host binds it comes from `hisparse_host_num_blocks` (`1225`). Correct: `from min(num_blocks, hisparse_host_num_blocks)`.
2. **Label and number are gated on different conditions.** The log appends `" + host"` when `hisparse_config is not None` (`2325-2326`), while the number includes the host pool only when `host_blocks_per_request` is truthy (`1222`). A hisparse config with no host-resident group logs "GPU + host" for a device-only number; conversely a host-resident group without `hisparse_config` is counted but not labelled. The entry's "the served token capacity" inherits that ambiguity.
3. Nothing in this file guarantees ≥ 1 concurrent request **against the host pool**: the startup check's memory input is device `available_memory` minus one device block (`1127-1130`) and its need is `sum(spec.max_memory_usage_bytes …)` over specs (`1043-1047`, called at `1134`); `hisparse_host_num_blocks` appears only at `1223-1225` and the scheduler-config equality assert at `2284`. So the `%.2fx` in the log can legitimately print below `1.00x` with no error — worth saying, because the entry tells the operator to trust that line.

## 4. Counterexample C — the "derived from the declared length" framing is inverted, and block rounding bites

For one full-attention group `T_g = L`, so `num_tokens = int(N·L/cdiv(L,P))` — **`L` cancels**: the number is the pool, independent of the declared length. The entry calls that same number "derived from the declared length". Both framings cannot be right; the L-dependence is real only in the hybrid regime of §2 (factor `L/ΣT_g`).

Block rounding makes even the uniform case short whenever `P ∤ L`:

```
F uniform FA L= 8192 P=16 per_req= 512 conc=  1.95312 reported= 16000 pool_tokens= 16000 ratio=1.000000
F uniform FA L= 8001 P=16 per_req= 501 conc=  1.99601 reported= 15970 pool_tokens= 16000 ratio=0.998125
F uniform FA L=   17 P=16 per_req=   2 conc=500.00000 reported=  8500 pool_tokens= 16000 ratio=0.531250
```

A 17-token `max_model_len` on 16-token pages reports 53 % of the pool. `int()` truncation (`2308`) adds a sub-token floor on top.

## 5. Latent `ZeroDivisionError` at `1221` (unreachable-or-not is outside the file)

`limits = [kv_cache_config.num_blocks / num_blocks_per_request]` (`1221`) has no guard. Attention-free models produce exactly `kv_cache_groups=[]` with `num_blocks=1` (`1604-1615`), so any call to `get_max_concurrency_for_kv_cache_config` on that config divides by zero; symmetrically, an all-host-resident config leaves `num_blocks_per_request=0`. Every other empty-spec path in this file *is* guarded (`1119`, `2433-2440`, `1604-1607`), which is why this looks like an omission rather than a convention. Whether `update_kv_cache_capacity` is ever called on such a config depends on a call site this file does not hold. Minor companion: `1223` is a bare `assert`, erased under `python -O`, turning a missing `hisparse_host_num_blocks` into a `TypeError` at `1225`.

## 6. Remaining caveats the entry should carry

- **Printed ratio ≠ stored numbers.** `%.2fx` (`2328-2333`) rounds `max_concurrency`, so `num_tokens ÷ max_model_len` does not reproduce the printed ratio (case A: 1.953125 → `1.95x`). The entry's "their ratio" is approximate; the exact pair is the stored fields (`2321-2322`), whose readers are unheld.
- **The number is post-shrink across workers.** `get_kv_cache_configs` re-plans every rank against `min_num_blocks` (`2665-2677`) and the scheduler config asserts all ranks agree (`2280-2286`). So under TP/PP the logged capacity is the **smallest** rank's, not that rank's own memory — the entry's "startup log is the single place where declared and served meet" needs "and it is a fleet minimum".
- **On `--max-model-len -1` the printed "declared" figure is engine-fitted.** `_auto_fit_max_model_len` writes `vllm_config.model_config.max_model_len = auto_fit_max` (`2476`) before configs are built (`2635-2636`), and the log re-reads `max_model_len` at `2323`. The model's declared context is then `original_max_model_len`, printed nowhere in this file. This directly qualifies the entry's "declared side: `max_model_len`".
- **Override does not apply on the HiSparse path in this file.** `get_kv_cache_config_from_groups` returns at `1616-1620` before reaching `1627-1628`, so `may_override_num_blocks` is bypassed there; whether `get_hisparse_kv_cache_config` applies it is unheld. The entry's unqualified "the served pool can be an operator override" is therefore true for the dense path only as read here.
- **`int()` + `//` mean the figure is a lower bound of the allocated bytes** — consistent with `size = bytes_per_block * num_blocks` (`1629`), and it includes the null block that `check_memory` deliberately reserves (`2627-2633`).

## 7. Proposed corrections (smallest safe set)

All keep the counter's three pinned strings (`kv_cache_utils.py:1627`, `kv_cache_utils.py:2328`, `server-models.cpp:2379`) — verified against `tools/round42-capacity-audit.py:126-145`, which pins exactly `A1` (1627), `A2` (2328) and the `max_model_len` count; the entry's own `out_of_counter_limit` states prose reading is reviewer-judged, so no counter change is needed or allowed.

**Fix 1 — replace entry line 12** (the identity sentence):

> - The token capacity the engine reports is `int(max_concurrency * max_model_len)` (`get_kv_cache_capacity`, `kv_cache_utils.py:2308`). `max_concurrency` is the number of `max_model_len`-long requests whose blocks fit: per request, each KV-cache group charges `cdiv(spec.max_memory_usage_bytes(vllm_config), spec.page_size_bytes)` blocks from the one pool all device groups alias from (`kv_cache_utils.py:1631`), host-resident groups charge `hisparse_host_num_blocks`, and the smaller limit wins (`kv_cache_utils.py:1210-1227`). So the number is `int(L · min(N/Σ_device cdiv(T_g), H/Σ_host cdiv(T_g)))`, with `T_g` the group's own per-request token demand. On a single full-attention group `T_g = L`, the length cancels and the figure is the pool itself (to block rounding); on a hybrid model the sliding-window group's `T_g` is window-bounded, so the figure is only the declared-length share of the pool, `N·P·L/Σ_g T_g` — the pool is full at that concurrency, but part of it is not declared-length tokens. In neither case is it a second independent measurement.

**Fix 2 — table cell (entry:28, vLLM row, "served side" column):** `kv_cache_size_tokens = int(max_concurrency * max_model_len)` **from `min(num_blocks, hisparse_host_num_blocks)`**, plus the qualifier that a hybrid model's figure is the declared-length share (`L/Σ_g T_g`), not the pool.

**Fix 3 — operator paragraph (entry line 15), append:** "Read the number with two qualifiers: the printed `%.2fx` is rounded, so divide the stored fields instead of the log; and on `--max-model-len -1` the per-request length printed is the engine-fitted one (`kv_cache_utils.py:2476`), not the model's declared context. A hybrid model's figure is not comparable with a full-attention pool without the `L/Σ_g T_g` factor — which is what a K05 cross-engine comparison must not silently skip."

**Fix 4 (optional, lesson hygiene):** `corpus/lessons/round-42.md` §Gate, assimilation row for the r5 amendment says the staged prose "was corrected from the file (derived from `max_model_len`, not read off the block count)". The safer parenthetical is "the product is `int(conc·L)` and is `L`-independent on a single full-attention group". The gate leg (`tools/round42-capacity-audit.py:190-220`) checks only dated located quotes and URLs, so this edit is inert for the counter.

**Fix 5 (source note, not a lane change):** record `1221`'s unguarded division and the `2325`/`1222` label/number condition mismatch as a recheck note on S478 rather than a runtime finding — the file, not the lane, owns them.
