    Container Service for Kubernetes:スタンドアロン LLM 推論サービスのデプロイ

    最終更新日:Sep 18, 2026

    このガイドでは、Qwen3-32B をスタンドアロンの大規模言語モデル (LLM) 推論サービスとして Container Service for Kubernetes (ACK) 上にデプロイする手順を説明します。最終的に、GPU ノード上で実行される vLLM または SGLang を利用した、動作可能な OpenAI 互換の推論エンドポイントが完成します。

    背景情報

    Qwen3-32B

    Qwen3-32B は、Qwen シリーズの最新の進化形であり、推論効率と会話の流暢さの両方に最適化された 32.8B パラメーターの高密度アーキテクチャを特徴としています。

    主な特徴：

    • デュアルモード性能：論理的推論、数学、コード生成などの複雑なタスクに優れていると同時に、一般的なテキスト生成においても高い効率を維持します。

    • 高度な機能：指示追従、マルチターン対話、創造的なライティング、および AI エージェントタスク向けのクラス最高のツール使用において、優れた性能を発揮します。

    • 大規模なコンテキストウィンドウ：ネイティブで最大 32,000 トークンのコンテキストを処理でき、YaRN テクノロジーを使用することで 131,000 トークンまで拡張可能です。

    • 多言語サポート：100 以上の言語を理解し、翻訳できるため、グローバルなアプリケーションに最適です。

    詳細については、ブログ、GitHub、およびドキュメントをご参照ください。

    前提条件

    開始する前に、以下が準備できていることを確認してください。

    • Kubernetes 1.22 以降を実行する ACK クラスターと GPU アクセラレーテッドノード。詳細については、「ACK マネージドクラスターの作成」および「クラスターへの GPU ノードの追加」をご参照ください。

    重要

    GPU ノードは、推論ポッド全体で 64 GB を超える合計 GPU メモリを提供する必要があります。インスタンスタイプ ecs.gn8is-2x.8xlarge (カードあたり 80 GB の GPU メモリ) を推奨します。詳細については、「GPU コンピューティング最適化インスタンスファミリー gn8is」をご参照ください。

    推論エンジンの選択

    このガイドでは 2 つの推論エンジンをサポートしています。ワークロードに基づいて選択してください。

    エンジン

    最適な用途

    主な差別化要因

    vLLM v0.10.0

    高スループット、低レイテンシーのサービング

    PagedAttention KV キャッシュ、TP、PP、DP、EP 並列処理、OpenAI 互換 API

    SGLang 0.4.10.post2

    マルチモーダルおよびマルチ LoRA ワークロード

    RadixAttention プレフィックスキャッシュ、PD 分離、マルチ LoRA バッチ処理、FP8/INT4/AWQ/GPTQ 量子化

    どちらのエンジンも、2 つの GPU (--tensor-parallel-size 2) を持つ Kubernetes StatefulSet としてデプロイされ、ポート 8000 で ClusterIP Service を公開します。

    モデルデプロイ

    ステップ1: モデルファイルの準備

    ModelScope からモデルをダウンロードします。

    git-lfs がインストールされていない場合は、先に yum install git-lfs または apt-get install git-lfs を実行してください。他のインストール方法については、「Installing Git Large File Storage」をご参照ください。
    git lfs install
GIT_LFS_SKIP_SMUDGE=1 git clone https://www.modelscope.cn/Qwen/Qwen3-32B.git
cd Qwen3-32B/
git lfs pull

    モデルを OSS にアップロードします。

    OSS コンソールにログインし、バケット名をメモします。まだ作成していない場合は、「バケットの作成」をご参照ください。その後、モデルファイルをアップロードします。

    ossutil のインストール手順については、「ossutil のインストール」をご参照ください。
    ossutil mkdir oss://<your-bucket-name>/Qwen3-32B
ossutil cp -r . oss://<your-bucket-name>/Qwen3-32B

    PersistentVolume (PV) と PersistentVolumeClaim (PVC) を作成します。

    llm-model という名前の PV は、OSS バケットディレクトリを読み取り専用ストレージとして推論ポッドにマウントします。以下のいずれかの方法を選択してください。

    ACK コンソールを使用

    1. [PV の作成]

      • ACK コンソールにログインし、左側メニューで [クラスター] をクリックします。

      • [クラスター] ページで、対象クラスターの名前をクリックします。左側メニューで、[ボリューム] > [永続ボリューム] を選択します。

      • 右上隅にある [作成] をクリックします。

      • [PVの作成] ダイアログボックスで、以下のパラメーターを設定します。

        [パラメーター]

        [値]

        [PVタイプ]

        OSS

        [ボリューム名]

        llm-model

        [アクセス証明書]

        OSS バケット用の AccessKey ID と AccessKey シークレット

        [バケットID]

        前の手順で作成した OSS バケット

        [OSSパス]

        /Qwen3-32B

    2. [PVC の作成]

      • [クラスター] ページで、対象クラスターの名前をクリックします。左側メニューで、[ボリューム] > [永続ボリューム要求] を選択します。

      • 右上隅にある [作成] をクリックします。

      • [PVCの作成] ダイアログボックスで、以下のパラメーターを設定します。

        [設定項目]

        [値]

        [PVCタイプ]

        OSS

        [名前]

        llm-model

        [割り当てモード]

        既存ボリューム

        [既存ボリューム]

        [PVの選択] をクリックし、作成した PV を選択します

    kubectl を使用

    1. 以下の内容で llm-model.yaml という名前のファイルを作成します。このファイルは、OSS の認証情報を持つ Secret、モデルディレクトリを指す静的 PV、およびその PV にバインドする静的 PVC を定義します。

      apiVersion: v1
kind: Secret
metadata:
  name: oss-secret
stringData:
  akId: <your-oss-ak>       # OSS バケットへのアクセスに使用する AccessKey ID。
  akSecret: <your-oss-sk>   # OSS バケットへのアクセスに使用する AccessKey シークレット。
---
apiVersion: v1
kind: PersistentVolume
metadata:
  name: llm-model
  labels:
    alicloud-pvname: llm-model
spec:
  capacity:
    storage: 30Gi
  accessModes:
    - ReadOnlyMany
  persistentVolumeReclaimPolicy: Retain
  csi:
    driver: ossplugin.csi.alibabacloud.com
    volumeHandle: llm-model
    nodePublishSecretRef:
      name: oss-secret
      namespace: default
    volumeAttributes:
      bucket: <your-bucket-name>       # バケット名。
      url: <your-bucket-endpoint>      # エンドポイント (例: oss-cn-hangzhou-internal.aliyuncs.com)。
      otherOpts: "-o umask=022 -o max_stat_cache_size=0 -o allow_other"
      path: <your-model-path>          # モデルディレクトリへのパス (例: /Qwen3-32B/)。
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: llm-model
spec:
  accessModes:
    - ReadOnlyMany
  resources:
    requests:
      storage: 30Gi
  selector:
    matchLabels:
      alicloud-pvname: llm-model

    2. 設定を適用します。

      kubectl create -f llm-model.yaml

    ステップ2: 推論サービスのデプロイ

    vLLM を使用したスタンドアロン推論サービスのデプロイ

    1. vllm.yaml という名前のファイルを作成します。

      YAML テンプレートを展開して表示

      apiVersion: apps/v1
kind: StatefulSet
metadata:
  labels:
    # Prometheus がスクレイピングするためのラベル
    alibabacloud.com/inference-workload: vllm-inference
    alibabacloud.com/inference_backend: vllm
  name: vllm-inference
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      alibabacloud.com/inference-workload: vllm-inference
      alibabacloud.com/inference_backend: vllm
  template:
    metadata:
      labels:
        alibabacloud.com/inference-workload: vllm-inference
        alibabacloud.com/inference_backend: vllm
    spec:
      volumes:
      - name: model
        persistentVolumeClaim:
          claimName: llm-model
      - name: dshm
        emptyDir:
          medium: Memory
          sizeLimit: 15Gi
      containers:
      - command:
        - sh
        - -c
        - vllm serve /models/Qwen3-32B --port 8000 --trust-remote-code --max-model-len 2048 --gpu-memory-utilization 0.85 --tensor-parallel-size 2
#        image: vllm/vllm-openai:v0.10.0
        image: kube-ai-registry.cn-shanghai.cr.aliyuncs.com/kube-ai/vllm:v0.10.0
        name: vllm
        ports:
        - containerPort: 8000
          name: http
        readinessProbe:
          initialDelaySeconds: 30
          periodSeconds: 10
          tcpSocket:
            port: 8000
        resources:
          limits:
            nvidia.com/gpu: "2"
            memory: "16Gi"
            cpu: "4"
          requests:
            nvidia.com/gpu: "2"
            memory: "16Gi"
            cpu: "4"
        volumeMounts:
        - mountPath: /models/Qwen3-32B
          name: model
        - mountPath: /dev/shm
          name: dshm
---
apiVersion: v1
kind: Service
metadata:
  name: inference-service
spec:
  type: ClusterIP
  ports:
    - port: 8000
      protocol: TCP
      targetPort: 8000
  selector:
    alibabacloud.com/inference-workload: vllm-inference

    2. サービスをデプロイします。

      kubectl create -f vllm.yaml

    ステップ3: 推論サービスの検証

    1. ポートフォワーディングを設定して、ローカルからサービスにアクセスします。

      重要

      kubectl port-forward は開発およびデバッグ専用です。本番環境レベルの信頼性、セキュリティ、スケーラビリティは備わっていません。本番トラフィックについては、「Ingress 管理」をご参照ください。

      kubectl port-forward svc/inference-service 8000:8000

      期待される出力：

      Forwarding from 127.0.0.1:8000 -> 8000
Forwarding from [::1]:8000 -> 8000

    2. テストリクエストを送信します。

      curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "/models/Qwen3-32B", "messages": [{"role": "user", "content": "Test"}], "max_tokens": 30, "temperature": 0.7, "top_p": 0.9, "seed": 10}'

      成功した場合のレスポンスは次のようになります。

      {"id":"chatcmpl-d490443cd4094bdf86a1a49144f77444","object":"chat.completion","created":1753684011,"model":"/models/Qwen3-32B","choices":[{"index":0,"message":{"role":"assistant","reasoning_content":null,"content":"<think>\nOkay, the user sent \"Test\". I need to confirm their request first. They might be testing my functionality or want to see my reaction.","tool_calls":[]},"logprobs":null,"finish_reason":"length","stop_reason":null}],"usage":{"prompt_tokens":10,"total_tokens":40,"completion_tokens":30,"prompt_tokens_details":null},"prompt_logprobs":null,"kv_transfer_params":null}

      レスポンスにメッセージを含む choices 配列が含まれていれば、モデルは正常に動作しています。

    次のステップ

    推論サービスが稼働したら、本番環境に対応するために以下の次のステップを検討してください。

    • LLM 推論サービスのモニタリングの設定：Managed Service for Prometheus と統合して推論メトリクスを収集し、パフォーマンスのボトルネックを検出し、リソース割り当てのための長期的な傾向を分析します。

    • LLM 推論サービスの自動スケーリングの設定：Horizontal Pod Autoscaler (HPA) と ack-alibaba-cloud-metrics-adapter を使用して、GPU、CPU、メモリ使用率に基づいてポッドを自動的にスケーリングします。これにより、アイドル期間中のコストを低く抑えながら、トラフィックスパイクに対応できます。

    • Gateway with Inference Extension を使用したインテリジェントルーティングとトラフィック管理の実装：モデル名でリクエストをルーティングし、単一のエンドポイントで複数の LoRA バリアントを管理し、重要なモデルに優先度レベルを割り当てます。

    • Fluid データキャッシュの最適化ポリシーのベストプラクティス：クラスターノード間でモデルデータをキャッシュすることにより、大規模なモデルファイル (>10 GB) のポッドのコールドスタート時間を短縮し、再起動のたびに OSS からの繰り返しダウンロードを回避します。
