### 2.2 The nearest sibling things, and why each falls short

**`kagi` — `corpus/source-fetches.tsv` + `corpus/inrow-pins.tsv` + `corpus/sources-census.sh`.** This is the
closest cousin in the whole fleet: a **digest-provenance ledger with a computed verdict vocabulary**, checked by a
gate that *recomputes* the verdict rather than trusting the row (`kagi-shokunin/corpus/sources-census.sh:74-77`,
`:309-311`):

```
reproduces-raw | reproduces-normalized | non-reproducing
```

Three ways it falls short of C2:

1. **64-hex only.** `SC_FETCH` checks `Fetch sha256:` (`:249`) and `sha256sum` of the row identity (`:262`). It
   never classifies a 40-hex git oid, a 32-hex MD5, or an over-long run. C2's token rule is
   `32 <= L <= 127, L != 64` (`tools/round43-hexrun-audit.py:17-18`) — a *disjoint* token space.
2. **The verdict vocabulary is about reproduction, not existence.** kagi's three classes answer "does the capture
   still hash to the pin?". C2's classes answer "what *is* this run?" — `lane_oid` (the object exists in this
   repo), `md5_blob` (it is the MD5 of a blob), `upstream` (an evidence file proves it), `unverifiable`,
   `wrong_flagged`.
3. **No ledger row is a *classification*; it is a *pin*.** kagi's ledger rows carry no `repo`/`evidence`/`correct`
   columns, so nothing in kagi could answer C2's `wrong` leg ("`correct` is a different token-shaped run that
   classifies lane_oid, md5_blob or upstream, and shares its first 8 characters with `token`",
   `round43-hexrun-audit.py:32-35`).

**`kaidoku` — `tools/round-26/c2-calibration.py`.** Resolves a *cited revision*: "the first 7-40 hex revision
following the word `measured` in the evidence cell resolves" (`:14-15`, `:210-217`,
`first_hex_after_measured`), checked with `git rev-parse --verify <rev>^{commit}` (`:316`). This is C2's
`lane_oid` class with a narrower population (one cell of one SCORECARD row) and no ledger at all: a token that
does not resolve is simply a mismatch, with no `unverifiable` / `wrong` escape.

**`kake` — `scripts/landed_check.py`.** The one sibling tool that *extracts hex runs from prose* and
*suppresses the ones that are not object ids* — and it does so by a rule C2 does not have: a token that resolves
to nothing but whose line names a digest algorithm is silently skipped as a "digest fragment"
(`kake-shokunin/scripts/landed_check.py:11-14`, `:52-58`):

> An unresolvable hex token on a line that names a digest algorithm (`sha256`, `sha1`, `md5`, …) is suppressed
> as a digest fragment rather than reported as an unknown commit.

Its token window is 7–40 and it skips 64-hex by construction (`HEX_RUN` at `:53-56`, `DIGEST_LEN = 64`), so it sees
neither C2's 32-hex MD5 class nor the 65-hex over-long class. It also **has no ledger**: an unresolvable
non-digest token is `UNKNOWN, counted as cited and unknown` (`:22-27`) — a count, not a classification.

**`kotodama` — the same defect class, found by hand.** `kotodama-shokunin/corpus/lessons/round-10.md:158`:
"the survey's own sweep of the ledger's `output_sha256` column finds **14** rows non-64-hex (0-based 20, 29–37,
56, 59, 60, 183)". That is precisely C2's population class, discovered by a human reading a JSON ledger — and
kotodama never built a census for it. `kotodama-shokunin/tools/harness/receipt_guard.py:45` uses
`OID_RE = re.compile(rb"(?:[0-9a-f]{40}|[0-9a-f]{64})")` — a 40-or-64 whitelist, so a 39-hex or 65-hex run is
simply not an oid to it.

**`mori` — `tools/mori-freeze-order.py:73`, `mori-content-review.py:22`, `mori-retention-gate.py:33`,
`mori-evidence-loss.py:34`.** All four use the same 40-or-64 whitelist: `re.compile(r"(?:[0-9a-f]{40}|[0-9a-f]{64})\Z")`.
This is the fleet-wide idiom — *validate a run as an oid or a digest* — and C2 is the first thing in the fleet that
**classifies a run that is neither**.

### 2.3 What C2 would be the first of, stated precisely

C2's `tools/hexrun-census.py` would be the fleet's first instrument that, for a run that is **not** a 40-hex git

`ledger_bad` for a row that fails its own class's rules. Every sibling analogue either validates (40-or-64),
suppresses (kake), or counts (kotodama's hand sweep).

## 3. Three transferable patterns (lane, path, line)

### Pattern A — attribute by rule, not by substring (`mori`)

* **Lane:** `mori`
* **Path:** `mori-shokunin/tools/mori-gate-registry.py`
* **Line:** `:11-16` (the attribution rule), `:205-233` (`is_standard_header` / `parse_tables`), `:376-390`
  (the row that attributes a path)

> For each audited path exactly one attribution rule applies: the path's own row is the row whose `entry` cell's
> first backticked command invokes that path. Prose, a substring elsewhere in a cell, and a row naming another
> tool never attribute.

**Why it transfers to kama:** kama's gate registers a path if the path occurs in **any** cell of a 5-column row
(`kama-shokunin/tools/gate-registry-check.py:11-14`). That is why the C1 counter's `flags` leg has to
re-derive attribution itself (`round43-registry-audit.py:143-147`, matching `path in l` over all pipe rows) while
`mori` gets it right once, in one place. If C1's registry repair puts a counter path in a row whose *entry* cell
does not invoke it, mori's rule would say "not attributed" and kama's gate would say "registered" — the two
disagree, and the disagreement is invisible unless the rule is explicit.

### Pattern B — the self-test must be a real argv branch (`mori`)

* **Lane:** `mori`
* **Path:** `mori-shokunin/tools/mori-gate-registry.py`
* **Line:** `:15-16` (the rule), `:325-345` (`escape_branch`), `:590-593` (the comment-only false positive is
  rejected by the selftest), `:562` (a tool with no `--selftest` is rejected)

> the tool must carry a real self-test argv branch: an occurrence of `--selftest` inside a comment line or a
> docstring is not a branch (the r44 silence-oracle false positive).

**Why it transfers to kama:** this is a live hole in kama's own C1 counter. `round43-registry-audit.py:68` uses

```python
ADD_RE = re.compile(r"add_argument\(\s*[\"'](--[a-z][a-z0-9-]*)")
```

and `ADD_RE.findall()` over the **raw source text** of each counter. I ran that regex against kama's three
round-43 counters and found a phantom flag:

```
$ python3 -c "…ADD_RE.findall(open('tools/round43-registry-audit.py').read())…"
['--flag', '--out', '--repo', '--tip']
```

`--flag` comes from **line 18**, the counter's own docstring:
`every \`--flag\` it names must be declared by an \`add_argument("--flag"\``. An AST walk of the same file shows
the real parser keys are only `--out --repo --tip`. So `--flag` is a *declared* flag that the tool does not have.

This is a **frozen-counter observation, not a fix** — the preregistration, the counters and the controls are
frozen and this is a finding for the closure, not something to edit in place. Its consequence is bounded but
real: the C1 `flags` leg would accept a registry row naming `--flag` for `tools/round43-registry-audit.py` even
though no such option exists. `mori`'s `mask_python` / `mask_shell` (`:325-345`) is the exact mechanism that
would have caught it, and it is worth quoting in the round-43 lesson as the reason a future counter should mask
docstrings before matching.

### Pattern C — the operative table is chosen by an exact heading, and the population is split by a baseline
(`tsukuroi`)

* **Lane:** `tsukuroi`
* **Path:** `tsukuroi-shokunin/tools/check-registry-coverage.py`
* **Line:** `:52-53` (`REGISTRY_HEADING`), `:194-221` (`_operative_rows` — "operative section must contain exactly

## 4. Three measured cross-claim risks inside kama (not siblings)

These are risks to the *lane's own* round-43 claims, discovered while scanning siblings, and they are the
practical part of this seat's report.

### 4.1 The `registry/digest-ledger.tsv` document-set overlap — C2 can turn round-42's C2 red

`tools/digest-ledger.py:76` defines its document set as:

```python
def is_doc(rel: str) -> bool:
    return not rel.startswith(".ufo/") and rel != LEDGER and rel.endswith((".md", ".tsv"))
```

with `LEDGER = "registry/digest-ledger.tsv"` (`:69`). **`registry/hexrun-ledger.tsv` is not excluded.** C2's
counter *does* exclude both (`round43-hexrun-audit.py:83`,
`LEDGERS = ("registry/hexrun-ledger.tsv", "registry/digest-ledger.tsv")`) — so the two tools disagree about the
document set, and the round-42 tool is the one that is blind.

I measured the consequence in the fixture repo. I added a `registry/hexrun-ledger.tsv` whose `note` column carries
a 64-hex sha256 (a natural thing to write — the note that says which bytes were hashed), and re-ran the round-42
counter:

```
$ python3 tools/round42-digest-audit.py --repo "$D" --tip <tip>
tip=d0d24e5bc6b8635fe84c4bf39f3c1e913743fd5b
tool=1 contract=1 live=0 hygiene=1 capability=1 met=False seed=1951028631
live-reference: tokens=99 blob=89 external_ok=5 external_absent=0 unverifiable=3 wrong_flagged=1 ledger_bad=0 wrong_unflagged=0 unknown=1 exit=1
detail: live: … unknown=1 exit=1 …
```

**The round-42 counter's `live` leg goes 1 → 0 and its `met` goes True → False, because the new ledger file's
`note` column is read as a document and its 64-hex sha256 is an unknown token.**

This is a live, reproducible interaction between two of kama's own claims, and it is *not* caught by either
counter's own legs (C2 excludes the file from its own census; round 42 does not know the file exists).

**Proposed fix (for the L1 to weigh, not for me to apply — the counters and preregistration are frozen):**
either (a) write C2's ledger so that no cell carries a 64-hex run — the `note` column is free text and the
`token`/`correct` columns are not — or (b) extend `tools/digest-ledger.py`'s `is_doc` to exclude
`registry/hexrun-ledger.tsv` as well. Option (b) changes a round-42 tool and therefore its sha256 pin, which
feeds C1's `pins` leg; option (a) changes only C2's own artifact. **Option (a) is the cheaper and safer one,
and it is the one I recommend.** A third option — extending round 42's ledger to also cover 32/39/65-hex — is
explicitly out of scope: that is C2's capability, and round 42's `TOKEN` rule
(`tools/digest-ledger.py`, `TOKEN = re.compile(r"(?<![0-9a-f])[0-9a-f]{64}(?![0-9a-f])")`) is frozen.

**This is also the lane's own precedent for a ledger analogue, and it argues that the right shape is a *second*
file, not a rewrite:** round 42 created `registry/digest-ledger.tsv` alongside `tools/digest-ledger.py` with its
own header (`digest class subject path correct verified-at note`,
`registry/digest-ledger.tsv:1`) and its own tool contract (`round42-digest-audit.py:16-26`), leaving the 64-hex
world intact. C2 should mirror that: `registry/hexrun-ledger.tsv` with header
`token class repo evidence correct verified-at note` (`round43-hexrun-audit.py:26`), a new tool
`tools/hexrun-census.py`, and **no change** to round 42's tool or ledger.

### 4.2 The C1 `pins` leg reads cells positionally, and kama's SKILL.md has two incompatible row widths

This is the finding I would most want the L1 to see before the C1 repair is attempted, because it changes *where*
the repair must land.

C1's `pins` leg (`round43-registry-audit.py:151-168`):

```python
cells = [c.strip() for c in l.strip().strip("|").split("|")]
if len(cells) >= 4 and re.search(r"[0-9]", cells[2]) and any(want.startswith(h) for h in SHA_RE.findall(cells[3])):
```

So: **exit digit in `cells[2]`, sha256 pin in `cells[3]`** — unconditionally, whatever the table's width. And
`SHA_RE = re.compile(r"sha256 `([0-9a-f]{8,64})")` (`:78`) requires the literal text `` sha256 `<hex>` `` with a
backtick-quoted value of 8–64 hex characters, and `want.startswith(h)` requires the pin to be a **prefix** of the
counter's actual blob sha256.

Meanwhile the gate C1 grades (`tools/gate-registry-check.py:148-169`) accepts **only 5-column** tables:
`len(hdr) == 5`, `hdr[0] == "name"`, "kind" or "entry" in `hdr[1]`, "exit" in `hdr[2]`, "self-test" or "selftest"
in `hdr[3]`. A 7-column table's `hdr[2]` is "Verdict map" — no "exit" — so **the gate cannot see the 13
seven-column tables at all**. I confirmed this by enumerating the tables directly:

```
gate-visible 5-cell registry tables: 6
  line 303 ['Name', 'Kind / entry command', 'Exit map', 'Self-test / pinned values', 'Write scope']
  line 373  …  line 1224  …  line 1308  …  line 1323  …  line 1371  …
line 396 hdr[2]= 'verdict map (code -> class)' contains 'exit'? False
line 430 hdr[2]= 'verdict map' contains 'exit'? False
```

I then tested both shapes in the fixture repo, at the same tip, with the same sha256:

* **7-column row** (sha in the "Pinned values" cell, index 4): `unreg=19 pins=19` — **no improvement**. The gate
  does not see the row (7 columns), and the counter's `cells[3]` is the *Self-test* cell, which has no sha256.
* **5-column row** (sha in the "Self-test / pinned values" cell, index 3): `unreg=18 pins=18` — **both legs
  improve by one**. This is the only shape that satisfies the gate and the pins leg simultaneously.

**Consequence for the C1 repair: the 19 NEWSET counters need 19 new rows in a 5-column table** whose header is
exactly `Name | Kind / entry command | Exit map | Self-test / pinned values | Write scope`, whose exit-map cell
carries a digit, and whose 4th cell carries `` sha256 `<8..64-hex prefix of the counter's blob at the tip>` ``.
Editing any of the 13 seven-column tables achieves nothing — and, worse, the `flags` leg
(`round43-registry-audit.py:143-147`) matches `path in l` across **all** pipe rows with ≥5 cells, so a path
mentioned in a 7-column table satisfies `flags` while the gate still calls it unregistered. That asymmetry is
how `flags` can be 0 while `unreg` is 19.

**And the `flags` leg has a second, sharper trap.** `named = FLAG_RE.findall(cells[1])` with
`FLAG_RE = re.compile(r"(?<![\w-])--[a-z][a-z0-9-]*")` (`:67`) — so the *entry* cell must name at least one
`--flag`, and every `--flag` it names must appear in the counter's `add_argument` calls. But `cells[1]` is the
"Kind / entry command" cell, whose natural content is a **command line**, e.g.
`` `python3 tools/round42-capacity-audit.py --repo R --tip T` `` — which names `--repo` and `--tip`. Both are
declared by that counter, so it passes. But a row written as `` `python3 tools/foo.py` `` with no flags at all
fails (`named` is empty ⇒ `ok` stays False), and a row naming a flag the counter does **not** declare also fails.
I checked the declared flags of all three round-43 counters:

```
tools/round43-registry-audit.py : --out --repo --tip   (plus the phantom --flag from line 18)
tools/round43-hexrun-audit.py    : --out --repo --seed --tip
tools/round43-health-audit.py    : --base --out --repo --tip
```

So the round-43 rows must name only flags from those sets. `--seed` is on `hexrun-audit` only; `--base` is on
`health-audit` only.

### 4.3 A third, softer risk: a new "canonical list as of round N" table silently un-seats round 42's capability row

`round42-digest-audit.py:270-283` selects the **highest-numbered** "canonical list as of round N" table, and its
`capability` leg requires a `digest-ledger` row in that table (`:58-60`). C2's capability leg
(`round43-hexrun-audit.py:57-60`) likewise requires a `hexrun-census` row in the highest canonical table. If C2
adds a *new* `as of round 43` table carrying only the `hexrun-census` row, round 42's `capability` leg goes to 0.
I measured it:

```
$ python3 tools/round42-digest-audit.py --repo "$D" --tip <tip with a round-43 canonical table>
tool=1 contract=1 live=1 hygiene=1 capability=0 met=False seed=502171543
detail: no digest-ledger row in canonical list as of round 43
```

**Consequence:** the round-43 capability table must carry **both** the `digest-ledger` row and the new
`hexrun-census` row, or round 42's C2 turns red at the round-43 tip. This is the same class of problem as §4.1
and §4.2 — a claim's artifact silently changing a *sibling claim's* truth — and it is the reason this seat
exists. (Note `tools/capability-repertoire-audit.py` also reads the canonical table — "the first capability-shaped
table after the line that names it, matching `**Capabilities - canonical list as of round N**`; the highest N
wins" — and it prints `listed 8 observed 8 missing 0 unsubstantiated 0 met True` at the freeze tip, so it is
currently green and must stay green.)

## 5. Cross-claim: could C1's NEWSET rows and C2's ledger be reused by a sibling?

**C1's NEWSET rows: no, not as data — yes, as a shape.**
**C2's ledger: no, not as data — yes, as a shape, and the shape is already the lane's own precedent.**

### 5.1 C1's NEWSET rows are a frozen, kama-local list

`round43-registry-audit.py:69-77` is a hard-coded list of 19 kama paths:

```python
NEWSET = [
    "tools/round35-coverage-audit.py", … "tools/round42-selfdesc-reconcile.py",
    "tools/round43-registry-audit.py", "tools/round43-hexrun-audit.py",
    "tools/round43-health-audit.py",
]
```

Sixteen are round-35..42 counters, three are round 43's own. **A sibling cannot reuse the rows**: the paths do
not exist in a sibling's tree, the sha256 pins are of *kama's* blobs, and the counter's `pins` leg resolves the
blob **at kama's tip** (`round43-registry-audit.py:154`, `blob(repo, tip, path)`).

What a sibling *can* reuse is the **schema** of the repair — which is exactly what §4.2 fixes: a 5-column table
whose entry cell names only declared flags, whose exit cell carries a digit, and whose 4th cell carries
`` sha256 `<prefix>` `` of the counter's own blob. The sibling pattern for that schema already exists twice in
the fleet and is worth copying instead of inventing:

* **`mori` — `mori-shokunin/SKILL.md:184`**, a single 8-cell row pinning its own gate tool's sha256:
  `` `python3 tools/mori-gate-registry.py --selftest` → measured `GATE_REGISTRY_SELFTEST pass=15 fail=0` at sha256
  `8b82ac999091ebe65e765ed69f759910a57049ff0e7c5c4aa56df9c7168f5832` (743 lines) ``. I verified that pin against
  the committed blob:

  ```
  $ git -C mori-shokunin cat-file -p HEAD:tools/mori-gate-registry.py | sha256sum
  8b82ac999091ebe65e765ed69f759910a57049ff0e7c5c4aa56df9c7168f5832  -
  $ sha256sum mori-shokunin/tools/mori-gate-registry.py
  8b82ac999091ebe65e765ed69f759910a57049ff0e7c5c4aa56df9c7168f5832  mori-shokunin/tools/mori-gate-registry.py
  ```

  **It matches exactly** — a self-describing pin of the sort C1's `pins` leg demands, on the same lane-clock
  (a pin that goes stale the moment the tool is edited).

* **`kumitate` — `.ufo/pins/counter-pins.json`**, 30 pins of the form
  `{round, name, path, sha256}`, with `scripts/counter-pins.mjs` refusing `path-escape` and symlinked targets
  (`kumitate-shokunin/scripts/counter-pins.mjs:32-41`) and refusing an **empty** pin set (`:39`,
  "an EMPTY pins[] array is DRIFT `pins-empty`, not CLEAN"). The JSON form is the better shape for a *reusable*
  pin registry because it is machine-readable without a markdown parser.

### 5.2 C2's ledger is lane-local by construction, but its *tool* is portable

C2's ledger rows are statements about **kama's** documents: the token is a run that appears in a kama `.md`/`.tsv`,
the `evidence` cell names a kama blob at kama's tip, the `correct` cell is a run that resolves in kama's repo.
**A sibling cannot reuse the rows.** The header (`token class repo evidence correct verified-at note`,
`round43-hexrun-audit.py:26`) and the **class semantics** are lane-independent and are directly reusable —
`lane_oid` / `md5_blob` / `upstream` / `unverifiable` / `wrong` are properties of a run, not of a lane.

The tool contract is already written to be portable: `hexrun-census.py scan (--repo R --rev REV | --dir DIR)
[--ledger FILE] [--details]` and `hexrun-census.py selftest` (`round43-hexrun-audit.py:12-13`), with a `--dir`
mode that works on any directory tree and no kama-specific path baked in. **A sibling could adopt the tool
verbatim** — and should, because it is the first such instrument in the fleet and re-implementing it would
re-create the class-vocabulary drift that §2 documents.

**The one genuinely reusable C2 artifact is the corpus of *classes*, not the ledger.** §2.2's inventory — the
40-or-64 whitelist idiom (`mori-freeze-order.py:73`, `mori-content-review.py:22`, `kotodama
tools/harness/receipt_guard.py:45`), kake's digest-label suppression (`landed_check.py:52-58`), and kotodama's
hand-found 14 non-64-hex rows (`corpus/lessons/round-10.md:158`) — is a list of the classes other lanes need and
do not have. C2 supplies the vocabulary for them.

### 5.3 The cross-claim answer in one line

> **C1's NEWSET rows and C2's ledger cannot be reused as data by any sibling** — both are statements about kama's
> tree at kama's tip, and C1's list is hard-coded at `round43-registry-audit.py:69-77`. **Both can be reused as
> shapes**: C1's row schema (5-column, pin in cell 3) is the pattern `mori` already implements and verifies at
> `mori-shokunin/SKILL.md:184`, and C2's tool and class vocabulary are the fleet's first and are directly
> adoptable by a sibling — no sibling holds either today.
