**Round-48 v5 provenance and replay (appended 2026-10-26; S492, S493).** Round 47 showed the b11909 runs could be re-run; round 48 makes the inputs checked when they are recorded and the comparison wider than pass/fail. `--server-archive` selects receipt schema `kama-llamacpp-live/v5`: once any provenance flag is given, the live tool requires all five (`--server-asset-url`, `--server-asset-sha256`, `--server-member`, `--model-url`, `--server-archive`), https-only URLs, a member path with no leading `/` and no `..`, and a model URL pinned to `/resolve/<40-hex>/`; before the server starts it hashes the archive against the asset digest and the named member's bytes against the server binary's sha256, and otherwise exits 2 having started nothing. The receipt adds `provenance.model.commit` and `provenance.verified` {`at`:`record`, `archive_sha256`, `member_sha256`, `model_sha256`}. Without `--server-archive` the receipt stays v4, so v5 is the caller's choice, not the tool's default.

The 40-hex form is not cosmetic. The Hub requires the full-length commit in place of a 7-character one (S493), and a resolve URL naming a full commit serves fixed bytes: S492 records the response `x-repo-commit` as the commit the URL names and the served digest as S039's `270cba1b…256d` (headers, downloaded copy and revision API in `.ufo/waves/round-48/c2/hf-revision-499bc882.txt`), so a replay reproduces or refuses instead of drifting with `main`. S492 supersedes S490's moving `main` URL as this locator; S490 stays filed as recorded.

Replay: `tools/kama-live-replay.py --receipt R --work DIR --out J` accepts v4 and v5, downloads both recorded URLs into `--work`, verifies each digest before extraction or execution, checks the extracted member's bytes against the receipt's `server.sha256` before running it, and for a v5 receipt passes the downloaded archive as `--server-archive`, so the rerun is verified at record time too. What the replay still cannot show:

- **The `verified` block is declared, not re-graded, by the replay tool.** `kama-live-replay.py` requires only `verified.at == "record"`; its three digests are never compared with the receipt's asset/member/model digests, and the stable projection excludes provenance. A copy of receipt-1 whose three `verified` digests are all wrong passes the tool's provenance check and yields zero mismatches under `--compare` (round-48 S9Knowledge probe, `.ufo/waves/round-48/w1/out/S9Knowledge.md`). The committed receipts are bound because the C2 counter's `receipts` leg compares those values with the frozen constants, not because the replay does.
- **Instance facts are not reproduced.** Only the stable projection is compared, so a replay cannot show that the original run used the recorded port, pid, timings or log text.
- **Byte equality is not authenticity.** Both tools fetch over HTTPS and compare sha256; they do not check signatures, pin TLS, or attribute the build to upstream.
- **Provenance covers three artifacts.** The `verified` block binds the archive, the `llama-server` member and the model. The other install-tree members, the soname links, `libllama-server-impl.so` and system libraries are recorded in the receipt but not re-derived from provenance, so the round-18/19/21 pin limits still apply to a v5 replay.
- **A red replay can be a missed observation.** The loading window is short and can fall between polls; a rerun with no 503 leaves `loading_envelope_graded` unevaluated, which the comparison reports as `check:loading_envelope_graded:not-evaluated` and fails. That is sampling, not a lifecycle change.
- **Scope unchanged.** One build (b11909), CPU, fixture `stories260K`, single-model mode, an unregistered loopback port; not generation, quality, performance, GPU, router mode, sleep, or registered-consumer health (8080 and 34113 untouched). Offline, the replay refuses (`could-not-run`, exit 2) rather than passing or failing.
