## Finding (draft defect, not fixed in place)

`tools/release-recheck.py` locates the release range by first text hit. For S170 the cited
line is pin L414 (the **object-branch** guard
`if (tok >= 0 && tok < n_vocab) ... push_back({tok, bias})` after `strtol`), but the draft
(`.ufo/waves/round-44/c1/draft-ledger.tsv:76`) paired it with release **L420** — the
**array-branch** twin with byte-identical text — while the true counterpart is release
**L433**. Show it:

```
$ git -C <LL> show d854d98b:tools/server/server-schema.cpp | sed -n '420p;433p'
                        if (tok >= 0 && tok < n_vocab) ctx.params.sampling.logit_bias.push_back({tok, bias});
                        if (tok >= 0 && tok < n_vocab) ctx.params.sampling.logit_bias.push_back({tok, bias});
```

Consequence: the frozen counter still reports `VALID` because it compares text, not
position (`tools/round44-release-recheck-audit.py:44`), so a `holds` on this row would
survive a real change to the object-branch guard as long as the array-branch twin stayed
equal. Proposed fix (lane files are frozen; not applied): have `tools/release-recheck.py`
prefer the pairing that preserves the pin→release line offset (or search nearest to
`pin_line + offset`) and fall back to first hit only when no offset-consistent hit exists;
then re-emit the S170 row as `382-414 / 401-433`. My fragment already uses the corrected
pairing, so this row is not exposed in the integrated ledger for these six ids — but the
same first-hit pattern can silently affect other seats' rows in the other 85.
