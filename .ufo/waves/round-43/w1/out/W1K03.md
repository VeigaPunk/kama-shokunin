## Part 3 — Falsification: what the C3 counter actually accepts

The seat's second duty is the first falsifier pass. I built a synthetic tip in my
own seat clone and ran the **real, frozen** counter
`tools/round43-health-audit.py` against it (counter unmodified; the lane's clone
was never written to). Receipts are in `.ufo/waves/round-43/w1/out/W1K03/`.

### 3.1 The counter is satisfiable — and one landmine is not obvious from the spec

The counter's `coverage` leg requires a README line naming the entry by the path
`corpus/knowledge/runtime-health-surface-processes.md` (the counter checks
`ENTRY in l` for a line of `corpus/README.md`). But **the README's dominant
convention omits the `corpus/` prefix**: 54 lines use `` `knowledge/<file>.md` ``
and only 4 use `corpus/knowledge/…`. A builder following the README's own
convention writes a coverage-map row that the counter cannot see:

```
exp0-baseline-readme-pathfail.out:  entry=1 rows=1 coverage=0 gate=1 refetch=1 census=1 met=False
   detail: coverage: entry or README coverage line absent at tip
exp0b-fixed-readme-path.out:        entry=1 rows=1 coverage=1 gate=1 refetch=1 census=1 met=True   (exit 0)
```

The fix is to write **both** path forms in the row, which the README already does
once for a sibling entry (`corpus/README.md:627`,
`` `knowledge/context-capacity-engine-sides.md` (`corpus/knowledge/context-capacity-engine-sides.md`) ``).
**The L1's landed README row does exactly this** (`corpus/README.md:644`) — the
landmine was avoided, but it was avoidable only by luck or by having read the
counter's source; it should be recorded as a route check for the next round.

### 3.2 A second row for the same page URL shadows the counter's row resolution

The counter resolves a source to a registry row by scanning for the page URL and
taking the **last** matching row in file order, then validating *that* row's
cells. Two consequences, both reproduced:

- **A row whose source cell merely contains the PR page URL steals the PR slot.**
  Adding a third row for the pull request's commit list with the source cell
  `https://github.com/vllm-project/vllm/pull/58552/commits` (which *contains*
  the frozen page URL `https://github.com/vllm-project/vllm/pull/58552`) makes the
  counter validate the wrong row:
  ```
  exp1-commits-row-shadows-pr.out:  entry=0 rows=0 coverage=1 gate=0 refetch=1 census=1 met=False
     detail: row S482 (PR): anchor lacks copy sha256
     detail: entry provenance trio or source ids wrong: [...]
     detail: gate: no dated, <=25-word quote located in the copy for S482 (PR)
  ```
  The same URL in the **API** form (`https://api.github.com/repos/vllm-project/vllm/pulls/58552/commits`)
  does **not** contain the frozen page URL and the counter stays green:
  ```
  exp4-third-row-api-url.out:  entry=1 rows=1 coverage=1 gate=1 refetch=1 census=1 met=True   (exit 0)
  ```
  So the *form* of a URL in a `source` cell is load-bearing for this counter.

- **Two rows for one URL with the same scope cell break the census.** The census
  rule `E04` fires on "duplicate url … within scope" unless the second row's
  `teaches` cell says `supersedes S…`:
  ```
  exp2c-same-scope-duplicate.out:  ... census=0 met=False
  cen-exp2c.out:95: file E04 S482 duplicate url github.com/vllm-project/vllm/pull/58552 within scope …
  ```
  With **different** scope cells the same pair is only a W04 warning and the
  counter's own row/entry/gate legs still pass (the counter picks the later row,
  so the entry's `source:` line must name *that* row's id — `exp3c` shows
  `entry=0` when the entry names the earlier id instead).

  **This is why the lane's landed lesson collapses staged S441 into S481 is the
  right call**, and it is stronger than the lesson states: a second row for the
  same URL is not merely redundant, it either shadows the counter's row
  resolution or breaks the census.

### 3.3 The staged rows cannot be landed verbatim

Copying the staged rows S430/S431 (renumbered S480/S481) unchanged fails four
checks at once — the `rows` leg, the `census` leg, and the entry's provenance
line:

```
exp5b-verbatim-staged-rows.out:  entry=1 rows=0 coverage=1 gate=1 refetch=1 census=0 met=False
   detail: row S480 (REL): opened 2026-10-24, anchor lacks copy sha256
   detail: row S481 (PR): opened 2026-10-24, anchor lacks copy sha256
cen-exp5b.out:95: file E09 S480 recheck=90d — re-open the release page and expect the "Fast restart" entry …
cen-exp5b.out:97: file E09 S481 recheck=90d — re-open the pull request and expect the title to still read …
```

Three concrete transformations the staged rows need, each with a cause:

1. **`opened` must be `2026-10-25`** (the counter's `DATE`), not the staged
   `2026-10-24`.
2. **The `anchor` cell must carry the SHA-256 of the committed copy** — the
   staged anchor quotes the release prose instead.
3. **The `recheck` cell must be a bare cadence** (`90d`, `on-release`, or an ISO
   date). The staged cell is `90d — re-open … (ran 2026-10-24)`, which the census
   rejects as `E09`. The lane's own recent rows show the convention: S478's
   `recheck` cell is exactly `on-release` and the recheck *instruction* lives in
   the anchor cell; S206's is exactly `90d`.

### 3.4 The Gate quote must be the copy's byte form, not the staged page form

The staged anchors quote the release as `a /health endpoint ( #58552 )` (spaces
inside the parens, no backticks). The committed API copy carries
`` a `/health` endpoint (#58552) `` — backticked, no inner spaces. The counter
normalises whitespace but not punctuation, so the staged form does not occur in
the copy and the gate leg rejects it:

```
exp6-staged-quote-forms.out:  entry=1 rows=1 coverage=1 gate=0 refetch=1 census=1 met=False
   detail: gate: no dated, <=25-word quote located in the copy for S480 (REL)
   detail: gate: no dated, <=25-word quote located in the copy for S481 (PR)
```

The same applies to the pull-request title: the copy's title is
``[Fast Start] Add `/health` endpoint for the weight cache daemon`` and the
staged form drops the backticks. The counter's own frozen quote list is already
in the right form (``a `/health` endpoint (#58552)``), which is the tell.

### 3.6 The two committed copies are not byte-stable across fetches

The landed lesson notes it; I measured it. A second `gh api` fetch of PR 58552
differs from the committed copy in the `base` object only — the repository's
open-issue and size counters moved between fetches:

```
committed copy : 25514 bytes, sha256 976ea2ea9d6230005eda35adc3b49cbf048fb4f7c37756c461b70a3781a314b9
my re-fetch    : 25514 bytes, sha256 aff67c2ea3ae8214fff117d5c13796f0c6dac90ddea2f4a3d460e66020b78a21
cmp → differ at char 17605; json key diff = ['base']
  "open_issues_count': 9433"  vs  "open_issues_count': 9432
   "size': 328276"             vs  "size': 328195
```

The release object is byte-identical across fetches (both
`20c282d566d6788b0913bae9090b85a36263d0adb6ecb9112ea923100a71ab21`), and
`title` and `body` are equal in both PR copies. The consequence is a real
verification hazard for any seat that re-fetches and compares the whole file: it
will report a digest mismatch that is not a defect. The landed row's anchor cell
therefore pins the **committed** digest, and a verifier must compare `title` +
`body` (or the committed blob), not the whole object. The landed lesson already
says this — "this object's bytes are volatile inside …" — which is correct and
worth carrying into the closure.

## Part 4 — Proposed move (one bounded proposal)

**Move: re-point the hosted-platform health family from kake to the lane that
actually owns hosted model-serving deployment configuration, and record the
re-point in the round-43 refusals ledger — without changing any refusal
decision.**

The refusals stand on their own reasoning ("remote platform deployment field …
not local endpoint health"). What is wrong is only the *destination* they name,
and it has been wrong for four rounds while the family sat in the staged package
unclaimed. The proposal is to record, in `registry/staged-refusals.tsv` (the
landed ledger, `file:hosted-health-route-configuration.md`, line 16) and in the
round-43 lesson's Assimilation set, that:

- the family's **subject** is hosted *model-serving deployment* configuration
  (Vertex AI `serving_container_health_route`, SageMaker `AIP_HEALTH_ROUTE`,
  Azure Container Apps `appHealth`, Azure ML `inference_config`) — a field that
  decides *which route a platform's orchestrator probes on a vLLM container*;
- it is **not** kake's province, because kake's province is "web properties &
  publishing" (PROVINCE.md:3) and "remote web properties" (PROVINCE.md:41), and
  kake's only hosted health knowledge is Render's own `healthCheckPath` for its
  own operator property (`render-web-services.md:62`, row S060) — a different
  family on a different platform;
- it is **not** kumitate's province either, because kumitate's PROVINCE.md:28
  sends local model serving to kama and its own domain is orchestration &
  tooling, not cloud vendor deployment fields;
- the honest owner is therefore **unassigned in this fleet**, and the flip
  condition should be re-stated as *a claim about which process or platform
  probes a served container's health route* rather than as a hand-off to kake,
  which no lane has accepted in four rounds of offering.

**Why this is the right move for this round.** It costs no counter leg (the
counter's `gate` leg requires an "admit" line and a "reject" line in the lesson's
`### Assimilation set`; the landed set has both, and this edit changes neither).
It adds no row, no tool and no probe. It converts a **silent dead-letter** — four
refusals pointing at a lane that never took the family — into a **named gap with
an owner question**, which is what the round's own `considerthese` proposal 3 was
reaching for when it built the ledger.

**One caution, stated as a contradiction rather than smoothed over.** The landed
lesson refuses the r13 gateway row S442 ("a different repository and a different
process (the gateway)") while kama's own `runtime-health-surface-matrix.md:22`
says "Routing/gateway health dispatch is kumitate's surface". Those two are not in
conflict — the gateway is a *vLLM-internal* gateway, not kumitate's dispatch
mechanism — but the sentence is close enough that the closure could read the
refusal as a mis-filing. If the L1 amends the ledger reason, one clause
distinguishing "the vLLM-internal gateway process" from "kumitate's
dispatch/route mechanism" removes the ambiguity at zero cost.

**Risk.** If the family is genuinely kake's — i.e. if the fleet intends kake's
domain to widen to hosted deployment configuration — this proposal would name a
gap where there is none. That is a province decision, not a seat's: it belongs to
the L0/integrator, and the honest outcome for this round is to *ask*, not to
re-point. The ledger's `flip` column is the right place to ask it, and the
existing `today=yes` markers already show the family keeps being re-offered
(rounds 35, 36, 39, 40, 41) — five rounds of an offer nobody answers.
