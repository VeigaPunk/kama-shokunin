## 1. The pattern that links the four held entries and staged r7–r16

One sentence, from the held corpus itself: *a path is not a surface.* Every one of these documents is a different attempt to say it, and they fail in the same place — they stop at "route" and never reach "process".

| document | the coordinate it fixes | where it stops |
|---|---|---|
| `corpus/knowledge/runtime-health-surface-matrix.md` (held, round 10) | route × engine × revision | the table's key is the **engine**; seven columns, none of them a process (`runtime-health-surface-matrix.md:12`) |
| `corpus/knowledge/endpoint-health-probe-conventions.md` (held, round 35) | route → status meaning | the 503 is scoped to *a route on a server*, but a 503 from the daemon's `/health` means a third thing (not ready) — held entry never names a process |
| `corpus/knowledge/served-model-id-resolution.md` (held, round 35) | identity route vs liveness route | its own §"A related gap this round could not close" (`:37-46`) is exactly the process gap, and it is closed by S004's handler being **one** of two vLLM `/health` routes |
| `corpus/knowledge/engine-pin-watch.md` (held, round 42) | revision (a pin is a recheck trigger) | pins the *engine's docs line*, not the *process* that answers; a pin can be current while the route moved owner inside it |
| staged r7 (`…-r7.md`) | llama.cpp has **two** paths, one handler | first crack: path ≠ surface |
| staged r8 | a surface with **no** health route at all | path need not exist |
| staged r9 | what the lane's own probe records when the path is absent | receipt shape, not meaning |
| staged r10 | the requested path ≠ the shipped path | a route ships under another name |
| staged r11 | readiness logic that is **not a route** (`ready_checker.py`) | a module can be readiness without being a surface |
| staged r12 | the release's `/health` is the **daemon's**, not the server's | process ownership, first stated |
| staged r13 | **four** processes answer `/health` or `/ready` | the matrix needs a process column |
| staged r14 | "the matrix is not wrong; it is **unnameable**" | the gap is structural, not a missing sentence |
| staged r15 | the path has had **three owners** already | ownership moves *inside* a pin |
| staged r16 | the process column is **still owed** | three rounds of the same measurement |

**The pattern in one line:** *a route's meaning is a property of the process that owns it; a row keyed on the engine (or on the path) therefore cannot be read, and a version pin does not fix it because ownership can move inside the pin.*

Three consequences that the round-43 C3 entry now lands, and that the held entries do not yet say:

1. **Two vLLM `/health` routes exist.** The lane holds one (`corpus/SOURCES.md:16`, row S004, the inference server). The other is the weight-cache daemon's parent process, shipped in v0.31.0 (`#58552`) and moved to the preload CLI inside the same PR. Their 200s mean opposite things.
2. **The three named states are not three wire outcomes.** The pull request's body names `starting` / `ready` / `failed`; the merged code answers **two** statuses. `starting` and `failed` are both 503 with nothing in the body to tell them apart.
3. **The route is opt-in.** `--weight-cache-health-port` defaults to `None`; "Port for the parent /health endpoint; disabled by default." So "vLLM ships a `/health` endpoint" is true of the release note and false of a default install.

## 5. Falsifiable observations for the L1 / closure (each is a claim I can re-run, not a conclusion)

1. **The entry's own stated limit is closable today.** `runtime-health-surface-processes.md:57` says the diff is "not a read of `preload.py` at the merge commit or at tag v0.31.0". I read both: the merge commit `e7900156` and tag `v0.31.0` carry a **byte-identical** `preload.py` (sha256 `d2704e80…effa57d`, 12631 bytes). One `curl` per ref closes the limit and upgrades the entry from "the PR's patch" to "the shipped file". *Not applied here — report only.*
2. **The "three states" wording is a wire-level overstatement if read as three responses.** The PR body names `starting`/`ready`/`failed`; the shipped handler returns 200 or 503 with an empty body (`Response(status_code=200 if state.is_ready else 503)`), so `starting` and `failed` are indistinguishable on the wire. The landed entry already says this (`runtime-health-surface-processes.md:41`); the *staged* r12/r13 prose does not, and a future round that copies staged prose verbatim would overstate.
3. **The route is off by default.** `--weight-cache-health-port` defaults to `None` ("disabled by default"), so a default v0.31.0 install answers **no** daemon `/health` at all. Any phrasing of the form "vLLM now serves `/health` in two places" needs the opt-in qualifier. The landed entry has it (`:18` "opt-in", "disabled unless the port is set"); staged r12/r13 do not.
4. **The C3 counter's `refetch` leg does not exercise the merge.** The frozen spec (`tools/round43-health-audit.py:26-31`) checks the two frozen quotes in the live *release body* and *PR body/title*. It never reads `preload.py`, so the counter's `met=True` is compatible with the route having been removed from the shipped file. My §4 rows are the only evidence in this round that the shipped file still carries it. The `junk-c3-fabricated` shortcut control closes the *quote-fabrication* hole (round-42 R42C06), not this one.
5. **The counter's `rows` leg cannot see the held S004 duplication.** It finds the two new rows "by URL in the source cell" and checks ids absent at `--base`; it does not check that the *held* S004 row (`corpus/SOURCES.md:16`, same product, one `/health`) is distinguishable from the new PR row. A reader of `corpus/SOURCES.md` sees two rows for one product's two `/health` routes with **no process cell in either**. The `used-by` cell of S004 still names only `runtime-health-surface-matrix.md` — the new entry does not appear there. (Registered rows are immutable per KQ22, so the fix is a superseding row or a `used-by` append, not an edit — a decision for the L1, not a defect I am asserting.)
