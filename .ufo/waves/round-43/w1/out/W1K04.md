## 2. Coupling predictions, and which ones are real

**P1 — C1's `pins` leg depends on C2's and C3's counter blobs (hard, already discharged).**
`NEWSET` in `tools/round43-registry-audit.py` lists `tools/round43-hexrun-audit.py`
and `tools/round43-health-audit.py`. The `pins` leg requires each NEWSET counter to
have a SKILL.md row whose 4th cell names a `sha256 <prefix>` equal to the
counter's actual blob SHA-256 **at the tip** (`hashlib.sha256(blob(tip, path))`).
The three counters are byte-identical from the freeze to the tip:

```
$ git cat-file -p 895793e0:tools/round43-registry-audit.py | sha256sum   # 683c72c0de4b2448…
$ git cat-file -p origin/master:tools/round43-registry-audit.py | sha256sum  # same
$ git log --oneline 895793e0..origin/master -- tools/round43-*.py           # (empty)
```

So the three pins are stable **only while the counters are not edited after the
freeze**. Any post-freeze edit to a counter invalidates C1's `pins` row and
`mismatches` goes 0 → ≥1. This is the coupling the assignment anticipated; it is
discharged as long as the wave-1 L1 does not touch the frozen counters.

**P2 — C1's `flags` leg couples C1's SKILL.md rows to C2/C3 counter *sources*.**
Each registered counter's SKILL.md "Kind / entry command" cell may name only
`--flag`s the counter declares via `add_argument("--flag")`. The three counters
declare: registry-audit `--repo --tip --out`; hexrun-audit `--repo --tip --seed --out`;
health-audit `--repo --tip --base --out`. C1's landed rows name exactly those
(`SKILL.md:1400-1402`), so this coupling is currently satisfied — but any rename
of `--seed`/`--base` in a counter would silently break C1.

**P3 — C1's `spot` leg counts C3's lesson file (real, and C3 must not change the count).**
`spot` requires SCORECARD's `| calibration |` row to state `N (outside closures on
record)` where `N` = the number of `corpus/lessons/*verifier-spotcheck.md` blobs at
tip. C3 writes `corpus/lessons/round-43.md`, which does **not** match
`*verifier-spotcheck.md`, so the count is unchanged (29 at base and at the landed
tip). C1's landed SCORECARD states `29` — correct. If C3 had named its lesson
`round-43-verifier-spotcheck.md`, C1's `spot` leg would break. **Filter: C3's
lesson file name must not end in `verifier-spotcheck.md`.**

**P4 — C2's `live` leg reads C1's and C3's documents (real, and it is the C2↔C3 coupling).**
`live` runs `hexrun-census.py scan --repo --rev TIP` over every `.md`/`.tsv` blob
outside `.ufo/` and requires `unknown=0`, `ledger_bad=0`, and
`distinct`/`lane_oid`/`md5_blob` equal to the counter's own census of the same
documents. The two upstream commit oids that C3's entry cites
(`ff54ad893015a13e869a9c51b8f30f44dfbb8ef7`,
`087ebc203d88f0aa0491ba808e70e3ebd1537904`, both 40-hex) are *not* lane objects
and *not* blob MD5s — they are classifiable only by a `registry/hexrun-ledger.tsv`
row with an evidence file that contains the token. The landed ledger carries
exactly two such rows, pointing at C3's own copy:

```
$ git show origin/master:registry/hexrun-ledger.tsv | awk -F'\t' '$4 ~ /round-43\/c3\//'
76: ff54ad89…  upstream  vllm-project/vllm  .ufo/waves/round-43/c3/vllm-pr-58552-commits.json
77: 087ebc20…  upstream  vllm-project/vllm  .ufo/waves/round-43/c3/vllm-pr-58552-commits.json
```

**This is the one hard coupling between claims**: C2's ledger must carry rows for
the oids C3's entry cites, and C3's evidence copy must exist for C2's ledger to be
valid. Probed directly:

```
# C3's files present, its two ledger rows dropped  →  live=0, unknown=2
$ python3 tools/round43-hexrun-audit.py --repo <probe> --tip <tip> --seed 42
tool=1 contract=1 live=0 hygiene=1 capability=1 met=False seed=42
detail: live reference census {… 'distinct': 214 …}; tool exit 1
        '… upstream_ok=62 unverifiable=9 wrong_flagged=2 ledger_bad=0 unknown=2'
```
(`controls/probe-noledgerrows.c2.out`)

Conversely, dropping C3's whole file set leaves C2 green (`probe-c3dir.c2.out`:
`live=1 … met=True`, `distinct` 214 → 212, `upstream_ok` 64 → 62) — because with
the entry gone, the two oids are not in the document population any more. So the
coupling is one-directional in effect but strict in both directions of the pair:
**the ledger rows and the entry text must land together.**

**P5 — C1's SKILL.md row for C2 cites a path under C2's own directory (real, and a
latent `missing-path` defect).** `tools/gate-registry-check.py` flags a registry
row whose entry/self-test/write-scope cell names a repo-relative path that does
not exist at the evaluated revision (`missing-path:PATH`). C1's row for
`tools/round43-hexrun-audit.py` cites `.ufo/waves/round-43/c2/base-unresolved.tsv`
(`SKILL.md:1401`, cell 4). That file is committed at the **freeze** commit
(`895793e0`), so it is a frozen control artifact, not a C2 deliverable — but it
lives under C2's directory. Probe:

```

```
(`controls/probe-c2dir.c1.out`)

**Filter for the separability control: the C1-only control must keep
`.ufo/waves/round-43/c2/base-unresolved.tsv` (a frozen file) even though it sits
under C2's directory.** Dropping the whole directory breaks C1 by two legs
(`defect=1` and, transitively, `selftest=1` because the gate's own selftest
re-runs the lane arm against the same tree). This is exactly the round-42 KQ53
failure mode, reappearing one directory deeper.

**P6 — C3's `coverage` leg reads every base `.md` outside `.ufo/` (real, and it
constrains where C1/C2 may put the words).** `coverage` fails if any tracked
`.md` outside `.ufo/` **at the base commit** contains `weight cache daemon` or
`vllm preload`. Verified at base `6897ead`: 3437 `.md` blobs outside `.ufo/`, zero
hits. C1's and C2's documents at the tip are not in scope (the leg reads the
*base* tree), so this is satisfied — but it does mean C3's phrase pair must not
appear in any base-era document, and it will fail if the L1 backports a C3-like
sentence into an existing base document.

**P7 — C3's `census` leg reads C1's SOURCES.md correction line (real, and
currently clean).** `census` runs the fleet-root `scripts/sources-census.sh
validate --file <tip export>/corpus/SOURCES.md` and requires exit 0. That
validator parses the whole `## Registry` table, so C1's appended search-log
correction line and C3's two rows are both inside the validated file. The landed
file validates clean (`census=1` at the tip), so no defect.

**P8 — C3's `refetch` leg is host-dependent, not a claim coupling.** `refetch`
does a live `gh api` (fallback `curl`) of the two API URLs and requires the
frozen quotes plus every quote the Gate leg accepted. It reads no other claim's
file. It did pass at the tip (`refetch=1`); it is the only leg that would fail on
a network outage.

**P9 — C2's `capability` leg reads C1's SCORECARD head (real, and it constrains
the head mirror).** `capability` needs (a) a `hexrun-census` row in the *highest*
`canonical list as of round N` table and (b) `tools/capability-repertoire-audit.py`
to print `met True`, which requires that every capability name observed in *any*
capability-shaped table in SCORECARD.md appears in the canonical table, and that
every canonical row's evidence cell names a path that exists at the revision.

The landed file satisfies this: the head mirror at `SCORECARD.md:119` and the
§Round 43 canonical table at `SCORECARD.md:2308` both carry 9 names, and the
audit prints `missing 0 unsubstantiated 0 met True`.

**But the head mirror and the canonical table are two different tables**, and the
round-42 lesson recorded the exact failure (KQ/Mistakes row 5: "the head sentence
added for C1 matched the pattern both frozen counters use to find the highest
canonical capability table"). Probe evidence — the C2-only control, built by
reverting C1's head mirror to base but keeping C2's §Round 43 canonical list,
reads green; the variant that also strips C2's canonical row out of the
§Round 43 section reads `capability=0`. So:

**Filter: C1's head-mirror capability table and C2's §Round 43 canonical table must
carry the same name set, and the §Round 43 canonical marker must be the highest
`canonical list as of round N` heading in the file.** The landed file has
`canonical list as of round 43` at `SCORECARD.md:2304` with the table at 2308 —
above the round-42 marker at 2257 — so the resolver picks the right table.

## 3. Separability controls — exact file sets, and the run

Controls are built at the **freeze commit** `895793e0`, not the round base
`6897ead`: the counters are committed at the freeze, and a control built on the
round base scores the counters against a tree that does not contain them
(`pop=28`, and C1's `pins` leg cannot see `tools/round43-*.py` at all). Measured:
the same C1-only file set on the round base reads `pins=3` with
`detail: pins: tools/round43-registry-audit.py has no row or no blob at tip`
(`controls/sep-c3-only.registry-audit.out` shows `pop=28` for the base-built C3
control). The builder therefore starts from the freeze for C1 and C2, and from
the round base for C3 (whose counter needs the *base* tree for its `coverage`
leg, which is why `--base 6897ead` is passed explicitly).

Builder: `scripts/build_separability_r43.py` (this directory). It clones the lane
clone read-only into a throwaway sandbox under
`/fast/scratch/kama-r43/seats/W1K04`, asserts
`git rev-parse --show-toplevel` equals the sandbox, and commits only with the
fixture identity `r43-sep <r43-sep@fixture.invalid>` — never in the lane clone
or the parked worktree.

Per-claim file sets (preregistration `separability`, restated as applied):

* **C1 only** — `SKILL.md`, `README.md`, `corpus/SOURCES.md` (base + the one
  `- **2026-10-25 - correction to the round-42 entry above.**` line), and
  `SCORECARD.md` with C2's `hexrun-census` canonical row and the whole
  `## Round 43 — …` section removed. Keeps the frozen
  `.ufo/waves/round-43/c2/base-unresolved.tsv` (P5).
* **C2 only** — base `SKILL.md`, `README.md`, `corpus/SOURCES.md`,
  `corpus/README.md`; no C3 entry/lesson/copies/scratch; `SCORECARD.md` = landed
  file with **C1's head-mirror table reverted to base** but C2's §Round 43
  canonical list kept (P9).
* **C3 only** — base tree + the landed `corpus/knowledge/runtime-health-surface-processes.md`,
  `corpus/lessons/round-43.md`, `.ufo/waves/round-43/c3/`,
  `.ufo/waves/round-43/assimilation/`, the two SOURCES rows, and the
  `corpus/README.md` coverage-map + frontier-disposition blocks.

Result (`controls/`, each receipt ends with `exit=`):

| control | C1 counter | C2 counter | C3 counter |
|---|---|---|---|
| `sep-c1-only` | **met=True** `mismatches=0 pop=31 registered=31` | met=False `tool=0` | met=False `entry=0` |
| `sep-c2-only` | met=False `unreg=19 pins=19` | **met=True** `tool=1 contract=1 live=1 hygiene=1 capability=1` | met=False `entry=0` |

each other counter is `met=False` — the claims are separable, and the false

Two caveats on the C3-only row, both measured:

1. `sep-c3-only` was built on the **round base**, so `pop=28` and C1 reads
   `unreg=16` — the C1 leg cannot see the three frozen counters. That is a
   property of the base, not a coupling. The C1-only control on the freeze base
   reads `mismatches=0 met=True` (`controls/sep-c1-only-freeze.c1.out`).
2. `sep-c3-only` built from the **raw seat outputs** (W1C05 `entry.md` +
   W1C08 `rows.md` + W1C07 lesson/copies + W1C09 scratch) reads
   `entry=1 rows=0 … met=False` with
   `detail: row S481 (PR): anchor lacks copy sha256`
   (`controls/sep-seat-c3-only.c3.out`). The W1C08 rows as delivered carry
   `<PLACEHOLDER-RELEASE>` / `<PLACEHOLDER-PR>` in the anchor cell; the counter
   hashes the committed copy blob at the tip and needs the real digest. The
   landed `corpus/SOURCES.md` has them substituted
   (`sha256 20c282d5…` for S480, `sha256 976ea2ea…` for S481), which is why the
   landed tree reads `rows=1`. **The substitution is the L1's step and it is
   load-bearing: it is what makes C3's `rows` leg fire.** The seat file also
   notes the PR copy's bytes are volatile between fetches (W1C07's fetch hashes
   `aff67c2e…`, the committed copy `976ea2ea…`; only the committed bytes satisfy
   the anchor).

## 5. Filters to keep each claim verifiable without the others (round-42 KQ53)

1. **C3's lesson file must not be named `*verifier-spotcheck.md`** — C1's `spot`
   leg counts those and would break (P3).
2. **The two `registry/hexrun-ledger.tsv` rows for `ff54ad89…` and `087ebc20…`
   must land with C3's entry**, and C3's
   `.ufo/waves/round-43/c3/vllm-pr-58552-commits.json` must exist for them to
   be valid (P4). Do not delete or renumber those ledger rows.
3. **C1's SKILL.md row for `tools/round43-hexrun-audit.py` cites
   `.ufo/waves/round-43/c2/base-unresolved.tsv`.** That file is frozen at
   `895793e0`; the C1-only separability control must keep it, and no seat may
   delete it as "C2's directory" (P5).
4. **C1's head-mirror capability table and C2's §Round 43 canonical table must
   carry the same capability names, and §Round 43's `canonical list as of round
   43**` marker must be the highest in the file** (P9).
5. **The three `tools/round43-*.py` counters must not be edited after the
   freeze** — C1's `pins` leg hashes their blobs at the tip (P1), and C1's
   `flags` leg reads their `--flag` declarations (P2).
6. **C3's SOURCES rows must carry the substituted copy digests, not the
   `<PLACEHOLDER-…>` tokens** as delivered by W1C08 (§3 caveat 2).
7. **C3's phrase pair `weight cache daemon` / `vllm preload` must not appear in
   any base-era `.md`** — C3's `coverage` leg scans the base tree (P6).
8. **Build every separability control at the freeze commit**, not the round base
   (§3) — otherwise the counters are scored against a tree lacking themselves.
