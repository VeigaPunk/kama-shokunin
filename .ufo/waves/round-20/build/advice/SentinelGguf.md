## Findings

1. **MEDIUM — symlinked regular files can be read; receipt input is less protected.** `inspect_path` follows a symlink because `os.open` omits `O_NOFOLLOW`; `fstat` then accepts a symlink target that is regular (`gguf-identity.py:301-308`). It hashes the entire target before checking GGUF magic (`:308-315`). [INFERENCE] An automated candidate path that is a symlink to a readable credential or another user's regular file will therefore read/hash that target before returning bad-magic; a valid GGUF symlink can disclose its path/hash/identity metadata. The parser does correctly reject a directly opened non-regular target after `fstat`; `O_NONBLOCK` prevents the FIFO-open hang. The receipt helper instead opens without nonblocking/no-follow/regular-file checks and calls unbounded `json.load` (`gguf_receipt_reconcile.py:145-152`), so a FIFO receipt can hang and a symlink can redirect it. Access remains limited to the invoking UID; no elevation is involved. Current `/home/vgpnk/.ollama` was absent; no other user's home was inspected.
   **Smallest remediation:** open both inputs once with `O_RDONLY|O_CLOEXEC|O_NONBLOCK|O_NOFOLLOW`, then `fstat` and require regular files before reads. For automated scanning, constrain every path component beneath explicit model-store roots using descriptor-relative no-symlink/beneath resolution; reject foreign-owned/out-of-root inputs unless explicitly allowed. Apply a bounded byte read and strict JSON/duplicate-key/depth checks to receipts; emit only required receipt fields.

2. **MEDIUM — full-file hash and aggregate metadata remain unbounded.** Good existing controls: `DEFAULT_MAX_STR=16 MiB`, `DEFAULT_MAX_KV=1,000,000`, array length 1,000,000, total array items 4,000,000 and depth 32 (`gguf-identity.py:26-31,147-173`); the selftest artifact includes string/KV/array/depth-bound cases. Gaps: `stream_sha256` reads the entire file until EOF (`:291-298`), before parsing even the magic (`:308-315`); there is no max file/hash byte or wall-time limit. `--max-kv`/`--max-str` accept any nonnegative integer without a hard ceiling (`:498-505`). The parser retains all keys, all arrays and matching candidate values (`:242-258`), so per-string/per-array caps do not bound aggregate memory/output for a large file.
   [INFERENCE] A sparse multi-GiB regular file consumes unbounded hash time; a same-size non-GGUF file is fully read before rejection. A huge user-supplied `--max-str` plus large input can permit correspondingly large reads, and many distinct keys/arrays can accumulate in `seen`/`arrays`/`candidates`. Impact: prolonged local denial of service, memory growth, or massive output.
   **Smallest remediation:** add finite hard `max_file_bytes`, `max_hash_bytes`, cumulative metadata/key/output budgets and a wall-time cap; do not let CLI overrides exceed hard maxima. Reject oversize files from `fstat` before hashing. Enforce lengths before `read()`/loop/allocation and against remaining bytes. Keep the existing array depth/length/item limits. Hash only a complete bounded file; over-budget means named could-not-evaluate (exit 2), never a partial digest or identity match. Check magic before spending time hashing known non-GGUF inputs.

3. **MEDIUM — digest and decoded metadata can describe different file states.** `inspect_path` computes SHA-256, checks only `st_size`, rewinds, and then parses (`gguf-identity.py:308-315`); there is no post-parse metadata check. [INFERENCE] A concurrent writer able to modify a same-size model between the hash pass and parse can produce a digest from one byte state and declared metadata from another; the receipt helper can then report a hash match alongside metadata that the hash did not bind. Impact: false identity/metadata reconciliation.
   **Smallest remediation:** fail if descriptor identity/size/mtime_ns/ctime_ns changes across the complete operation and recheck after parsing; ideally hash and parse the same observed byte stream, preserving exact full-file digest semantics. Do not claim a stable identity if concurrent mutation is detected.

4. **LOW — output traversal is not a current file-write sink, but plain-text path output is injectable.** The declared parser only writes stdout; JSON mode uses `json.dumps` (`gguf-identity.py:547-556`), so no direct output-file traversal path is present. Non-JSON mode prints raw `path` (`:551`). [INFERENCE] A filename with newline/control characters can forge log lines; downstream output writers could turn input paths or metadata into traversal if they derive output filenames from them.
   **Smallest remediation:** escape/repr the path in text mode or make JSON the machine interface. Keep any exporter on fixed/generated filenames and verify descriptor-relative containment; never use `general.name`, receipt strings, or the input path as an output path.
