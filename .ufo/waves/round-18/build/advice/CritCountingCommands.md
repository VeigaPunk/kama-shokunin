Fixes are small and enumerated.

Scope: this seat attacked only the two counting-command specs as written in `build/spec.json` (items `C1Measure` at spec.json:22, `C2Survivors` at spec.json:37, plus the `C1Controls` contract at spec.json:17 they consume). Neither `c1/measure.py` nor `c2/survivors.py` exists yet — `.ufo/waves/round-18/c1/` and `c2/` are empty — so every statement is about the specified design, marked [INFERENCE] where it depends on how an implementer reads the spec. Axes named before attack: **operability** (can a non-author reproduce the measurement; do counts honestly classify nothing-observed) and **calibration** (do the counters themselves discriminate the claim they certify).

# Findings

## F1 — Neither counter anchors the "before" arm to committed bytes; the frozen copies are untracked working-tree files

Both specs take frozen subjects as bare `--frozen-tool PATH`-style arguments and verify nothing about them beyond hashing. `git ls-files .ufo/waves/round-18` returns **0 entries** — `frozen/` is untracked working-tree bytes, and `frozen/SHA256SUMS` is itself mutable (a tampered copy and a tampered manifest still agree). The lane's own precedent is strict: round-16 `measure.py` "Verifies the frozen "before" probe snapshot against … manifest.json (sha256, and bytes when declared) and byte-for-byte against the git blob recorded as source_commit:source_path" (`.ufo/waves/round-16/measure.py:5-10`); mismatch "exits 4 without running the harness — a wrong "before" red baseline is worse than none" (`measure.py:9-10`), implemented by `git cat-file blob` comparison at `measure.py:115-129`. The spec's "records sha256 of every input file" (spec.json, item C1Measure) records what ran but does not prove those bytes equal `e75cf680…:tools/kama-llamacpp-live.py`.

Impact: operability (non-author re-run gets whatever bytes sit in `frozen/`, not committed bytes) and calibration (a softened frozen subject raises both arms, hollowing the claim).
Smallest safe correction: each counter resolves every "frozen" input to `git -C LANE cat-file blob e75cf680b53484a61709ee1b2787d8dbc6419f74:<path>` (or accepts a path but refuses — exit 2 — unless its bytes equal that blob byte-for-byte), recording `{path, sha256, git_object: <commit>:<path>, bytes_match: true}` per input.

## F2 — measure.py's "before" arm runs the NEW control suite on the frozen subject; it is not a re-run of round-17's baseline

The spec runs "controls.py --json against frozen tool+gate and against current tool+gate" (spec.json, item C1Measure), i.e. a 1×2 sweep with this round's controls held constant. Round 17 instead committed paired evidence `controls-frozen.json` + `controls-current.json` (tracked under `.ufo/waves/round-17/runs/`), with frozen controls on the frozen subject reading `accepted_bad=6 inconclusive=1` (spotcheck: "frozen (tool `b8c5e8d4…`, gate `6b9576a1…`): `accepted_bad=6 inconclusive=1`", `corpus/lessons/round-17-verifier-spotcheck.md:113`). Consequences:

- The published "before" number (accepted_bad=6) is committed and re-verifiable; measure.py's "before" is a different quantity — the new suite's verdict on the old build — and if it diverges, nothing in the spec flags that the new controls mis-grade the old subject.
- The delta confounds two changes (control-set growth vs subject hardening). Forged-receipt controls against a gate that has no `--require-schema` flag classify per C1Controls' own escape hatch — "a gate that errors on an unknown flag counts as not rejecting on the targeted predicate" (spec.json, item C1Controls) — so `accepted_bad` on the frozen arm is inflated *by construction*. The claim "6 accepted-bad → 0" collapses into "N (new surface) → 0," indistinguishable from "6 → 0 on the retained checks."
- `uncontrolled_checks` is defined over "v3 check ids that no rejected-targeted control failed this run" (spec.json, item C1Controls); the frozen v2 subject emits no v3 ids, so the frozen-side list is computable only against a static id list, not the subject's own schema — an apples/oranges before→after.

This is the strongest counterexample to the "before" question asked in the assignment: yes, the before arm can be rigged — not by running the current *detector* on the frozen subject but by letting an unverified new-suite bug (or honest new-surface inflation) set the baseline. Only a 2×2 grid (frozen controls × frozen subject, current controls × current subject, the two off-diagonals informational) separates the effects, exactly the grid `mutants.py` already implements: "the 2x2 grid {frozen check.py, current check.py} x {pair, full}" (`.ufo/waves/round-18/frozen/round-17_c1_mutants.py:46-47`).
Smallest safe correction: run both control suites on both subjects; require frozen-controls×frozen-subject to reproduce `accepted_bad=6, inconclusive=1` (the committed round-17 numbers) before any delta is emitted, and report `accepted_bad` split into `new_surface` vs `retained_surface` controls.

## F3 — survivors.py's "before" arm never replays the named mutants on their original subject; the baseline is unfalsifiable

Family (a) applies the H edits "to the CURRENT check.py" only (spec.json, item C2Survivors). The round-17 survivors were measured on `54a2926` check.py: H1–H3 "0/3 applicable new mutants killed, 3/3 survived" on the round-17 subject (`.ufo/waves/round-17/falsify/advice/MutC1Preregistered.md:20-21`, "all six F8 variants"). If the C2CheckPyRobust work removes or rewrites the mutated lines, every H entry lands `site_missing` — "missing site -> `site_missing`, never skipped" — and "exit 0 iff every named survivor is killed … on the CURRENT side" then cannot be satisfied by a legitimate refactor; the perverse incentive is to keep the vulnerable lines so mutants stay applicable, or [INFERENCE] to fudge `site_missing` into `killed`. There is no `obsolete`/`refactored-out` disposition, though the lane already uses a third bucket — S045 admits "killed over applicable per mutant and detector" (cited in `build/advice/CritC2Cherry.md:24`) and round-17 excluded H4 as "not a fourth survivor or a killed mutant" (`MutC1Preregistered.md:21-22`).

The same spec line leaves the frozen arm with no expectation at all: mutants are "reported killed/survived for the FROZEN detector and the CURRENT detector," but exit 0 only constrains the current side. A registry entry that *weakens* the attacker's published edit (e.g. H2 mutating only one of the two `.strip()` call sites, still functionally weaker but a different mutant) would report `survived` on the frozen arm too — and since frozen-arm outcomes are unconstrained, exit 0 anyway. The committed evidence (H1–H3, H5–H7 survived; `MutC1Preregistered2.md`) gives an expected frozen-arm vector; the counter must *check* it: reproduce `survived` under the frozen detector on the frozen subject for every named mutant, else exit 2 (measurement fault — the registry does not encode the named attack). A before-arm that cannot fail is rigged by omission.
Smallest safe correction: registry dispositions `{killed, survived, site_missing, not_applicable, invalid_run}`; families (a), (b), (c), (e) run on BOTH subject versions (frozen check.py, current check.py) against BOTH detector versions; exit 0 requires current-side kills AND frozen-arm reproduction of each named mutant's published frozen-side outcome.

## F4 — Input digests are recorded, but the digest set misses real inputs; paths, not identities

Both specs promise "sha256 of every input file" — good — but the enumerated inputs omit:

- **controls.py's hidden inputs.** The harness copies `REGISTRY_SRC = LANE / 'registry' / 'endpoint-consumers.tsv'` into every sandbox (`.ufo/waves/round-18/frozen/tests_llamacpp-live_controls.py:83`, staged at `:386-390`) and defaults the probe to `DEFAULT_PROBE = LANE / 'tools' / 'kama-probe.sh'` (`:84`) — `LANE` resolved positionally as `Path(__file__).resolve().parents[2]` (`:82`), so a controls.py staged at the wrong depth silently binds a different registry/probe. Its own JSON records only `tool_sha256`/`gate_sha256` (`:649-650`) — no probe or registry digest. A registry or probe change alters outcomes with zero trace.
- **Environment.** Nothing records `sys.version`/`sys.executable`, `platform`, cwd, argv, timeouts. The cited base-fault class is Python-version-sensitive (the claimed fix cites `docs.python.org/3.14/`, spotcheck R6/line 246: "`documented_by` still cites the `/3/` docs path"), and crash-fault verdicts (deep nesting, 5,000-digit ints — `MalformedNonUtf8.md`, `TimeoutPath.md`) depend on interpreter limits.
- **Per-run evidence.** "the controls JSON digests" are recorded, not the JSONs; round 17 committed `controls-{frozen,current}.json` so the outside closure could `jq` the raw classifications (`round-17-verifier-spotcheck.md:113-126`). A digest of a discarded artifact is provenance of nothing.
- **Timing/nondeterminism.** Round 17's live measurement produced a load-dependent flake — "1/60 false failure under 32x CPU load observed **zero** 503s" (`round-17-verifier-spotcheck.md:18-19`). A counting command with no trial accounting can turn a flake into a count; per-control wall time, timeouts, and a flake/`invalid_run` classification are required.

Smallest safe correction (minimum provenance): see §Minimum provenance below; the diff vs spec is adding probe, registry, interpreter, per-run artifact bytes, and the counter's own source sha256.

## F5 — Detector-self mutants are judged by the mutated tool's own selftest: circular, and selftests are not external oracles

Family (b) grades fault-controls self-mutants with "the mutated tool's own `--selftest` plus its main-run numbers vs the unmutated tool's" (spec.json, item C2Survivors); family (c) likewise "detector = its `--selftest`". The round-17 attacker who found these mutants used a strictly external oracle: "(process exit, F0 detected, detected count, accepted count, F1…F8 detected booleans) compared with the pristine arm" plus "the entire JSON document after deleting only `seconds`" (`.ufo/waves/round-17/falsify/advice/MutFaultControlsSelf.md`, decision-tuple paragraph). And the published result shows the selftest oracle alone is weaker than external comparison on at least one arm: mutant (b) any-nonzero-detected was "**KILLED by frozen JSON decision comparison**" but "**SURVIVED** both current-only decisions and every selftest" (MutFaultControlsSelf.md, findings (b)). For append-only, the attacker documented that the *landed* selftest cannot kill these mutants at all — "the selftest never rewrites `opened`" (`.ufo/waves/round-17/falsify/advice/MutAppendOnlyGuard.md:54`) — so a `survivors.py` verdict of "killed" is only meaningful if it records *which* selftest fixtures exercise the mutated code path; a mutant killed by a fixture that never exercises the site is a vacuous kill. Circularity residual: the mutated tool defines the pass shape of its own selftest; an external arm (pristine-vs-mutant decision-tuple diff, the attacker's own criterion) is the cheap non-circular supplement already proven on this code.
Smallest safe correction: kill criterion = (external pristine-vs-mutant decision-tuple diff) OR (selftest outcome change) with the exercised fixture names recorded per mutant; never selftest alone; record the pristine baseline tuple in the output.

## F6 — Counting edges that silently launder bad states

- `killed iff accepted>0 or exit!=0` (spec.json C2Survivors) counts `exit==2` (detector's own fault) as a kill; must be `exit==1 && accepted>0`, with `exit==2`, timeouts, and unparseable JSON classified `invalid_run`, excluded from both numerator and denominator — the `site_missing`-never-skipped precedent (`frozen/round-17_c1_mutants.py:9-12`, "reported ``site_missing`` (n/a), never silently skipped and never counted as survived").
- Family (d) hard-codes "correct = 82" (spec.json C2Survivors). The 82 derives from "82 messages and 82 unique task IDs" in `refused-result-1.json` (`.ufo/waves/round-17/falsify/advice/ProvenanceRerun.md`) — committed bytes (verified via `git ls-files`: `round-17/build/refused-result-1.json` and `attempts.json` are tracked). The counter must record those inputs' sha256 + derivation, and must replicate the ledger precondition — the round-17 tool copies `bound_task_call_sha256` "from the most recent `wave_run` entry" (`frozen/round-17_dispatch-provenance.py:69-70`), so a scratch ledger without a wave_run entry changes the artifact's shape; record whether the reproduction appends to a real ledger copy or a fresh one, and compare the whole appended entry, not just `refused`.
- Family (e) verdict "traceback/exit not per-row" needs the bounded expectations: record wall clock and the probe timeout exercised (the F7 fault's own bound is "~40s wall on one row", `frozen/tests_probe-verdicts_fault-controls.py:36-37`), per-run exit + stdout sha256, not a boolean.
- measure.py `--self-mutants` kill criterion "selftest or measured numbers change" makes live-harness flake a *kill* — the opposite failure direction of F4. Kill = selftest/deterministic oracle change; live-number drift is `inconclusive`, never `killed`.
- Zero-loading control classification is correct in C1Controls (tool exit 2 + gate exit 3) — but measure.py must classify a `not-evaluated` row as its own bucket, not fold it into `misclassified`/`good_rejected`; the C1 contract gives it a distinct class, and the spec's exit predicate names only the four counts.

# Could the 'before' side be rigged? — direct answer

Yes, in both directions. (i) `measure.py` as specced rigs itself: the baseline is set by controls written in the same round that must show improvement, applied to unverified frozen bytes (F1/F2); an innocent new-surface inflation reads as claimed improvement, and a suite bug symmetric to both arms is invisible. (ii) `survivors.py` rigs the baseline by construction (F3): no frozen-subject replay of the named mutants, no expected frozen-arm vector, and an exit criterion that only inspects the current side — a weakened registry entry cannot be caught by the command that certifies it. (iii) Literal current-detector-on-frozen-subject is actually present in family (a)'s design (frozen AND current detectors on the current check.py) but the true before cell — frozen subject × frozen detector replaying the published survivors — is absent.

# Minimum provenance each must emit

Common (both commands, per run JSON):
1. `counter_sha256` (self), `argv`, `cwd`, `started/ended UTC`, `python_version`, `platform`.
2. Per input file: `{resolved_path, sha256, bytes, git_object: "<commit>:<path>", blob_match: bool}` — frozen inputs MUST blob-match `e75cf680…` or the run refuses (round-16 `measure.py:90-136` precedent).
3. Per executed child: `argv`, `exit`, `stdout_sha256`, `stderr_sha256`, wall seconds, timeout bound.
4. Every intermediate artifact the counts derive from, written alongside `--out` (atomic, refuse inside measured dirs — `mutants.py:59-64` precedent) and referenced by sha256.

measure.py additionally:
5. `probe_sha256`, `registry_sha256`, `controls_sha256`, model + fake-template digests; resolved `LANE` used by controls.
6. 2×2 cell grid; frozen-controls×frozen-subject must equal committed round-17 `controls-frozen.json` counts (`accepted_bad=6, inconclusive=1`) before any delta prints.
7. Per-control rows `{id, arm, tool_exit, gate_exit, receipt_sha256, failed_checks, targeted, classification}`; `uncontrolled_checks` per subject schema, split `retained` vs `new_surface`.
8. Dispositions: `inconclusive`, `invalid_run`, `not_evaluated` are first-class; timeouts never merge into any count.

survivors.py additionally:
9. Mutant registry (embedded or file) carrying, per mutant: `{name, subject, detector, source_advice_path, source_advice_sha256, exact OLD/NEW strings}` — a verifier diffs the registry edit against the attacker's published edit; advice docs are committed (`git ls-files` confirms `MutC1Preregistered{,2}.md`, `MutFaultControlsSelf.md`, `MutAppendOnlyGuard.md` tracked).
10. Pristine baseline tuple per detector before grading; external decision-tuple diff per arm.
11. Per mutant×arm: `{verdict: killed|survived|site_missing|not_applicable|invalid_run, deciding_fault, evidence (exit + artifact sha)}`; counts print the universe/denominator (per CritC2Cherry.md:30 — "Stated universe, in the lesson, before counting").
12. Expected frozen-arm outcomes hard-coded per named mutant; frozen-arm mismatch = exit 2, not silent pass.
13. Family (d): sha256 of `refused-result-1.json` + `attempts.json`, ledger precondition noted, expected=82 with its derivation cited.
14. Family (e): per-fault timeout bound, exit, stdout sha256, and the per-row verdict shape asserted.
