downloading rather than loading is a state the b11755-era corpus does not describe.

## 6. What the trigger does and does not license

- **It does falsify nothing.** The envelope body, its key order, its HTTP status, its content type,
  the gate's position in the pre-routing chain, the public `/health` exemption, the ready-path
  `/v1/models` body and the router-mode readiness asymmetry are all unchanged at b11887. The lane's
  `MODEL_LOADING` probe mapping and `corpus/knowledge/llamacpp-loading-lifecycle.md` remain accurate
  as statements about b11755 **and** about b11887.
- **It does mean the row is stale in a different way.** S038's own scope text is "identity of the
  official b11755 Linux x64 CPU binary kama ran; **not runtime behaviour**" and its `teaches` cell says
  "the release is mutable (Pre-release), so cite the digest, not the tag alone". A newer release does
  not invalidate S038; it only means the pin is behind. `b11887`'s own ubuntu-x64 asset digest
  (`sha256:5e5e9c72db765a7f2e15fe1a512d9fad777e8c85efea08d53ff6c44677d86d5c`, size 22493515) is the
  candidate for a *new* identity row if the lane ever re-pins; the b11755 asset digest still
  re-derives and is still the correct identity for the binary the lane actually ran.
- **Frontier step available.** Because the behaviour is unchanged, a pin bump from b11755 to b11887
  would be behaviour-neutral for the probe contract — a fact the lane can state cheaply and verify by
  re-running `tools/kama-llamacpp-live.py` against a b11887 binary (not done here; no binary was
  downloaded or run by this seat).

## 8. Confidence and remaining unknowns

- **High confidence** on the loading-envelope, `Loading model` text, and `/v1/models` ready-path
  findings: both an independent raw-fetch channel and a blobless-clone diff agree, and the raw bytes
  are sha256-pinned to the git blobs and (for b11755) to the lane's own round-16 snapshot.
- **Medium confidence** on one negative: the compare API's 300-file cap means my *file-list* claim
  rests solely on the clone diff (`git diff --stat b11755 b11887 -- tools/server` → 22 files). The
  clone is a full clone of the upstream default branch history, so this is not evidence-limited in
  practice, but the API alone could not have shown it.
- **Not tested (unknown):** runtime behaviour of a b11887 binary. No llama.cpp binary was built,
  downloaded or executed; every statement here is source-level. The "loading server answers 503"
  property is a code-path inference at both tags, exactly as the lane's corpus already states.
- **Not tested (unknown):** whether the b11887 *router* relays a loading child's 503 envelope
  unchanged. The proxy relay path is materially unchanged
  (`b11755 server-models.cpp:2857` / `b11887 server-models.cpp:2805`, both
  `msg.status = response.status;`), but I did not run a router and did not read the whole proxy
  body relay path line by line. The lane's existing `[INFERENCE from server-models.cpp]` marking on
  that point should stay an inference.
- **Out of scope for this seat** (flagged, not investigated): the `b11887` router's new
  download-worker child and the `POST /tts` / WS `/v1/realtime` surfaces are new behaviours that no
  held corpus row describes; whether they belong to a later round's scope is the lane's call.
