Distinguishing observation / proposed counter leg
- Archive mtime alone does not identify which bytes were executed. Comparing the member mtime to the tar header would flag this instance (all four marker records have `before.mtime_ns == header_mtime_ns`, then the copy changes it), but requires the archive and can be defeated by restoring mtime. It is weaker than observing writes.
- A direct inotify lab using `tarfile.extractall(..., filter="data")` and then `shutil.copyfile` measured one member `CLOSE_WRITE` for extraction and a second for overwrite; `j3-inotify-lab.out` records the events. Its mtime-restoration phase also shows why mtime alone is forgeable.
- Proposed counter-only change, held out of the frozen counter: watch the pre-created member directory before starting the replay; require one `CREATE`, no `MOVED_TO`, and one `CLOSE_WRITE` for the member. The candidate copy is `j3-counter-plus.py` and unified diff `j3-counter-plus.diff`. It was exercised at the decoy commit: `j3-c1-copydecoy-plus.out` exit 1, `bind=1 own=0 teardown=1 newrow=1 met=False`; each bind observed `create=1, moved_to=0, close_write=2`. The candidate is advisory, not applied to the frozen counter. A stricter production version should also reject later `MODIFY` events after the extraction close-write, to cover rewrites via an already-open file descriptor; this refinement was not validated in the candidate.
