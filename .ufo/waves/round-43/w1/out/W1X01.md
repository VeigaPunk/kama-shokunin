## 10. What the integrator must satisfy for `live=1` (arithmetic that binds)

At 73 covered tokens, `unknown=0` and `unverifiable + wrong_flagged ≤ 25` force **`upstream_ok ≥ 48 − m`**, where `m` is
the number of the seven 32-char runs that equal the MD5 of a committed blob (73 = upstream_ok + unverifiable +
wrong_flagged + m). At the freeze tip `m = 0` — the census reports all seven inside `unknown=73` — so the operative
bound is 48; the wider [41, 48] range W1X05 derived is only reachable if a committed blob happens to hash to one of
those seven runs. My implementation's row rules, verbatim:

* 7 TAB cells; a cited token with two rows → `ledger_bad`; fewer than 7 cells → `ledger_bad`; a class outside
  `upstream|unverifiable|wrong` → `ledger_bad`.
* `upstream`: the `evidence` cell must be a **regular-file blob at REV** (mode 100644/100755) whose **bytes contain the
  token and the non-empty `repo` cell text**, both byte-for-byte; a missing path, a tree, or an empty `repo` → `ledger_bad`.
* `unverifiable`: `note` (trailing whitespace stripped) ≥ 10 characters.
* `wrong`: `correct` must fully match the token regex (32–127, ≠ 64), differ from `token`, share its first 8 characters,
  and itself resolve as `lane_oid`, `md5_blob` or a valid `upstream` row.
* A 40-run that exists in the repo, or a 32-run equal to a committed blob's MD5, is classified before the ledger, so
  ledger rows for such tokens are inert (they are not double-counted, and a row for them is never `ledger_bad`).

Integration cautions, all consequences of the frozen contract, not defects:

* Any round-43 document added after this build (lesson, entry, SCORECARD/SKILL edits) that cites a new 32–127
  non-64 run must get a row, or `unknown` rises. After integrating, re-run
  `python3 tools/hexrun-census.py scan --repo <clone> --rev <final tip> --details` and diff the `unknown`/
  `ledger_bad` rows.
* Evidence files must not be `.md`/`.tsv` inside the tree: they would become documents and their contents would add
  counted tokens. The sibling evidence dirs already use `<oid>.json`, which is safe.
* `md5_blob` means "the MD5 of *a* committed blob", not "the file the prose names currently has". The one hit here is
  the *frozen* copy `.ufo/waves/round-16/frozen/kama-probe-before.sh` while `SCORECARD.md:25` presents it as
  `tools/kama-probe.sh`'s md5 (round-17 advice already flags that anchor as stale). Anyone reading `md5_blob` as
  "citation correct" would over-read the class.
* `--ledger FILE` reads the working-tree file when it exists and falls back to the blob at `REV`; that lets a proposed
  ledger be validated against a committed tip from a dirty worktree.
