## Attack / impact

A decoy substitution of `libllama-server-impl.so` in the extracted tree after the member digest check and before server exec is feasible in principle: the sealed fd protects only `llama-server` bytes. The `.so` is opened by the dynamic loader as a path-backed dependency, so a changed file can supply different implementation code at load time. The counter's observed `/proc/<pid>/exe` and `F_GET_SEALS` checks identify only the launcher image. `server_impl_sha256` is not a field described by the frozen C1 contract, and no current mapped-library digest check is described there. A later whole-tree digest would only detect this if it is recomputed after the substitution and binds the exact mapped inode/content; a digest measured earlier would not notice a post-check swap. This is the strongest counterexample to interpreting C1 as full-server-code identity, but not a failure of its explicitly bounded claim.

Impacted axes: operability (provenance/integrity of code actually serving requests); potentially depth (coverage of runtime code identity). No change to C1 verdict: preregistered limit explicitly excludes library identity.
