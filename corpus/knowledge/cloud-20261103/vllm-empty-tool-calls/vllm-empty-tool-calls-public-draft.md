# vLLM chat responses: absent and empty tool calls

**Status:** Unpublished public-audience candidate for independent review. This is prospective instructional material and paper decisions, not an incident report, deployment finding or test result.

## Evidence and scope

The upstream [issue #44104](https://github.com/vllm-project/vllm/issues/44104) describes an author's observed failure after a tool result: a final assistant answer with text and `finish_reason: "stop"` nevertheless included `tool_calls: []`; the reporter illustrated a client loop that checks only for non-`None`, enters a tool branch and indexes the empty list. The author also reported empty lists in streaming text deltas. These are reports, not observations made here. The author identified vLLM 0.20.2 checkout `bc150f5`, a then-main checkout `7bd738988`, and later gave a model-only serialization repro on another checkout. This does not establish the state of every release or deployment.

The upstream [PR #44105](https://github.com/vllm-project/vllm/pull/44105) is marked merged into main on 2026-06-23. The [merged commit `6c427dd40141870b9076c9a9f128eec3a7ce86bc`](https://github.com/vllm-project/vllm/commit/6c427dd40141870b9076c9a9f128eec3a7ce86bc) and [rendered change set](https://github.com/vllm-project/vllm/pull/44105/files) show wrapped serializers added to `ChatMessage` and `DeltaMessage`, and tests and integration-test expectations changed. The wrapper invokes the normal serializer, removes the `tool_calls` key if the serialized list is empty or the key is already absent, and otherwise returns the nonempty list without modifying it. The relevant response locations are non-stream `choices[].message` and streaming `choices[].delta`. This is a serialization change, not proof that the in-memory model list became absent or that every intermediary and client preserves the wire representation.

The diff displays tests of omitted default-empty fields in whole responses, including ordinary and exclude-unset dumps, SDK parsing, and preserving representative nonempty calls in both message and delta forms. Integration expectations were adjusted for absent calls, including a length-limited case and a tool-choice-none case. These test definitions are evidence of intended checks, not proof they passed in our environment or cover every serializer mode, caller, model, release or deployment. The PR author separately reported six passing tests in one named test file and a passing Ruff check. Those are author-reported results, not results independently reproduced here. No upstream software, requests, endpoints, service, model, integration suite or tool-call execution was run here.

The PR page and pinned commit diff were independently read as GitHub-rendered text through web retrieval, not a direct independently hash-verified checkout. Inconsistent GitHub Contents API results for merge and parent may reflect a query-ref cache error; those parent-query bodies are not relied upon. The commit page identifies the fix by its PR number and shows the additions. Source interpretation is limited to the displayed diff and test cases, not an assertion about a live binary. No upstream prose is reproduced here.

## Failure mechanism and response boundary

An empty list and an absent property are distinguishable in JSON. A client's `is not None` check can treat the former as present and then fail if it assumes an element exists. This is a client control-flow hazard in the issue author's reported situation; it is not a conclusion that every SDK or client behaves this way. The patch's intended response is to omit a serialized empty field while preserving nonempty calls. It does not instruct clients to discard calls, conflate all null or missing fields, or assume that content, finish reason, tool results and call payloads always correlate in one way. In a stream, a delta is one fragment, not necessarily a complete reconstructed tool call.

## Twelve adversarial hypothetical decisions

All examples are invented paper exercises. Where a decision assumes the shown wrapper, it is conditional on that code actually being applied to the relevant model and on the described serialized data. It is not a service test.

1. **Empty final message.** A non-stream assistant response has final text and the relevant serializer receives an empty list. **Decision:** the wrapper removes the key from that serialized message. Do not infer that the underlying list changed or that every gateway will emit identical bytes.
2. **Unset default.** The normal handler already omitted the key due to serialization options. **Decision:** the wrapper's absent-key fallback and safe removal leave it absent. The fallback handles an absent serialized key; it does not describe every optional property.
3. **Streaming text fragment.** A delta has text and an empty serialized tool-call list. **Decision:** that delta's key is removed. A single text delta cannot establish that no other delta in the stream carried a call.
4. **Nonempty message.** A non-stream message serializes one actual tool call. **Decision:** the wrapper leaves the list in the serialized dictionary. Its presence does not establish that executing the call is authorized, safe, or successful.
5. **Nonempty stream fragment.** A delta contains a tool-call fragment, with an index and partial function arguments. **Decision:** do not suppress it merely because it is incomplete; the nonempty list survives this wrapper. Reconstruct and validate the sequence according to the client's streaming contract; the patch does not validate accumulated arguments.
6. **Client indexes an empty list.** A proxy or older server supplies `tool_calls: []`, and a client enters a branch solely because the value is not `None`. **Decision:** guard the list's actual contents before indexing and diagnose response origin and version. This defensive client check does not prove the server patch is installed.
7. **Null versus omitted.** A hypothetical response contains explicit JSON null rather than an empty list. **Decision:** do not infer its treatment from the zero-length list branch; the shown typed list and serializer code do not establish a universal null contract. Inspect the actual protocol, validation path and client handling.
8. **Length stop without calls.** An integration test changes its expectation to a parsed SDK value of `None` in a length-limited, required-tool case. **Decision:** that assertion alone does not distinguish an omitted wire key from explicit null. The serializer diff supports omission only where the shown empty-list path applies. Neither a parsed `None` nor an omitted field means the request completed its intended tool operation; examine the finish reason and, when needed, the correlated wire payload.
9. **Text plus nonempty call.** A hypothetical message includes both text and a nonempty call list. **Decision:** the wrapper preserves the list; do not discard it because text exists or assume that all text implies a terminal answer. Validate the whole response and applicable client contract.
10. **SDK object versus wire.** The same client property is `None` after parsing an omitted key. **Decision:** the object alone may not prove whether a server, proxy or client normalization caused the representation. Preserve authorized raw response evidence and correlate it to the hop and parser version before assigning cause.
11. **Mixed deployment.** One replica has the change and another does not, or a proxy rewrites JSON. **Decision:** merge status alone cannot identify behavior of either response. Match failures to replica, build, endpoint and network path; a later upstream merge does not retroactively fix older binaries.
12. **Passing unit test claimed as end-to-end proof.** The PR author reports a local test result, and the diff contains SDK-model assertions. **Decision:** accept those as reported and defined evidence respectively, not proof of a production tool cycle, all streaming combinations, or this environment's test result. Separate model serialization, transport, parser, client branching and tool execution when diagnosing.

## Practical diagnostic approach and limits

For a future authorized investigation, first capture the exact endpoint, streaming mode, correlation identifier, response-producing hop, server build/commit and SDK/client version. Preserve the relevant response shape at the server boundary and after intermediaries, using minimum necessary data and redaction; avoid collecting prompts, tool arguments, credentials or personal data unless necessary and authorized. Record whether the field is absent, null, empty, or nonempty, alongside finish reason and relevant stream ordering. Do not equate lack of a log with proof of absence.

Then trace the specific serialized model and dump options, the proxy's handling and the client's parse and branch behavior. For streaming, inspect ordered fragments and reconstructed calls rather than a single delta. If a call is nonempty, separately validate identity, arguments, authorization and execution outcome. If an empty list reaches an indexing client, fix the assumption at the appropriate boundary only after establishing ownership and compatibility. Verify exact version and rollout before proposing any upgrade, rollback or shim; this document does not direct configuration changes or live testing.
