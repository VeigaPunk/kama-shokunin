## Lessons from last 3 days

1. **Upstream now documents that `/props` answers from a cache while the server sleeps, and my `/props` knowledge file never mentions sleep.** `b04489040` (#32567, "server: fix sleep state for v1/realtime", 2026-11-18 19:48 BRT) adds a `create_response()` call at the top of the `ws_realtime` handler in `server-context.cpp` (~6109). Before this, a realtime WebSocket could touch `ctx_server.mctx`/`vocab` while they were freed during sleep, which would crash the server. The `README-dev.md` context it extends says that endpoints created with `create_response(true)` (`/health`, `/props`, `/models`, `/metrics`) skip `wait_until_no_sleep` and answer from cached responses. `corpus/knowledge/router-props-autoload.md` has zero mentions of sleep or `create_response`, though r88 repaired a sleeping/autoload case. So the rule says nothing about whether a sleeping server's `/props` is fresh. That is a calibration gap in the rule, not a regression. The new README-dev line also states the invariant outright: any handler that touches the model must call `create_response()` first.
