## Summary

Related issue: #36960.

The existing `/health` endpoint remains a lightweight liveness check. It can return HTTP 200 while an alive EngineCore is unable to execute model work, for example when a GPU operation hangs or a busy engine stops making forward progress.

This PR adds `GET /ready`, which combines two complementary readiness signals:

- while the engine is busy, detect ranks that have stopped completing model steps;
- while a single-DP engine is idle, run a guarded dummy batch through the executor/GPU/model-forward path; and
- report an intentionally sleeping or paused engine as not ready without executing GPU work.

The same state is shared across API server processes and aggregated by the DP supervisor.

## Behavior

| Engine state | `/health` | `/ready` | Readiness behavior |
| --- | ---: | ---: | --- |
| Dead | 503 | 503 | Reuses the existing `EngineDeadError` path |
| Busy and completing model steps | 200 | 200 | Reads cached progress; adds no probe-triggered GPU work |
| Busy without model-step progress past the configured threshold | 200 | 503 | Reports the stalled EngineCore rank(s) internally |
| Single DP, idle, and dummy batch succeeds | 200 | 200 | Exercises the executor/GPU/model-forward path |
| Single DP, idle, and dummy batch fails or times out | 200 | 503 | Does not permanently mark EngineCore dead |
| Deployment-wide DP size greater than one and idle | 200 | 200 | Skips the idle dummy batch to avoid an uncoordinated collective |
| Sleeping or paused | 200 | 503 | Returns `{"status":"not_ready","reason":"sleeping"}` |
| Render-only server | 200 | 200 | No EngineCore is attached |

`/health` semantics are unchanged. `/ready` returns a diagnostic JSON body only for the expected sleeping state; other successful or failed responses remain status-only.

## Implementation

### Explicit EngineCore readiness state

EngineCore exposes an internal `EngineCoreReadyState` with three states:

- `IDLE`
- `BUSY`
- `SLEEPING`

The state and a monotonically increasing `ready_progress_seq` are published to all connected frontend processes through `EngineCoreOutputs`. State transitions are published immediately. Continuous progress is published at most once per second to limit additional IPC traffic.

The progress sequence advances after a model step completes with scheduled tokens. DP-coordinated dummy work also records progress. Each frontend tracks the latest state, sequence, and progress timestamp for every managed EngineCore rank.

The frontend marks an EngineCore busy before sending a request. This starts the stall timer even if the core hangs before processing the request.

### Busy-engine readiness

`AsyncLLM.check_health_gpu()` first performs the existing liveness check. It then returns not ready if any managed rank:

- reports `SLEEPING`; or
- remains `BUSY` without model-step progress for longer than `VLLM_READY_STALL_TIMEOUT_S`.

This path only reads state already broadcast to the frontend. It does not queue a readiness RPC on an EngineCore that may already be stalled and does not add GPU work while user traffic is running.

### Idle GPU probe

For deployment-wide DP size one, `/ready` runs an EngineCore utility call only when every managed core is `IDLE`. EngineCore checks the authoritative scheduler, batch-queue, DP-wave, and sleep state again immediately before executing the dummy batch.

The idle probe has the following safeguards:

- successful probes are cached in EngineCore for a configurable TTL;
- concurrent HTTP probes share one in-flight frontend task;
- timing out an HTTP wait does not cancel or duplicate the underlying utility task;
- the dummy batch is skipped if the engine becomes busy or sleeping before the utility call executes; and
- failed probes are not added to the success cache.

### Data-parallel and multi-frontend behavior

For deployment-wide DP size greater than one, readiness still checks progress for every managed rank, but does not initiate idle dummy work. This avoids entering a MoE/DP collective on only one rank.

Readiness state is broadcast to every API server connected to an EngineCore, so the result does not depend on one frontend's local `OutputProcessor`. Tracked rank mappings are synchronized after elastic DP scale-up and scale-down.

The DP supervisor's `/ready` and `/readyz` handlers concurrently query every child `/ready` endpoint and return 503 if any child is not ready or cannot be queried. A readiness failure does not change supervisor lifecycle state or trigger shutdown by itself.

## Configuration

| Environment variable | Default | Purpose |
| --- | ---: | --- |
| `VLLM_HEALTH_CHECK_GPU_TIMEOUT` | 20 seconds | Frontend wait timeout for an idle GPU probe |
| `VLLM_READY_STALL_TIMEOUT_S` | 60 seconds | Maximum time a busy EngineCore may make no model-step progress; `0` disables stall detection |
| `VLLM_READY_IDLE_PROBE_CACHE_TTL_S` | 10 seconds | Cache lifetime for a successful idle probe; `0` disables caching |

The variables are excluded from compilation-cache factors. `/ready` is excluded from Prometheus HTTP-handler instrumentation, matching `/health`.

This change does not modify Helm defaults, Kubernetes manifests, or README deployment guidance.

## Related work and non-duplication

This proposal consolidates two readiness mechanisms already being discussed:

- #46811 adds an idle dummy-batch GPU readiness probe;
- #43122 adds busy-period forward-progress detection;
- #45526 added decode-progress detection and is closed; and
- #36451 checks whether EngineCore can answer an IPC utility request.

Compared with #46811, this implementation also:

- returns not ready while sleeping instead of probing released allocations;
- avoids idle dummy execution for DP greater than one;
- checks EngineCore-global scheduler state rather than one API server's local request state;
- shares one in-flight probe and caches successful results;
- detects busy-engine stalls; and
- aggregates child readiness in the DP supervisor.

Compared with #43122, progress is based on completed model steps rather than only emitted decode tokens. It therefore covers prefill and decode, maintains state per EngineCore rank, proactively broadcasts progress, and also verifies idle GPU execution for single-DP deployments.

An IPC ping such as #36451 proves that the EngineCore process and utility path can respond, but it does not execute a model forward pass. Conversely, the idle dummy probe cannot safely cover idle DP collectives. The combined state machine makes those limitations explicit.

## Limitations

- An idle DP deployment with size greater than one does not run a GPU execution probe. Readiness can only observe state and subsequent busy progress there.
- A legitimate model step, remote-KV wait, or collective taking longer than the configured stall timeout may temporarily return 503.
- A timed-out GPU operation cannot be cancelled. Sharing the in-flight task prevents repeated probes from accumulating, but it cannot interrupt a stuck CUDA kernel.
- The endpoint currently identifies sleeping explicitly, while other failures remain status-only and require logs or metrics for diagnosis.

### Two-GPU serving tests

TP=2:

```bash
CUDA_VISIBLE_DEVICES=0,1 .venv/bin/python \
  -m vllm.entrypoints.cli.main serve /root/vllm-ready-qwen3-0.6b \
  --tensor-parallel-size 2 --dtype float16 --enforce-eager \
  --max-model-len 512 --gpu-memory-utilization 0.35 --port 18000
```

- Baseline `/health`, repeated `/ready`, post-generation `/ready`, and a 16-token generation all succeeded.
- The two TP workers occupied separate GPUs.
- During a 200-token request, TP1 received `SIGSTOP`. After seven seconds, `/health` returned 200 and `/ready` returned 503.
- After `SIGCONT`, readiness returned to 200 and a subsequent short generation succeeded.

PP=2:


- Baseline `/health`, `/ready`, and a 16-token generation succeeded.
- Pausing PP1 produced `/health=200` and `/ready=503`.

Internal DP=2 with multiple API servers:

### Single-GPU edge cases

Sleep/wake, TTL, and idle-probe timeout tests used:

```bash
CUDA_VISIBLE_DEVICES=0 \
VLLM_SERVER_DEV_MODE=1 \
VLLM_READY_STALL_TIMEOUT_S=5 \
VLLM_HEALTH_CHECK_GPU_TIMEOUT=5 \
VLLM_READY_IDLE_PROBE_CACHE_TTL_S=2 \
.venv/bin/python -m vllm.entrypoints.cli.main serve \
  /root/vllm-ready-qwen3-0.6b --enable-sleep-mode \
  --dtype float16 --enforce-eager --max-model-len 512 \
  --gpu-memory-utilization 0.35 --port 18000
```

- After `POST /sleep?level=1`, `/is_sleeping=true`, `/health=200`, and `/ready=503` with `{"status":"not_ready","reason":"sleeping"}`.
- Waking only the `weights` tag left the engine sleeping and `/ready=503`. Waking `kv_cache` then produced `/is_sleeping=false`, `/ready=200`, and a successful eight-token generation.
- Probes after TTL expiry took 23.31 ms and 28.83 ms. The cache hit immediately after the first probe took 2.15 ms; all three returned 200.
- Pausing an idle EngineCore kept `/health=200`; `/ready` returned 503 after 5.002 seconds. After `SIGCONT`, readiness returned to 200 and generation succeeded.
- After repeated `/ready` requests, `/metrics` contained zero lines for `handler="/ready"`; the `/v1/models` control request had 15 related HTTP handler metric lines.

Busy-stall detection was disabled with:

```bash
CUDA_VISIBLE_DEVICES=0 VLLM_READY_STALL_TIMEOUT_S=0 \
.venv/bin/python -m vllm.entrypoints.cli.main serve \
  /root/vllm-ready-qwen3-0.6b --dtype float16 --enforce-eager \
  --max-model-len 1024 --gpu-memory-utilization 0.35 --port 18000
```

During a 900-token request, the EngineCore was paused for seven seconds. `/health` and `/ready` both remained 200. The request completed in 17.20 seconds after resuming and final readiness was 200, directly confirming that zero disables stall detection.

With the default 60-second threshold and `--max-model-len 8192`, a 7,000-token request ran for 77.24 seconds. `/ready` returned 200 at 15, 30, 45, 60, and 75 seconds while the request was still active, and after completion. This verifies that a long request with continuing model-step progress is not marked stalled merely because its total duration exceeds the default threshold.
