## Route-form mismatch worth the mapper’s attention

The receipt explicitly records `observations.v1_single_id = "kama-b61c98ad5747"` and `observations.v1_single_id_equals_list_id = false`; the raw list response has `data[0].id = "kama-b61c98ad5747:latest"`. The live tool source (`tools/kama-ollama-live.py:342-370`) shows it requested `/v1/models/{name}` with the bare nonce name while checking the collection route against `qualified`. This is a **real observed difference between these two response forms**, but the requested knowledge documents do not assert that the collection and item routes must return identical IDs. Therefore it is not a documented-claim contradiction: classify such a mapper row as **untestable**, not `disagrees`, unless another frozen statement supplies that equivalence requirement.

## Explicit non-contradictions / limits

- The replay doc’s warning not to read replay exit 0 as `MODEL_OK` does **not** conflict with the lifecycle receipt’s `MODEL_OK`: the lifecycle tool has a distinct verdict contract and requires multiple independent checks. The captured replay exit is one recorded check, not the aggregate verdict by itself.
- The bare single-route ID versus suffixed list ID does not refute the replay policy against implicit `:latest` completion: the tool explicitly requests the qualified name for replay and separately requests the single route by the bare name.
- The tags digest differs from the fixture GGUF SHA, but the docs do not claim those values are byte-identical; the show response’s blob path includes the GGUF SHA while tags/ps share a distinct server-reported digest. Do not report this as a proven digest-contract failure.
