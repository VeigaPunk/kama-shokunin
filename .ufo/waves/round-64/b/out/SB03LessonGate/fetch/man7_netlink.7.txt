6: netlink(7) Miscellaneous Information Manual netlink(7)
7: NAME top
8: netlink - communication between kernel and user space (AF_NETLINK)
9: SYNOPSIS top
10: #include <asm/types.h>
11: #include <sys/socket.h>
12: #include <linux/netlink.h>
13: netlink_socket = socket(AF_NETLINK, socket_type, netlink_family);
14: DESCRIPTION top
15: Netlink is used to transfer information between the kernel and
16: user-space processes. It consists of a standard sockets-based
17: interface for user space processes and an internal kernel API for
18: kernel modules. The internal kernel interface is not documented
19: in this manual page. There is also an obsolete netlink interface
20: via netlink character devices; this interface is not documented
21: here, and is provided only for backward compatibility.
22: Netlink is a datagram-oriented service. Both SOCK_RAW and
23: SOCK_DGRAM are valid values for socket_type. However, the netlink
24: protocol does not distinguish between datagram and raw sockets.
25: netlink_family selects the kernel module or netlink group to
26: communicate with. The currently assigned netlink families are:
27: NETLINK_ROUTE
28: Receives routing and link updates and may be used to modify
29: the routing tables (both IPv4 and IPv6), IP addresses, link
30: parameters, neighbor setups, queueing disciplines, traffic
31: classes, and packet classifiers (see rtnetlink(7)).
32: NETLINK_W1 (Linux 2.6.13 to Linux 2.16.17)
33: Messages from 1-wire subsystem.
34: NETLINK_USERSOCK
35: Reserved for user-mode socket protocols.
36: NETLINK_FIREWALL (up to and including Linux 3.4)
37: Transport IPv4 packets from netfilter to user space. Used
38: by ip_queue kernel module. After a long period of being
39: declared obsolete (in favor of the more advanced
40: nfnetlink_queue feature), NETLINK_FIREWALL was removed in
41: Linux 3.5.
42: NETLINK_SOCK_DIAG (since Linux 3.3)
43: Query information about sockets of various protocol
44: families from the kernel (see sock_diag(7)).
45: NETLINK_INET_DIAG (since Linux 2.6.14)
46: An obsolete synonym for NETLINK_SOCK_DIAG.
47: NETLINK_NFLOG (up to and including Linux 3.16)
48: Netfilter/iptables ULOG.
49: NETLINK_XFRM
50: IPsec.
51: NETLINK_SELINUX (since Linux 2.6.4)
52: SELinux event notifications.
53: NETLINK_ISCSI (since Linux 2.6.15)
54: Open-iSCSI.
55: NETLINK_AUDIT (since Linux 2.6.6)
56: Auditing.
57: NETLINK_FIB_LOOKUP (since Linux 2.6.13)
58: Access to FIB lookup from user space.
59: NETLINK_CONNECTOR (since Linux 2.6.14)
60: Kernel connector. See
61: Documentation/driver-api/connector.rst (or
62: /Documentation/connector/connector.* in Linux 5.2 and
63: earlier) in the Linux kernel source tree for further
64: information.
65: NETLINK_NETFILTER (since Linux 2.6.14)
66: Netfilter subsystem.
67: NETLINK_SCSITRANSPORT (since Linux 2.6.19)
68: SCSI Transports.
69: NETLINK_RDMA (since Linux 3.0)
70: Infiniband RDMA.
71: NETLINK_IP6_FW (up to and including Linux 3.4)
72: Transport IPv6 packets from netfilter to user space. Used
73: by ip6_queue kernel module.
74: NETLINK_DNRTMSG
75: DECnet routing messages.
76: NETLINK_KOBJECT_UEVENT (since Linux 2.6.10)
77: Kernel messages to user space.
78: NETLINK_GENERIC (since Linux 2.6.15)
79: Generic netlink family for simplified netlink usage.
80: NETLINK_CRYPTO (since Linux 3.2)
81: Netlink interface to request information about ciphers
82: registered with the kernel crypto API as well as allow
83: configuration of the kernel crypto API.
84: Netlink messages consist of a byte stream with one or multiple
85: nlmsghdr headers and associated payload. The byte stream should
86: be accessed only with the standard NLMSG_* macros. See netlink(3)
87: for further information.
88: In multipart messages (multiple nlmsghdr headers with associated
89: payload in one byte stream) the first and all following headers
90: have the NLM_F_MULTI flag set, except for the last header which
91: has the type NLMSG_DONE.
92: After each nlmsghdr the payload follows.
93: struct nlmsghdr {
94: __u32 nlmsg_len; /* Size of message including header */
95: __u16 nlmsg_type; /* Type of message content */
96: __u16 nlmsg_flags; /* Additional flags */
97: __u32 nlmsg_seq; /* Sequence number */
98: __u32 nlmsg_pid; /* Sender port ID */
99: };
100: nlmsg_type can be one of the standard message types: NLMSG_NOOP
101: message is to be ignored, NLMSG_ERROR message signals an error and
102: the payload contains an nlmsgerr structure, NLMSG_DONE message
103: terminates a multipart message. Error messages get the original
104: request appended, unless the user requests to cap the error
105: message, and get extra error data if requested.
106: struct nlmsgerr {
107: int error; /* Negative errno or 0 for acknowledgements */
108: struct nlmsghdr msg; /* Message header that caused the error */
109: /*
110: * followed by the message contents
111: * unless NETLINK_CAP_ACK was set
112: * or the ACK indicates success (error == 0).
113: * For example Generic Netlink message with attributes.
114: * message size is aligned with NLMSG_ALIGN()
115: */
116: /*
117: * followed by TLVs defined in enum nlmsgerr_attrs
118: * if NETLINK_EXT_ACK was set
119: */
120: };
121: A netlink family usually specifies more message types, see the
122: appropriate manual pages for that, for example, rtnetlink(7) for
123: NETLINK_ROUTE.
124: Standard flag bits in nlmsg_flags
125: ───────────────────────────────────────────────────────────────────
126: NLM_F_REQUEST Must be set on all request messages.
127: NLM_F_MULTI The message is part of a multipart message
128: terminated by NLMSG_DONE.
129: NLM_F_ACK Request for an acknowledgement on success.
130: NLM_F_ECHO Echo this request.
131: Additional flag bits for GET requests
132: ───────────────────────────────────────────────────────────────────
133: NLM_F_ROOT Return the complete table instead of a
134: single entry.
135: NLM_F_MATCH Return all entries matching criteria
136: passed in message content. Not
137: implemented yet.
138: NLM_F_ATOMIC Return an atomic snapshot of the table.
139: NLM_F_DUMP Convenience macro; equivalent to
140: (NLM_F_ROOT|NLM_F_MATCH).
141: Note that NLM_F_ATOMIC requires the CAP_NET_ADMIN capability or an
142: effective UID of 0.
143: Additional flag bits for NEW requests
144: ───────────────────────────────────────────────────────────────────
145: NLM_F_REPLACE Replace existing matching object.
146: NLM_F_EXCL Don't replace if the object already
147: exists.
148: NLM_F_CREATE Create object if it doesn't already
149: exist.
150: NLM_F_APPEND Add to the end of the object list.
151: nlmsg_seq and nlmsg_pid are used to track messages. nlmsg_pid
152: shows the origin of the message. Note that there isn't a 1:1
153: relationship between nlmsg_pid and the PID of the process if the
154: message originated from a netlink socket. See the ADDRESS FORMATS
155: section for further information.
156: Both nlmsg_seq and nlmsg_pid are opaque to netlink core.
157: Netlink is not a reliable protocol. It tries its best to deliver
158: a message to its destination(s), but may drop messages when an
159: out-of-memory condition or other error occurs. For reliable
160: transfer the sender can request an acknowledgement from the
161: receiver by setting the NLM_F_ACK flag. An acknowledgement is an
162: NLMSG_ERROR packet with the error field set to 0. The application
163: must generate acknowledgements for received messages itself. The
164: kernel tries to send an NLMSG_ERROR message for every failed
165: packet. A user process should follow this convention too.
166: However, reliable transmissions from kernel to user are impossible
167: in any case. The kernel can't send a netlink message if the
168: socket buffer is full: the message will be dropped and the kernel
169: and the user-space process will no longer have the same view of
170: kernel state. It is up to the application to detect when this
171: happens (via the ENOBUFS error returned by recvmsg(2)) and
172: resynchronize.
173: Address formats
174: The sockaddr_nl structure describes a netlink client in user space
175: or in the kernel. A sockaddr_nl can be either unicast (only sent
176: to one peer) or sent to netlink multicast groups (nl_groups not
177: equal 0).
178: struct sockaddr_nl {
179: sa_family_t nl_family; /* AF_NETLINK */
180: unsigned short nl_pad; /* Zero */
181: pid_t nl_pid; /* Port ID */
182: __u32 nl_groups; /* Multicast groups mask */
183: };
184: nl_pid is the unicast address of netlink socket. It's always 0 if
185: the destination is in the kernel. For a user-space process,
186: nl_pid is usually the PID of the process owning the destination
187: socket. However, nl_pid identifies a netlink socket, not a
188: process. If a process owns several netlink sockets, then nl_pid
189: can be equal to the process ID only for at most one socket. There
190: are two ways to assign nl_pid to a netlink socket. If the
191: application sets nl_pid before calling bind(2), then it is up to
192: the application to make sure that nl_pid is unique. If the
193: application sets it to 0, the kernel takes care of assigning it.
194: The kernel assigns the process ID to the first netlink socket the
195: process opens and assigns a unique nl_pid to every netlink socket
196: that the process subsequently creates.
197: nl_groups is a bit mask with every bit representing a netlink
198: group number. Each netlink family has a set of 32 multicast
199: groups. When bind(2) is called on the socket, the nl_groups field
200: in the sockaddr_nl should be set to a bit mask of the groups which
201: it wishes to listen to. The default value for this field is zero
202: which means that no multicasts will be received. A socket may
203: multicast messages to any of the multicast groups by setting
204: nl_groups to a bit mask of the groups it wishes to send to when it
205: calls sendmsg(2) or does a connect(2). Only processes with an
206: effective UID of 0 or the CAP_NET_ADMIN capability may send or
207: listen to a netlink multicast group. Since Linux 2.6.13, messages
208: can't be broadcast to multiple groups. Any replies to a message
209: received for a multicast group should be sent back to the sending
210: PID and the multicast group. Some Linux kernel subsystems may
211: additionally allow other users to send and/or receive messages.
212: As at Linux 3.0, the NETLINK_KOBJECT_UEVENT, NETLINK_GENERIC,
213: NETLINK_ROUTE, and NETLINK_SELINUX groups allow other users to
214: receive messages. No groups allow other users to send messages.
215: Socket options
216: To set or get a netlink socket option, call getsockopt(2) to read
217: or setsockopt(2) to write the option with the option level
218: argument set to SOL_NETLINK. Unless otherwise noted, optval is a
219: pointer to an int.
220: NETLINK_PKTINFO (since Linux 2.6.14)
221: Enable nl_pktinfo control messages for received packets to
222: get the extended destination group number.
223: NETLINK_ADD_MEMBERSHIP
224: NETLINK_DROP_MEMBERSHIP (since Linux 2.6.14)
225: Join/leave a group specified by optval.
226: NETLINK_LIST_MEMBERSHIPS (since Linux 4.2)
227: Retrieve all groups a socket is a member of. optval is a
228: pointer to __u32 and optlen is the size of the array. The
229: array is filled with the full membership set of the socket,
230: and the required array size is returned in optlen.
231: NETLINK_BROADCAST_ERROR (since Linux 2.6.30)
232: When not set, netlink_broadcast() only reports ESRCH errors
233: and silently ignore ENOBUFS errors.
234: NETLINK_NO_ENOBUFS (since Linux 2.6.30)
235: This flag can be used by unicast and broadcast listeners to
236: avoid receiving ENOBUFS errors.
237: NETLINK_LISTEN_ALL_NSID (since Linux 4.2)
238: When set, this socket will receive netlink notifications
239: from all network namespaces that have an nsid assigned into
240: the network namespace where the socket has been opened.
241: The nsid is sent to user space via an ancillary data.
242: NETLINK_CAP_ACK (since Linux 4.3)
243: The kernel may fail to allocate the necessary room for the
244: acknowledgement message back to user space. This option
245: trims off the payload of the original netlink message. The
246: netlink message header is still included, so the user can
247: guess from the sequence number which message triggered the
248: acknowledgement.
249: VERSIONS top
250: The socket interface to netlink first appeared Linux 2.2.
251: Linux 2.0 supported a more primitive device-based netlink
252: interface (which is still available as a compatibility option).
253: This obsolete interface is not described here.
254: NOTES top
255: It is often better to use netlink via libnetlink or libnl than via
256: the low-level kernel interface.

259: EXAMPLES top
260: The following example creates a NETLINK_ROUTE netlink socket which
261: will listen to the RTMGRP_LINK (network interface
262: create/delete/up/down events) and RTMGRP_IPV4_IFADDR (IPv4
263: addresses add/delete events) multicast groups.
264: struct sockaddr_nl sa;
265: memset(&sa, 0, sizeof(sa));
266: sa.nl_family = AF_NETLINK;
267: sa.nl_groups = RTMGRP_LINK | RTMGRP_IPV4_IFADDR;
268: fd = socket(AF_NETLINK, SOCK_RAW, NETLINK_ROUTE);
269: bind(fd, (struct sockaddr *) &sa, sizeof(sa));
270: The next example demonstrates how to send a netlink message to the
271: kernel (pid 0). Note that the application must take care of
272: message sequence numbers in order to reliably track
273: acknowledgements.
274: struct nlmsghdr *nh; /* The nlmsghdr with payload to send */
275: struct sockaddr_nl sa;
276: struct iovec iov = { nh, nh->nlmsg_len };
277: struct msghdr msg;
278: msg = { &sa, sizeof(sa), &iov, 1, NULL, 0, 0 };
279: memset(&sa, 0, sizeof(sa));
280: sa.nl_family = AF_NETLINK;
281: nh->nlmsg_pid = 0;
282: nh->nlmsg_seq = ++sequence_number;
283: /* Request an ack from kernel by setting NLM_F_ACK */
284: nh->nlmsg_flags |= NLM_F_ACK;
285: sendmsg(fd, &msg, 0);
286: And the last example is about reading netlink message.
287: int size;
288: /* 8192 to avoid message truncation on platforms with
289: page size > 4096 */
290: struct nlmsghdr buf[8192/sizeof(struct nlmsghdr)];
291: struct iovec iov = { buf, sizeof(buf) };
292: struct sockaddr_nl sa;
293: struct msghdr msg;
294: struct nlmsghdr *nh;
295: msg = { &sa, sizeof(sa), &iov, 1, NULL, 0, 0 };
296: size = recvmsg(fd, &msg, 0);
297: for (nh = (struct nlmsghdr *) buf; NLMSG_OK (nh, size);
298: nh = NLMSG_NEXT (nh, size)) {
299: /* The end of multipart message */
300: if (nh->nlmsg_type == NLMSG_DONE)
301: return;
302: if (nh->nlmsg_type == NLMSG_ERROR)
303: /* Do some error handling */
304: ...
305: /* Continue with parsing payload */
306: ...
307: }
