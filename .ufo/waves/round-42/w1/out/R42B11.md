Token rule (`classify.py`): `(?<![0-9A-Za-z])[0-9a-fA-F]{8,63}(?![0-9A-Za-z])` — alphanumeric boundaries, not hex boundaries, because words ending in `a`–`f` glue onto a following hex run (`LOG.md:1312` literally reads `landed971d4549`; a hex-boundary regex yields the artefact `ded971d4549`). Numeric literals, digit-only runs, SHA-1 object ids, md5s, docker container ids, `/proc/net/tcp` address hex and SCORECARD statement keys are separated from digest citations; the residue the mechanical rules cannot settle is hand-labelled in `classify.py:OVERRIDE`, each entry quoting the document context that justifies it (auditable line by line).

Resolution: a token matches a digest when it is a prefix of it, or (form `p…s`) both a prefix and a suffix, or (form `…s`) a suffix; candidate sets are the blobs reachable from the tip, all blob objects in the store, the 10 ledger rows, and the full 64-hex tokens cited in the same documents.

## 6. Prefix ambiguity: the 8-character collision class

`5585f602` (8 hex, `corpus/lessons/round-41-verifier-spotcheck.md:48`) matches **two** digests: the correct `5585f6027df2…` (blob `.ufo/waves/round-38/assimilation/exec-tag-inventory/ls-remote-tags.txt`) and the ledger's known-wrong `5585f602f71c…`. ## 7. Adjacent finding: one 65-hex run the ledger cannot see

```
$ python3 (LONG = (?<![0-9A-Za-z])[0-9a-fA-F]{64,}(?![0-9A-Za-z])) over the same 131 documents
len=64 occurrences=254 distinct=96
len=65 occurrences=1   distinct=1
  corpus/lessons/round-38.md:51 3ad0df68e8423a3b1b99d4e3b8d8c6271f7a4f4c96d3a5ad4e0a85a991ce234ff  (65 chars)
```

`tools/digest-ledger.py:52` is `TOKEN = re.compile(r"(?<![0-9a-f])[0-9a-f]{64}(?![0-9a-f])")`. A 65-character run fails the `(?![0-9a-f])` lookahead at every 64-character window, so the token is never collected: the scan's `tokens=96` equals exactly the count of 64-character runs (96), and `unknown=0 wrong_unflagged=0` is reported while the known-wrong R36-D2C package digest still sits in the corpus. An 8–63 sweep does not see it either (it is longer than 63); I reached it only by chasing its 16-hex prefix. The ledger's stated purpose — "so that no cited digest is unexplained" (`tools/digest-ledger.py:2-4`) — is not met for this citation.

## 9. Limits

- Prefix-only resolution cannot detect a wrong digest that shares the cited prefix; that is inherent (§6), and it is why the suffix forms matter.
- The 24 residue labels and ~60 other non-digest labels are hand-assigned in `classify.py:OVERRIDE` with quoted context; a reviewer can re-derive any of them. Tokens classified `git-object` by context alone (`04411e88`, `63a0d4df`, `873c5d77`, `8e953f68`, …) are commits of the fleet repo or of the never-pushed parked-worktree lineage and are absent from this clone (`git cat-file -t` → `Not a valid object name`); if a reviewer prefers to call them digests, the nothing-count grows by at most a handful and no wrong citation appears.
- `.ufo/` documents are excluded per assignment; `.ufo/` blobs are in the blob set (as in `digest-ledger.py`), which is why 91 of 93 blob resolutions point at `.ufo/` evidence.
- Re-hashes on this host: `llama-server`, `libllama-server-impl.so`, the staged `SOURCES.append.md`, and two tip blobs (`count-c1.py`, `server-schema.cpp`). The release archive and the `.so` ledger rows were confirmed by `sha256sum`; the other external rows were not re-fetched.
