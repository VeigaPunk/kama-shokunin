## Findings

### F1 — BLOCKER: the INI config file is a port and slot-count setter that no P-row and no decision names

`common/arg.cpp:729` — quote: *"config file applies first, so env variables and CLI arguments override it"* (`common/arg.cpp:773`). Route: `common_params_apply_system_config` reads `/etc/llama.cpp/config.ini` and `${XDG_CONFIG_HOME:-~/.config}/llama.cpp/config.ini` (`common/arg.cpp:741-742`, `common/common.cpp:1001-1014`), then `common/arg.cpp:764` `global.apply_to_params(params);` and `common/arg.cpp:767` `it->second.apply_to_params(params);`, which land in `common/preset.cpp:153` `opt.handler_int(params, std::stoi(val));` — **the same `handler_int` lambdas `--port` and `--parallel` use** (`common/arg.cpp:3320-3322`, `common/arg.cpp:2517-2521`). Real setter, not a comment: #3–#6. With only a config file and no argv/env the server listened on **18099** instead of 9931 and ran **7 slots** instead of 4; `parallel = 0` was refused by the server-branch lambda; `--port`/`LLAMA_ARG_PORT` still overrode the file.

Why the landed section misses it: (a) the population is mechanical (`POP_RE` over `common/` and `tools/server/`) and the route's own lines carry no `port =` / `n_parallel =` token and no `LLAMA_ARG_PORT` literal — **no line of the config-file route is a population row** (checked exhaustively: `common/preset.cpp` has 0 `POP_RE` matches; none of `common/arg.cpp:725-784` matches); (b) the value reaches `params.port` / `params.n_parallel` **through the handler**, so it passes through P09/P03's assignment lines but is not *one of* them; (c) `SKILL.md` never mentions `config.ini` (`grep -i config` over the whole landed file finds no mention) and the section's Limit paragraph admits only "a struct copy, a reference, a preset file read into argv" as ungraded setters.

**R16 is wrong for such a start.** It says a llama-server "listens on TCP port 9931 (P26, copied by P33) *only when none of these sets it*" and then lists `--port`/`LLAMA_ARG_PORT`, the preset options, `AIP_MODE=PREDICTION`, and the router-child case. A config file is a fifth setter not in that list; a start whose only port-setting input is `~/.config/llama.cpp/config.ini` with `port = 18099` is one for which **none** of R16's named conditions holds and the port is still not 9931. **R17 is wrong the same way**: it says the count resolves to 4 "only while the count is still auto at startup … and none of these set: `-np N`, `--parallel N` or `LLAMA_ARG_N_PARALLEL` (P03) … a preset option (P12, P20, P22)". A config file with `parallel = 7` yields 7 and none of R17's named conditions holds; #5 shows the config route is the *server-branch* `--parallel` lambda — the very one R17's P03 names.

This is the class the round-92 closure routed as R2/R3 (KQ149 "every setter named or excluded"), re-declared in the round-93 freeze text ("every setter … in its argument parser, **presets**, entry point and child-spawn code; env-driven modes"): a config-file INI is a preset and `common/preset.cpp` is inside the population root `common/`, but its lines carry no `port =` token, so the mechanical population misses the route. Under the frozen K2 rule ("an R16/R17 decision that states a port or slot count for a start that another setter changes") and the C2 disclosed limit ("a setter that writes the value through another name … is graded only through the rows its value passes … a non-author finding of such a setter that changes what R16/R17 state is K2"), this fires: the config file writes through a handler and changes what R16 and R17 state.

### F2 — BLOCKER candidate (scope caveat): the `llama-cli` embedded server listens on a random port and runs 1 slot

`tools/cli/cli-server.h:44` — quote: *"`server_params.port = port;`"* (after `tools/cli/cli-server.h:43` *"`common_params server_params = params; // copy`"* and `tools/cli/cli-server.h:35` *"`port = common_http_get_free_port();`"*). This is the whole-struct-copy case the landed Limit paragraph admits is "graded only through the rows its value passes (P09, P03)" — but it passes through **neither**: `llama-cli` never parses `--port`/`LLAMA_ARG_PORT` (#9) and overwrites the copied `port` member with a free port. Measured (#8): `llama-cli -m stories260K.gguf` spawns an in-process llama-server logging `n_slots = 1, kv_unified = 'false'` and `listening on http://127.0.0.1:38725` (a different random port each run); the standalone binary and unified `llama serve` (#7) both give `n_slots = 4`, `kv_unified = 'true'`, `listening on 9931`. R16 says a llama-server "listens on TCP port 9931 … only when none of these sets it" — for the embedded server **none** of R16's named conditions holds (no `--port`, no `LLAMA_ARG_PORT`, no preset option, no `AIP_MODE`, not a router child), yet it listens on a random free port. R17 says a llama-server "outside the router role resolves its slot count to 4 with a unified KV cache (P48) only while the count is still auto at startup" — the embedded server's count is **1** and never becomes 4, because `llama-cli` parses with `LLAMA_EXAMPLE_CLI`, so P01's `-1` default (`common/arg.cpp:1372`, `LLAMA_EXAMPLE_SERVER` only) never runs and the shared `common/common.h:464` default of 1 stands.

Scope caveat, stated plainly: `tools/cli/` is outside the counter's population roots (`common/`, `tools/server/`), so no P-row could exist for it even if the pattern matched, and the landed section's stated population is those two roots only. The R16/R17 decisions are nevertheless written about "a llama-server at b12177" without qualifying the entry point, and the `llama-cli` embedded server *is* one — it runs the same `server_http_context` / `server_context` code (`llama_server()`, `tools/server/server.cpp:805`). I flag it as a BLOCKER **candidate** with the caveat attached, not as an uncontested verdict; a reviewer may scope C2 to the `llama-server` binary alone.

### F3 — NOTE: a router child inherits `AIP_HTTP_PORT` and dies, contradicting the "router child gets the free port" clause

`tools/server/server-http.cpp:125` — quote: *"`port = gcp.port;`"* (under `if (gcp.enabled)`, `tools/server/server-http.cpp:118`; the AIP port is read at `tools/server/server-http.cpp:96`). The router copies its own environment to the child (`tools/server/server-models.cpp:1234` `child_env = base_env; // copy`), so `AIP_MODE`/`AIP_HTTP_PORT` reach the child, whose own `server_http_context::init` applies the AIP override *after* it was told `--port <free>` (`tools/server/server-models.cpp:316`). Measured (#12): the child is told `--port 56265`, logs `overriding server port 56265 with AIP_HTTP_PORT 18101`, then `couldn't bind HTTP server socket, … port: 18101` and exits 1. R16 names both `AIP_MODE=PREDICTION` (P36) and the router-child free port (P41) as overriding conditions; the *interaction* is unstated. NOT a K2 fire — R16 does name both conditions and the child never listens on 9931 either way — but R16's phrasing ("a router spawning it as a model child (P41: the free port the router chose)") reads as if the child always ends up on the free port. One clause would fix it.

### F4 — NOTE: `--port 0` with more than one TCP host is a startup error, not a free port

`tools/server/server-http.cpp:135-137` — quote: *"`--port 0 is not supported with multiple TCP addresses`"*. Measured (#10): exit 1. R16's clause "`0` binds any free port" (P37) carries no multi-address exception. Not a K2 fire: the process refuses to start, so no start is misstated about its port.

### F5 — NOTE: `LLAMA_SERVER_ROUTER_PORT` in the environment flips role detection

`tools/server/server-common.cpp:2235-2237` — quote: *"return `std::getenv(SERVER_ENV_ROUTER_PORT) != nullptr`;"* (`tools/server/server-common.h:765` *"its presence makes the process a child"*). Measured (#11): with `LLAMA_SERVER_ROUTER_PORT=9999` and no model the server does **not** enter router mode — it tries to load a model and exits 1 — because `server_role_detect` consults the env first (`tools/server/server.cpp:104-105`) before the "a server given no model is a router" rule (`tools/server/server.cpp:108-111`). R17's "The router role keeps auto" is therefore conditional on an env var it does not mention. Not a K2 fire on the port/count values themselves; noted because it is exactly the "env-driven modes" the KQ149 falsifier names.

- `common/preset.cpp` has **0** `POP_RE` matches and none of `common/arg.cpp:725-784` matches — the mechanism behind F1, not a separate finding.
