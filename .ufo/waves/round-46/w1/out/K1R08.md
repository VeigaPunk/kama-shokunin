## 4. Attack on the counter for these rows

The counter proves exactly one thing about a `holds` row: the seat-chosen pin range and the seat-chosen release range compare equal after whitespace stripping (`tools/round46-release-recheck-audit.py:213-268`, `def check_row`). It never reads the usage cell, the statement, the note (for `holds`), any caller, or any other file. Three executed demonstrations, plus the negative results that bound them.

### A1 — a `holds` window may drop the guard the statement is about (accepted)

`fragment-attack-narrow.tsv` narrows each row to the single error line (the only line the cited-line rule forces: strong cite `5476` / `3657`), leaving the FIM checks (`5466-5474`) and the `!can_split` + `n_ubatch` condition (`3652-3656`) unproven:

So S122 can be scored `holds` while nothing in the ledger covers "its guard", and S123 while nothing covers "cannot be split across batches / longer than `n_ubatch`". The verdict word and the evidence window can disagree without limit.

### A2 — the note of a `holds` row is never checked (false provenance accepted)

`fragment-attack-note.tsv` keeps the honest ranges but replaces each note with a claim the release contradicts (`"the /infill route and the handler were removed at b11906"`, `"a new precondition now rejects embedding prompts with 400"`):

`note` is length-checked only for `holds-reworded`/`drifted`/`removed` (`:270`), so the ledger's only prose field is free text for `holds`. A reader who trusts the note instead of the bytes is misled, and no counter rule fires.

### A3 — cross-file evidence is structurally invisible

Both rows' observable (`501`, `500`, and the route that reaches the handler) is decided in `server-common.cpp` and `server.cpp`, and the S123 status additionally in `server_res_generator::error`. The ledger schema has no column for the dependency file, and `check_row` opens exactly one path (the row's `path`). At b11906 those dependencies moved (`server-common.cpp:107→109`, `server.cpp:296→191`, `server_res_generator::error` at pin `4872-4875` → b11906 `5178-5181`), so a `holds` verdict cannot be re-derived from the ledger alone — it can only be re-derived by the reader re-reading two more files, which is what this seat did. This is a frozen-contract gap, not a row defect.

### A4 — a changed enclosing condition is invisible (the example in the brief)

The real b11906 delta inserts an early return two guards above the S123 anchor (`3881`, `3897`). The 7-line window `3950-3956` cannot express it, and `holds` passes regardless.
