# K05PredicateIdentity — C1/C2 predicate-to-code comparison

Axes: operability (C1), calibration (C2).

## C1 — meaningful wording/code mismatches

- **The mutant assertion is misstated in the frozen context and C1 target.** Both say the mutant's miss makes an “expected-detected check fail.” In `tools/round56-env-leg-battery.py:50`, the mutant is explicitly run with `expected="missed"`; `round56-env-leg-test.py:29` returns 0 when its result matches that expectation; the battery then includes that success in `all(results)` (`battery.py:51`). Receipt `.ufo/waves/round-56/measured/m-drop-ldaudit.out` says `ld_audit=missed`, `exit=0`. The kill is demonstrated by the positive-control assertion (`round56-counter`, expected detected) passing while the mutation changes detection to missed; the mutant leg itself passes its expected-missed assertion. **Smallest correction:** say “the mutant changes the result to missed; this confirms the detector's dependency on `LD_AUDIT`” rather than claiming the mutant's expected-detected assertion fails. If the intended kill contract is specifically a failing mutant test, change the harness expectation and re-freeze only before scoring; do not reinterpret the current receipt.
- **“reports the variable name as a problem” is narrower than the driver's predicate.** `env_leg` appends `env: server environment carries LD_AUDIT` to `probs` (counter lines 430–441); the driver declares detected if *any* problem contains the substring `LD_AUDIT` (`env-leg-test.py:25–26`). It does not independently assert a direct `env_leg` return value or exact problem entry. The tested current result is the intended entry, as recorded in `build-c1.out`, but a different problem string containing that substring would also satisfy the driver. **Smallest correction:** describe the measured driver criterion as substring-in-`probs`, or assert the exact expected problem entry.
- **The supplied live child is `sleep`, not a serving/model child.** `env-leg-test.py:20–25` launches `sleep 5` and passes its PID to `env_leg`. This accurately isolates the counter's `/proc/<pid>/environ` name classifier and supports the frozen limits clause (which disclaims successful audit-DSO injection), but the phrase “at a live child process” must not be generalized to live endpoint/server health. **Smallest correction:** explicitly call it a live `sleep` child environment probe; keep the claim limited to this classifier behavior.
- **Receipt `exit=0` is the test driver's status, not the classifier's status.** The driver maps outcome-versus-`--expect` to return code (`:29`); battery receipts append that return code (`battery.py:25`). Thus `missed exit=0` means “missed was expected,” not “counter succeeded at detecting” or a counter exit status. The wording in target is ambiguous but the values are faithful. **Smallest correction:** label it `probe_exit=0` or state “probe exits zero on expected outcome.”

## C2 — meaningful wording/code mismatches

- **“exactly equals” has ordinary Python equality semantics, not serialized-byte equality.** The checker retrieves committed blobs with `git show`, parses prereg JSON and battery Python AST, applies `ast.literal_eval` to a top-level `ROSTER` assignment, then compares Python dictionaries (`prereg-check.py:39–61`). Key order/whitespace are irrelevant; only the parsed name/designation/expected values matter. This is appropriate for semantic roster fidelity, but “exact” should be read as semantic mapping equality, not byte identity.
- **The checker’s stated `met` predicate does not validate roster schema/types.** It compares mappings, then counts `designation` values from prereg roster entries (`:61–65`). It has no explicit validation that each entry has exactly the three documented fields, that all values have expected types/allowed strings, or that `ROSTER` is a literal top-level `ast.Assign` (annotated assignment/non-literal assignment is not accepted). Consequently the frozen predicate is narrower than broad “roster parsed from its AST exactly equals preregistered name/designation/expected-outcome roster” wording could imply: it is literal mapping equality plus one kill and two accepted control designations. **Smallest correction:** describe the actual literal assignment and count checks, or extend schema checks only in a future pre-data freeze.
- **Designation mutations within the accepted control class are not killed.** `controls` counts both `control` and `positive-control` (`:63–64`). If the one-field mutation changes the positive-control designation to `control` in both committed battery and prereg data, equality and counts still yield `met=True`. The kill rule's generic “one-field designation mutation” therefore overstates what is tested; single-sided changes are caught by equality, while mutations that preserve the class counts can pass. **Smallest correction:** define the mutation domain (e.g. mutate one side only / change a kill to a non-kill), or require exact per-name designations against a frozen expected roster independent of the prereg roster.
- **C2 receipt has no explicit exit field.** `prereg-check.py:66–71` prints `met` but does not print or write the return code into `--out`; `measured/build-c2.out` ends at `met=True`, unlike C1 receipts which append `exit=...`. The target says exit 0, but that status cannot be independently read from this receipt alone; it requires the invocation result. `controls/base-c2.out` does include a manually appended `exit=1`, unlike checker-generated output. **Smallest correction:** have the invoking receipt wrapper append the actual checker return code, clearly distinguished from checker stdout.
