# R41B08 — Security review: tools/pin-watch.py

**Verdict: 3 actionable findings — option injection via the `repo` cell (Medium; High where the default remote is a non-HTTPS transport), ReDoS via `tag_regex` (Medium), path traversal via `engine` cells in `--tags-dir` mode (Medium) — plus two Low robustness/credential notes; all reproduced with PoCs under `/tmp`; minimal fixes given. The tool is otherwise clean: no `shell=True`, no string-built commands, `GIT_TERMINAL_PROMPT=0`, a 120 s subprocess timeout, header/duplicate-engine enforcement, and the peeled-`^{}`-line skip are all present and correct.**

## 1. Option injection via a `repo` cell starting with `-` — Medium (High under non-HTTPS origin)

`read_tags` builds `subprocess.run(["git", "ls-remote", "--tags", pin["repo"]], …)` (`tools/pin-watch.py:100-102`). The repo cell is a shell-escaped argv element (no shell), but **git parses it as an option** when it starts with `-`. `load_pins` never validates it.

- Exploit path: a row with `repo=--upload-pack=/path/to/exec` makes `git ls-remote` connect to the **configured default remote** (`origin`) using the attacker-supplied upload-pack executable. Empirically, with `origin` pointing at a local bare repo, the marker script **ran** (`?=128`, `fatal: Could not read from remote repository…`, marker file written). With a `ssh://` origin the executable would run on the remote host; with the lane's own `https://` origin `--upload-pack` is ignored by smart HTTP — so exploitability depends on the transport of the default remote of the invoking checkout. The lane's own documented invocation (`recheck: run python3 tools/pin-watch.py check --pins registry/engine-pins.tsv`, `corpus/knowledge/engine-pin-watch.md:5`) runs from a checkout whose origin is the lane remote.
- Even with benign options the attacker flips results: `--get-url` (rc=0, prints URL) and `--refs` (rc=0, empty stdout) turn every row from `error` into `missing`; `--unknown-flag` → rc=129. A single cell cannot smuggle both an option and a repository (no argv splitting), so arbitrary-option effects are the reachable surface.
- Severity: **Medium** (High where the invoking checkout's `origin` is a local-path/SSH transport; otherwise result-tampering). The shipped pins file itself is benign (`registry/engine-pins.tsv:1-4`; `sglang`/`vllm`/`llama.cpp`).
- Minimal fix: in `load_pins` (`pin-watch.py:63`), after cells are stripped:

  ```python
  if repo.startswith("-"):
      raise PinsError(f"{path}:{n}: repo must not start with '-'")
  ```

  (optionally also require a scheme from `{http,https,ssh,git,file}://`). This closes the injection with one guard; no `--` separator can help because a single cell cannot carry both.

## 2. ReDoS via `tag_regex` — Medium

`load_pins` only enforces `rx.groups >= 1` (`pin-watch.py:71-72`); `release_tags` runs `rx.fullmatch(name)` over every ref line (`:85`) and builds `tuple(int(g) …)` (`:87`). Python `re` backtracks.

- PoC: pattern `(a+)+$`, one tag name `'a'*n + 'b'`. Measured: n=20 → 0.026 s, n=24 → 0.41 s, n=26 → 1.64 s, n=28 → **6.53 s** — 4× per +2 chars, exponential; n=40 ≈ 28 min for a *single* line. A crafted pins file (or an upstream fork whose tag names are long) pins the CPU; `release_tags` has no timeout (only the git subprocess does, 120 s).
- Baseline: the lane's own `v(\d+)\.(\d+)\.(\d+)` over 2000 tag lines runs in 0.0018 s. No behavior change for the shipped patterns.
- Severity: **Medium** (DoS; no code execution; requires untrusted TSV or untrusted upstream tag names).
- Minimal fix (two cheap guards in `load_pins`):
  - reject quantified groups: `if re.search(r"\)[+*?{]", regex): raise PinsError(...)` — bans the classic catastrophic shape `(…)+`/`(…)*`/`(…)?`/`(…){m,n}` while keeping every shipped pattern (`v(\d+)\.(\d+)\.(\d+)`, `b(\d+)`) and ordinary classes/quantifiers like `[0-9]+`; and
  - cap tag-name length in `release_tags` (e.g. skip names longer than 64 chars) so even a pathological allowed pattern has a bounded per-line cost.

## 3. Path traversal via `engine` names in `--tags-dir` — Medium

`read_tags` reads `os.path.join(tags_dir, f"{pin['engine']}.txt")` (`pin-watch.py:93`) with no validation of `engine`.

- Exploit paths (all reproduced): `engine=../escape` reads `<tags_dir>/../escape.txt`; `engine=<abs-path>/victim` reads an absolute path (`os.path.join` discards the tags-dir prefix for absolute second args); a symlink `tags/ln.txt -> ../escape.txt` dereferences to any readable target regardless of its name. The read is content-driven: with `pin=v9.9.9` and the out-of-tree file holding `refs/tags/v9.9.9`, the tool prints `status=current` from the foreign file (exit 0); a missing target yields `status=error` — an existence/readability oracle.
- Impact: the tool will parse and reflect the *content* of any `*.txt` file (or symlinked file) the process can read, and its result lines leak which paths exist/are readable. It cannot write or execute; it is an information-disclosure / tampering primitive keyed off the TSV.
- Severity: **Medium** (file read oracle; constrained to `.txt`/symlinked targets and to lines shaped like `ls-remote` refs).
- Minimal fix: validate the engine cell in `load_pins` before it is ever used in a path:

  ```python
  if not re.fullmatch(r"[A-Za-z0-9][A-Za-z0-9_.-]*", engine):
      raise PinsError(f"{path}:{n}: invalid engine name {engine!r}")
  ```

  (rejects `/`, `\`, `.`/`..`, and leading-dot names) and, defensively, confirm the real path stays under the real `tags_dir`.

## 4. Credential prompts (residual) — Low

`GIT_TERMINAL_PROMPT=0` is set (`pin-watch.py:102`) — git's own terminal prompts are disabled, good. However the child inherits the caller's stdin (`subprocess.run` passes no `stdin=DEVNULL`; shim probe: `stdin-readable=yes`) and the full environment (`GIT_ASKPASS`/`SSH_ASKPASS` inherited), so when the caller has a TTY, `ssh` can still prompt for host-key confirmation or passwords on `ssh://` repos, and inherited askpass helpers can run. The 120 s timeout caps a hang at 120 s per pin.

- Minimal fix: `stdin=subprocess.DEVNULL` in the `subprocess.run` call; optionally `GIT_SSH_COMMAND="ssh -oBatchMode=yes"` in the env for ssh URLs. Keep `GIT_TERMINAL_PROMPT=0`.

## 5. Untrusted TSV robustness (uncaught crash) — Low

`load_pins` checks compile and ≥1 group but never that groups capture digits, while `release_tags` does `int(g)` (contract: "capturing groups are digit runs"). A row `v(\d+)\.(\d+)-([a-z]+)` with tag `v1.2-hotfix` passes load and then **crashes**: uncaught `ValueError: invalid literal for int() with base 10: 'hotfix'` at `pin-watch.py:87`, traceback, exit 1. Also: a NUL in the engine cell raises `ValueError` in `open()` (not caught by `except OSError`), and there are no row-count/size limits on pins or tag lists.

- Minimal fix: enforce the digit-group contract at load (groups must be `\d+`-only) or guard `int(g)` (`try/except ValueError` → treat as non-release); extend the `open` except to `(OSError, ValueError)`.

## Minimal-fix summary (all in `tools/pin-watch.py`)

1. `load_pins`: reject `repo.startswith("-")` (and optionally require a URL scheme); reject engine cell not matching `[A-Za-z0-9][A-Za-z0-9_.-]*`; reject regex matching `r"\)[+*?{]"`; enforce digit-only capture groups or guard `int(g)`.
2. `read_tags`: add `stdin=subprocess.DEVNULL`; catch `(OSError, ValueError)` on the file read.
3. `release_tags`: cap tag-name length (e.g. 64 chars).
