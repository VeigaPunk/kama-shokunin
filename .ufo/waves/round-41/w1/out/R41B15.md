### 1.3 Is the row decorative? No — it is substantive, accurate, and used
- **Anchor accuracy (verified).** `git-scm-docs-git-ls-remote.html` SHA-256 `296a3d5cbc4dc359cd94da807e7c09db368186edb4c199cca625139d7c9b5f74` matches S475's stated digest. §OUTPUT text "When showing an annotated tag, unless --refs is given, two such lines are shown … followed by ^{} … shows the name of the object the tag points at" is present at HTML lines 1919–1922; the §OPTIONS `--refs` anchor is at line 1826 (lines 1827–1828: "Do not show peeled tags …"); page header contains "last updated in 2.48.0". All row anchors re-derive.
- **The peeled-line rule is the tool's documented semantics.** `tools/pin-watch.py:82` implements exactly this: `if not sep or not ref.startswith("refs/tags/") or ref.endswith("^{}"): continue`. The knowledge entry `engine-pin-watch.md:22-28` grounds that rule explicitly in S475 ("The git manual's §OUTPUT says … (S475)"). Without S475 the rule would be an unsourced design choice; with it, it is grounded domain knowledge.
- **The rule is operative in the live data.** SGLang's pinned v0.5.22 is annotated: `ls-remote-sglang.txt` contains both `35ce3132…336c9 refs/tags/v0.5.22` and its peeled sibling `baa9befa… refs/tags/v0.5.22^{}`. vLLM's v0.32.0 is lightweight: `grep -c -E 'refs/tags/v0\.32\.0\^\{\}$' ls-remote-vllm.txt` = 0. Skipping `^{}` lines is not decorative; it is the documented correct handling of the annotated-tag double line.

**Conclusion:** S475 is a genuine, accurate, load-bearing-for-documentation mined row; the "decorative" hypothesis fails at substance level. The defect is calibration-level: the claim's wording ("rests on S475") overstates what the frozen counter measures. A counter that passed with S475 deleted or fake would also report `met=True`; C2's measured met does not certify S475's content. This is a fixable wording/enforcement gap, not a false claim.
