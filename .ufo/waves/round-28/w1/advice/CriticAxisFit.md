# C1 axis/design critique — round 28, wave 1

Read-only advisory review; no admission, score, or met/missed judgment. No wave-1 data results were used. Evidence below is the frozen design, existing skill, pinned source, and pre-freeze controls.

## Axes and direct answer

- **Depth:** the proposed *SKILL.md field → request value → observed rejection/transformation → explanation* surface fits the canonical example of verifiable technical detail. It is not automatically coverage merely because fields are enumerated.
- **Coverage:** neither 18 rows nor the absence of a file named `server-schema.cpp` at base measures the fraction of serving surfaces governed. Existing request-error knowledge does not establish that these particular field outcomes were already held, either.
- **Calibration:** vulnerable to treating a count as proof of explanatory depth, source-derived knowledge, shortcut resistance, or saturation.
- **Operability:** vulnerable to incorrect meaning cells and extrapolation beyond the pinned native-endpoint fixture.
- **Freshness:** this is a pinned-build observation, not current registered-consumer health or verification of other builds.
- **Adjacency:** request acceptance/storage belongs to serving behavior; model quality, request safety, and dispatch mechanisms remain outside this table's authority.

The surface can support **depth**, but the counter alone cannot establish that result. AXES calls quality a learning trend containing depth, freshness, and operability; the campaign's more specific “sourceless fixture” exception still needs examination. A live-observed table is not disqualified simply because producing it is cheap. Conversely, a citation token and a live-true number do not establish useful explanatory prose.

Evidence: E1, E2, E3, E4.

## Findings

### F1 — HIGH: counted rows can retain no technical explanation, or actively false advice

**Counterexample and evidence.** The strongest eligible guessing control actually counted **14/38**, without reading schema semantics or independently running a server before scoring. Its meaning cells say only “Blind guess from field name and public README only”; its SOURCES rows explicitly attest declaration identity, not outcome provenance. All 38 passed the static table/declaration/source checks. These are observed counter results, not a new test (E5, E6).

The frozen code checks meaning only by `len(cells[4].split()) >= 6` (E7). For the already-counted `top_p` row, keep the registry and the other five cells unchanged but replace the meaning with:

> The server preserves the original requested value unchanged.

The observed request was `1.5`, the stored value `1.0`, and the omitted default approximately `0.95` (E5). Thus this prose contradicts the observed transformation. **[INFERENCE, static counterexample; not executed]** The same row would remain counted: no live comparison reads its meaning. The same substitution is possible independently on every otherwise-counted row. Substring matching of the field/value/outcome cells also does not establish that surrounding prose or field identification is faithful (E7).

**Impacted axes:** depth, calibration; operability if readers act on the explanation.

**Smallest safe correction:** use the already-preregistered independent per-row prose review, with explicit findings against the request, observed value/default, and relevant implementation. Correct misleading text before integration. Report the count as verified outcomes, not as a semantic-prose gate. Do not edit the frozen counter or add a retrospective counting condition. If false guidance remains, that is axis-harm evidence for the canonical Rust judge, not a tradeoff offset by extra rows.

**Limit:** 14 is below 18. This is not evidence that an eligible blind fixture met C1's complete target.

### F2 — MEDIUM: the “runs the server, therefore does the work” boundary needs an artifact-level interpretation

**Counterexample and evidence.** The blind writer did not run a separate server; the counter ran it and confirmed 14 guesses. The label-keyed control likewise used the counter as its only live oracle. Its report identifies receipt-guided rewriting as claimed work, while HOLDS says a writer copying live outcomes does the claimed work (E5, E8, E9). Consequently, “the counter ran the server” cannot distinguish the control from the author: both receive that service.

The boundary is defensible for a claim about **new, accurately documented measured outcomes**. Independent manual probing is not intrinsically more expert than using the counter's genuine observations. It is not defensible as evidence that the author read behavioral source, learned a causal mechanism, or supplied correct meaning merely because an outcome is true. A source-free-in-the-behavioral-sense fixture can earn individual rows; a literally citation-free fixture cannot, because declaration citations are required (E7).

**Impacted axes:** calibration, depth.

**Smallest safe correction:** distinguish three authorities in the landed explanation: the declaration citation establishes field identity; the pinned live receipt establishes this request's observed outcome; separately cited implementation establishes any causal explanation. Preserve guessed/copied provenance honestly. Describe the shortcut boundary as artifact correctness and useful new detail, not an exemption based on who invoked the same oracle. Do not claim the controls prove that all source-blind outcomes are uncountable. A future target-reaching shortcut is a frozen-claim issue for the canonical judge, not something to dismiss solely because the counter observed truth.

### F3 — MEDIUM: “18 of roughly 70” is the wrong sizing denominator; the shortcut margin is narrower than it looks

**Evidence.** The control's lexical manifest contains 71 declaration-looking names, including the commented-out `t_max_prompt_ms` and seven speculative fields inside `#if 0` (E5, E10). It also includes nonnumeric and nested fields. These are not 71 comparable opportunities for a numeric bound/transformation row.

A static tally of explicit active scalar limit declarations gives **13 hard-limited + 7 soft-limited fields after the two pilot exclusions = 20**. Source locations are E10: lines 40–75, 89–184, and 335–336. This is a straightforward candidate set, **not a proven upper bound**: custom handlers and type transformations can supply other candidates, and live/default checks can eliminate candidates. Target 18 therefore asks for most of this obvious scalar-limit set, not merely an easy quarter of all lexical declarations.

The best observed eligible blind control is 14. The label-keyed receipt independently contains three additional eligible fields absent from those 14: `dry_allowed_length`, `dry_penalty_last_n`, and `repeat_last_n` (E5, E8). **[INFERENCE; no composite run]** Their distinct-field union contains 17 already-confirmed outcomes. This is not a new precommitted blind control, and choosing it after seeing receipts uses observation; it does show why “four rows above the strongest control” is not broad shortcut separation.

**Impacted axes:** calibration; depth if row cardinality is presented as saturation or mechanism diversity.

**Smallest safe correction:** keep target **18** and its kill rule unchanged. Explain the lexical-versus-active-versus-counter-eligible sets, report the actual control margin, and describe a finite field-outcome table rather than completeness or saturation. The local evidence does not establish dishonest sizing or an eligible target-reaching blind fixture. It also does not justify “the domain is nearly exhausted” from this count. One bounded request per field does not prove the entire response function or every boundary.

### F4 — HIGH, fixable at integration: the frozen counter counts explicitly excluded pilot fields

**Counterexample and evidence.** The label-keyed control renamed the two pilot rows. Both `n_cache_reuse` and `xtc_threshold` were counted; the report and HOLDS disclose that `excluded_fields` is not enforced by code (E8, E9). The canonical assignment and preregistration explicitly exclude them (E4). Thus a raw receipt is not sufficient evidence that all its rows are eligible for this round.

**[INFERENCE; not executed]** Adding those two pilot hits to the 17-distinct-field union described above would supply 19 individually observed hits. That is **not legitimate C1 data**, because it violates the explicit exclusions; it illustrates the importance of the external boundary, not a successful eligible control.

**Impacted axes:** calibration, depth provenance.

**Smallest safe correction:** ensure neither field enters the proposed registry or table and explicitly evidence their absence in closure review. Keep the frozen counter/hash/predicate untouched. If a receipt relies on these fields, disclose the contract violation rather than silently retargeting or presenting its raw count as eligible depth.

### F5 — MEDIUM, conditional: a fixture observation can become a false general request rule

**Counterexample and evidence.** `n_cmpl` has bounds `1..params_base.n_parallel`, not a universal `1..4`; the pre-freeze counter observed `1..4` under its launch defaults (E5, E10). The counter fixes native `POST /completion`, the short prompt, `n_predict: 1`, binary/library/model pins, and default launch arguments (E7). Its `effective` condition observes `generation_settings`, not sampler influence, model quality, identity, or safe request execution.

The existing skill explicitly says successful completion requests do not establish served identity and refuses model quality/request-safety claims (E3). New rows must not create a competing authority that treats acceptance or a stored parameter as one of those verdicts.

**Impacted axes:** operability, calibration, adjacency; depth if fixture-specific bounds are stated universally.

**Smallest safe correction:** introduce the table with the exact pinned build/model, default argv, endpoint, base request, and the definition “effective means stored in `generation_settings`.” Explain launch-dependent bounds as such, especially `n_cmpl`'s parallelism bound. Keep one-point observations distinct from general clamp/validation rules; source any generalization. Do not infer registered-endpoint health, model identity, sampling effectiveness, or output quality from a row.
