Verdict: C1's own leg is a useful live-image identity check, but its dev/inode comparisons do not establish uninterrupted identity of the extraction pathname through all observations.

# Counterexample and evidence

- **What it proves:** During the counter's `own_exe`, it opens `/proc/<pid>/exe`, hashes that open file descriptor, and compares its fstat device/inode and frozen digest against `os.stat(<work>/server/<member>)` (`tools/round51-replay-exe-audit.py:351-378`). It requires the live receipt's `server_exe` to carry that same tuple and digest, and replay `own_server` to resolve to that pathname and tuple (`:490-498`). This catches the tested outside byte-identical copy/host-install decoy, provided the observed inode is distinct.
- **Inode reuse / replacement race:** A device+inode pair is an identity for a filesystem object at an instant, not a durable extraction provenance token. If the extracted member is unlinked/replaced, its inode freed and reused, and a replacement with the same frozen bytes acquires that inode before `os.stat(member_path)`, the tuple and digest can match although the running executable was not the current extracted object. The member is not opened/held by the counter while comparing: `/proc/<pid>/exe` is opened first, then the member is stat'ed (`:355-370`). The claimed limit on copied-identical binary / archive download (`preregistration.json:41`) addresses deliberate byte-copy indistinguishability, not inode recycling or replacement races.
- **Could the replay swap the member?** The counter opens and fstats `/proc/<pid>/exe` before it writes `release` (`round51-replay-exe-audit.py:463-469`); thus it does observe while the replay is holding the server. It does not lock the extracted member or bind later path stats to the inode object held at extraction/exec time. After release the replay/live process can complete and clean/change files before receipt/path checks. `kama-live-replay.py` itself compares `server_exe` (captured by live tool) to a fresh `os.stat(server)` after `subprocess.run` returns (`kama-live-replay.py:338-345,355-368`).
- **Receipt timing:** Live tool calls `server_exe(proc.pid)` while child is running (`kama-llamacpp-live.py:2039-2044`), before `hold_for_witness` (`:2045-2049`). Counter's independently opened image is observed after ready and before release (`round51-replay-exe-audit.py:452-469`). These are separate snapshots, not an atomic simultaneous observation; requiring equal tuples/digests does not prove no intervening exec/path replacement. In ordinary operation server executable image is stable, but this is a residual race, not a demonstrated normal-path failure.
- **Source quote:** The fetched man7 `proc_pid_exe(5)` says `/proc/pid/exe` is a symlink containing the actual pathname of the executed command, and “attempting to open it will open the executable”; it also explicitly says an unlinked executable pathname gains ` (deleted)`. This is the right ground for the narrow statement that opening `/proc/<pid>/exe` opens the running executable. It does **not** support the stronger inference that matching pathname stat dev/inode proves the executable was extracted from the archive; that is supplied by replay procedure and is vulnerable to copy/replacement/inode-reuse scenarios.

# Smallest safe correction

Keep the claim bounded to “the observed running image's dev/inode and digest matched the extracted-member pathname at the observation” rather than “very file the replay extracted” as an unqualified provenance conclusion. For stronger binding, open the member once before exec and retain a descriptor through observation, or use an immutable/private extraction directory and verify a held member fd against the proc fd; record comparison while the witness is held. This reduces path substitution/reuse windows but does not independently prove archive acquisition against a malicious replay implementation.
