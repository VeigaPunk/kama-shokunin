## Evidence and boundaries

[Ollama issue #19177](https://github.com/ollama/ollama/issues/19177) reports that on main at `2cd63f7`, a runner failure after a streamed chunk was represented upstream as an in-band JSON error. According to the reporter, the Anthropic-compatible `/v1/messages` middleware decoded it as an empty chat response, emitted no error event and ended without `message_stop`, leaving partial content without the reason. The same issue says `/api/chat` delivered the error line. This is the reporter's account, including its reproduction, not our independently observed live behavior. It does not establish the behavior of every release, model, SDK, endpoint, deployment or cause of truncation.

[PR #19188](https://github.com/ollama/ollama/pull/19188) is marked merged into main on 2026-10-22. Its GitHub-identified merge commit is [`efabf6bc450454dc856c1f799aac7ea865e3a4cf`](https://github.com/ollama/ollama/commit/efabf6bc450454dc856c1f799aac7ea865e3a4cf); the [rendered diff](https://github.com/ollama/ollama/pull/19188/files) changes the Anthropic middleware and two test files. It decodes a string `error` alongside the chat response and, only when streaming and that string is nonempty, routes it to the error writer before ordinary chat conversion. If the streaming response has already been written, the error writer sends an SSE `error` event with the converted error fields; otherwise its JSON response path remains. In the web-search writer it also marks the terminal flag before passing the error to the inner writer, and sets SSE content type for passthrough chunks. These are observations about the shown change, conditional on the code being present and reached, not guarantees about the final bytes delivered over a network. Malformed JSON, an empty error string and differently shaped errors are not covered by that nonempty-string branch.

The issue mentions a related [OpenAI-writer PR #18953](https://github.com/ollama/ollama/pull/18953), which was shown open when retrieved on 2026-11-03. Its status may change. Do not infer an OpenAI-compatible endpoint fix, an `/api/chat` fix, or identical failure handling from the Anthropic change.

The current [Anthropic streaming documentation](https://platform.claude.com/docs/en/build-with-claude/streaming) describes named SSE events, a normal sequence ending in `message_stop`, and in-stream error events. Its [error documentation](https://platform.claude.com/docs/en/api/errors) notes that a stream can fail after HTTP 200. This is useful protocol context; it does not prove that Ollama, a proxy, or a particular SDK conforms in a deployment.

## What tests show and do not show

It asserts committed HTTP 200, SSE content type, a flush, preserved partial text, and a sequence ending in a structured error event instead of a success terminal event. Other added cases check JSON errors before streaming: ordinary streaming 500, web-search streaming 429, and non-streaming web-search 500. A separate test uses a local mock upstream and `ChatHandler` for both ordinary and web-search paths, asserting partial text, one terminal error event and no `message_stop`. These are test definitions and their assertions, not observed results here. The PR page displayed 12 checks as passed. ## Twelve adversarial hypothetical decisions

Each case is an invented paper exercise. Code-specific answers assume the pinned change is deployed, the described path is reached, and the stated input is successfully delivered to the writer. They do not claim an observed test or outcome in a live service.

1. **HTTP 200 with partial output and an error.** A client receives a text delta followed by an SSE `error`. **Decision:** classify the response as failed with partial output, not successful merely because HTTP is 200 or text is readable. Record the event and ordered sequence; avoid presenting the partial output as a completed answer.
2. **EOF without either terminal event.** A stream ends after a text delta with no `message_stop` and no observed `error`. **Decision:** treat completion as unconfirmed or interrupted, not as evidence of this exact runner bug. Compare server-side and client-side event traces and connection termination: a network break, proxy, cancellation or another fault is also possible.
3. **Runner failure before any output.** A streaming request receives a 500 JSON response before a stream is written. **Decision:** handle the HTTP/JSON error path rather than expecting an SSE event. The diff's added pre-stream test defines this case; it does not imply all pre-stream errors are 500 or prove that any live response occurred.
4. **Web-search rate limit before streaming.** A web-search request receives a 429 JSON error before output. **Decision:** treat status and error response as pre-stream failure, not a mid-stream SSE error. The added test asserts this specific scenario, not a universal mapping for all rate limits or writers.
5. **Web-search failure after partial content.** A nonempty in-band string error reaches the changed web-search streaming writer after the response has been written. **Decision:** the branch marks terminal state and delegates to the error writer, whose written-stream branch emits an error event. The test expects no `message_stop`; inspect the actual ordered wire events and delivery before claiming end-to-end success.
6. **Local versus forwarded error.** Two inputs carry the same nonempty error string after partial output, one encoded in-band locally and the other forwarded by a handler. **Decision:** the added middleware test defines both styles for each writer and expects the same terminal error pattern. A mock remote-handler test supplies further scoped coverage. Neither proves every remote transport or backend error is handled.
7. **Empty or object-valued error.** A hypothetical chunk has `error: ""`, or an object rather than a string. **Decision:** the shown nonempty string condition cannot establish successful error forwarding for either case. For an incompatible JSON type, decoding can itself fail; inspect the actual input and returned error rather than treating it as a tested runner failure.
8. **Malformed JSON or broken SSE frame.** An input line is truncated before it can be decoded, or the network breaks during an event. **Decision:** the shown decode-error return and the defined valid-input tests do not guarantee a readable error event at the client. Capture framing and writer/transport errors on both sides, with redaction.
9. **Error occurs before first content but status is already committed.** A response has no visible content delta, yet headers were already written before a recognized error reaches the streaming writer. **Decision:** the code's distinction is whether the writer reports the response written, not whether a person saw text. Investigate response commitment and emitted event sequence; do not infer the JSON branch merely from an empty display.
10. **Proxy strips or buffers the error.** The server trace shows an error event, but a downstream client sees only text and EOF. **Decision:** the server-side change does not guarantee delivery through an intermediary. Correlate authorized traces at the writer, proxy and client, content type, buffering and closure; distinguish emitted, flushed and received bytes.
11. **App retries a partial tool-use stream.** A client sees partial content, then an error, and wants to retry. **Decision:** do not assume a retry is safe or that partial tool input is complete. First establish whether any downstream side effect occurred and the relevant idempotency and authorization rules; do not execute partial tool arguments as a complete call.
12. **Merge or checks claimed as a fleet-wide fix.** A dashboard says the PR merged and some checks succeeded, but gives no deployed version or endpoint. **Decision:** that evidence alone cannot establish a production fix, an OpenAI-writer fix, successful client error handling or a completed output. Map the exact binary and route, intermediaries and SDK; distinguish the test definitions and reported checks from independent results.

## Diagnostic approach

For an authorized future investigation, capture the endpoint, stream mode, server build or commit, request correlation ID, client and SDK version, and whether web search or remote forwarding is involved. Preserve only necessary, redacted event names, order, response status, content type, flush and termination evidence at the server and relevant intermediaries. Avoid collecting prompts, partial generated content, credentials or tool arguments unless necessary and authorized. Lack of a logged event is not proof that it was never emitted.

Establish whether HTTP was committed, whether an in-band error reached the middleware and its shape, and whether the writer returned an error. Compare that with the client's received SSE frames and terminal handling. A delivered `error` signals failure; a missing `message_stop` without an error establishes incomplete or uncertain completion, not its cause. Separate response generation, translation, transport, parsing and downstream side effects. Verify the deployed build and compatibility before proposing a change; this lesson authorizes no configuration change, retry or live test.
