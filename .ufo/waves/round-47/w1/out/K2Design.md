# K2Design — round-47 C2 design critic (operability)

Verdict: the replay is **operable** — it exists, runs, and reproduces receipt-1's checks end-to-end on a fresh scratch (verified live, exit 0) — but the *provenance record* and the *replay comparison* are both weaker than the schema claims: record-time accepts unreplayable provenance, and replay compares predicate-level pass/fail, not the captured surfaces the receipt asserts. Five findings below, each with the smallest change that makes it truer.

## Findings (defects + smallest fix each)

### F1 — provenance is recorded, never verified at record time (tools/kama-llamacpp-live.py:1123-1131, 1362-1367, 1381-1386)

The four `--server-asset-*`/`--model-url` flags are accepted by argparse as bare strings (`help='provenance: … (recorded, not fetched)'`, line 1125). The only validation is a 64-hex regex on the two sha256 fields (lines 1362-1367). No scheme check, no atomicity check, no link between the recorded archive/member and the served binary (`server.sha256` is the binary's digest; `provenance.server.asset_sha256` is never connected to it). Demonstrated: `kama-llamacpp-live.py --model /tmp/m.gguf --model-sha256 <64hex> --server-asset-url not-a-url` parses with exit 0 and would emit a **pass** receipt whose provenance is `{asset_url:"not-a-url", asset_sha256:null, member:null, model:{url:null, …}}`; the replay side then refuses it (`provenance-missing:server.asset_sha256,server.member,model.url`). So a typo or omission at record time produces a green receipt that is unreplayable, and the inconsistency surfaces only when a fresh session tries to re-run it — exactly the round-45/46 durability failure mode this round claimed to close. The model side is tied to reality (line 1441-1442 `model-digest-mismatch`); the server asset side is not.
Smallest fix: in `main()` before building the receipt, if any of the four provenance flags is set, require all four (`parser.error` otherwise); require both URLs match `^https://`; require `member` to have no leading `/` and no `..` segment. Optionally add an optional `--server-asset-path` (local copy of the archive, which the installer has in hand) and fail unless the sha256 of that archive equals `asset_sha256` **and** the extracted member's `llama-server` sha256 equals `server.sha256` — that makes record-time provenance self-consistent. The all-four + scheme + member-shape subset is the minimal change; the archive binding is the strongest.

### F2 — replay compares predicate pass/fail, not the captured surfaces (tools/kama-live-replay.py:108-124; tools/round47-live-replay-audit.py:264-291)

`compare()` checks: schema, outcome, server.sha256, model.sha256, and per-evaluated-check `passed` equality. Captured bodies are never compared. Demonstrated: two receipts differing in `captures.health.body` (`{"status":"ok"}` vs `{"status":"degraded"}`), `props.fields.build_info` (b11909-… vs b99999-…), and `slots.element_count` (4 vs 0) match (`compare()` → `[]`); even a rerun receipt with **no captures key at all** matches. The counter's replay leg mirrors this (only schema/outcome/start/sha256s/inside/check equality). Nuance: some surfaces are indirectly pinned by checks — health body must equal exactly `{"status":"ok"}` (check `health_ready`), models ids/owned_by, metrics status 501, props model_alias, probe verdicts, loading-503 envelope exactness, teardown graceful/port-closed, model unchanged — so the gap is the surfaces *not* referenced by any check: `props.fields` beyond alias (build_info), slots body/element_count, metrics body, transitions bodies, teardown `term_wait_ms`/`log_lines`. The live rerun shows the stable fields actually are equal; only `models.created` (epoch), `term_wait_ms` (timing), and `log_lines` text (paths/times) legitimately drift.
Smallest fix: extend `compare()` to compare semantic stable fields, not raw bytes: `captures.props.fields` dict equality, `captures.slots.element_count`, health/models parsed content (already covered by checks), and `teardown` `returncode`/`port_refuses`/`sigkill_sent`; explicitly exempt `models.created`, `term_wait_ms`, `log_lines` text, `port`, `child_pid`, `argv` (documented as run-varying). A naive body_sha256 comparison would false-fail on `models.created` (625 s drift observed) — semantic compare is the only safe form.

### F3 — the counter replays receipt-1 only (tools/round47-live-replay-audit.py:96, 258-262, 297-319)

`RECEIPTS` names all three receipts for the structural `receipts` leg, but the `replay` leg and both `tamper` cases use only `RECEIPTS[0]`. Two of the three committed b11909 instants are trusted on structure alone (schema/outcome/checks/build_info/provenance fields); they are never re-exercised. The frozen predicate itself says "reproduces receipt-1's checks", so this is a sufficiency gap for a future round, not a freeze violation. Smallest fix (next round): loop the `replay` leg over all three receipts (cost ≈ 3× the 24 MB downloads), or teach `kama-live-replay.py` to accept multiple `--receipt` values and run them in one invocation.

### F4 — replay depends on two third-party hosts, and the b11909 row is a GitHub prerelease (tools/kama-live-replay.py:20, 57-65, 141-142; tools/round47-live-replay-audit.py:75)

Documented in both docstrings ("Network: https only, for the two recorded URLs"; "Needs network access to github.com and the model URL"), so it is a disclosed tradeoff, not a hidden defect — and my live run confirms it works today. The axis risk: the asset URL points at a **prerelease** tag (`release-b11909.json`: prerelease true, published 2026-10-26T21:00:58Z). If GitHub prunes/edits the tag or Hugging Face moves the model, every future replay permanently refuses, and the committed evidence silently becomes unre-runnable — the same cliff round 45/46 hit with the model cache file. Smallest hardening that does not rewiden the claim: add an optional `--cache-dir` to the replay so a fresh session reuses an already-acquired, digest-verified copy (still refusing on digest mismatch), and/or commit the two acquired artifacts (22.5 MB + 1.2 MB, or their digests plus a mirror URL) into the wave evidence directory so an offline replay path exists. At minimum, note the prerelease retention risk in the SCORECARD capability row.

### F5 — `teardown.log_path` null is a legitimate fix for D5, not evidence removal; it does narrow the retained log (tools/kama-llamacpp-live.py:20-28, 82-85; receipt-1.json:551-566; tools/round47-live-replay-audit.py:171-178)

The b11906 receipts' `log_path` pointed into deleted seat scratch — a dead pointer (round-46 Mistakes dead-pointer row). The v4 fix records `log_path: null` and inlines the kept lines in `teardown.log_lines` (receipt-1: 3 lines, `log_lines_truncated: false`, `log_tail_truncated: false`). That is a fix, not a removal: the pointer never referenced durable evidence (scratch was always scheduled for deletion), so nothing durable is lost by nulling it; the counter accepts null **or** a committed repo-relative path (lines 172-178). Two honest caveats: (a) the retained lines are a regex-filtered subset (`LOG_KEEP = build|model loaded|listening|loading`, cap `LOG_KEEP_MAX=200`, lines 82-85) — the full raw log is never preserved, so post-hoc forensics beyond the lifecycle markers are impossible; (b) D5's proposed remedy was "in-tree or basename", and the implementer chose a third option (null), which should be recorded as the decision. Smallest improvement: add an optional `--keep-log PATH` that writes a repo-relative copy of the raw log next to the receipt (then `log_path` becomes the committed path the counter already accepts); otherwise keep null and state the filter policy in the capability row (the docstring already does, lines 24-25).

## Impacted axes

Operability (C2) — the score-8 claim remains supported: the replay is real and ran (exit 0, match=True, frozen digests reproduced). F1-F3 make the *claim* truer (record-time provenance self-consistency, capture-level agreement, all-three-receipt replay); F4/F5 are hardening/evidence-fidelity notes, not falsifications.
