## Findings

### F1 (medium, definition + predicate violation; latent on lane) — `origins()` is first-parent-only, contradicting the frozen "no parent of c" birth definition

- Evidence (definition): `tools/append-only-audit.py:15` — "birth a commit whose blob of the file holds key k while **no parent of it** holds k"; the counter implements exactly that: `tools/round50-append-audit-v5-check.py:417-418` (`allpar = {ln.split()[0]: ln.split()[1:] ...}`) and the loop at `:445-452`.
- Evidence (code): `tools/append-only-audit.py:470` — `parents[parts[0]] = parts[1] if len(parts) > 1 else None` keeps only the first parent; the all-parent loop at `:495` (`for q in (parents[x] or "").split():`) can therefore only ever see 0 or 1 parents. On a merge whose key arrives **only via the second parent**, the tool records a spurious birth at the merge and unions the merge's own section titles into origin.
- Fixture (6 commits, built with `commit-tree`, fixture identity, toplevel asserted; driver `out/V6Review/merge_fixture.sh`): root holds `## Head`+25 dated lines; branch commit adds `twin` under `## Birth`; merge tree holds `twin` under `## Moved` (parents [base, twin-holder] vs [twin-holder, base]); event deletes `twin`+20 dated lines while regrowing `## Moved` to its parent size (the v3 eligibility rule requires the exempt section not to shrink at the event — my first fixture draft violated that and correctly got no carve; keep the regrow).
- Result — same tree, parents swapped, verdict flips:
  - order-a (first parent = base): `deleted=21 graded=20 ungraded=1 status=unrestored` (out/V6Review/order-a.json)
  - order-b (first parent = twin-holder): `deleted=21 graded=21 ungraded=0 status=unrestored` (out/V6Review/order-b.json)
  - Reference computed with all parents (frozen definition): `origin(twin) = ['## Birth']` in both orders — no carve either way (driver output).
  - This violates the counter's own predicate sentence ("gives the same verdict under either merge-parent order", `tools/round50-append-audit-v5-check.py:75-77`) for histories where a key arrives only via the second parent. The counter's order-a/order-b fixtures cannot catch it: their merge holds the twin in *both* branches, so origin is order-independent under either parsing.
- The frozen counter itself rejects the tool on this fixture: `python3 tools/round50-append-audit-v5-check.py --repo <fixture> --tip 68846c0f9a7a999b4c8293c31a614c53546246f2` → `fixture=1 lane=0 scenarios=12/12 met=False`, decisive line `detail: lane: event 68846c0f9a7a f.md ungraded 1 > v5 natively exempt 0` (out/V6Review/counter-merge-fixture.txt; the fixture's other two lane details — tool exit 1 because the 20 dated deletions are unrestored, and the counter's v4 binder not binding my minimal contract row — are artifacts of the minimal fixture, not part of the finding).
- Live lane exposure at 97c864be (out/V6Review/lane-exposure-output.txt; driver `lane_exposure.py`): 327 commits, 2 merges; comparing first-parent-origin vs all-parent-origin for every audited file: **0 divergent keys**. So no wrong verdict exists on the lane today — this is a latent contract mismatch, not a measured misgrading. Risk: any future merge that introduces contract-relevant lines via the second parent silently ungrades their deletion (over-carving raises `ungraded`, and the lane bound has **zero margin** — see residual risks).
- Proposed fix (3-line diff, event diffing stays first-parent, matching the counter's own `par = (allpar.get(c) or [None])[0]`): out/V6Review/proposed-fix-first-parents.diff. Note the parsing predates v5 (unchanged since v3/v4), but only v5's birth semantics read `parents`; v4 origin was "first blob in rev-list order" and never touched it.

## Verified clean

- **`pkeys is keys` sentinel (v5:493-502)**: `pkeys = keys` is assigned only in the same-blob-parent branch, immediately followed by `break`; otherwise `pkeys` is a fresh per-commit set (`v5:494`), so identity can only mean "some parent holds this exact blob" and the skip is correct (no key can be new). Empty-vs-empty sets are distinct objects, so a keyless blob still runs the (no-op) birth loop. Root commit: `parents[x] is None` → `"".split()` → `[]` → every key a birth, matching "(a root commit: every key it holds)".
- **`body_of` caching (v5:474-478)**: keyed by blob sha (content-addressed), shared across commits and files per `audit()` call; cached keysets never mutated (`|=` targets the fresh `pkeys`); `if b else []` is unreachable for real shas.
- **`sections()` fence state machine (v5:282-322)**: 27 unit checks pass (out/V6Review/fence-tests-output.txt, driver `fence_tests.py`): up-to-3-space indents for open/close, closing run same char and ≥ opening length, only spaces/tabs after the closing run, backtick-fence info may not hold a backtick (tilde info may), tab-led lines neither open nor close (CommonMark §4.5), unclosed fence runs to EOF, CRLF lines handled (per-line `rstrip(b"\r")` before the tests, preserving v3 title semantics — v3 stripped CRs only on title lines, v5 on every line, with identical title output outside fences), headings cannot open fences, mixed runs (```` ````~ ```` = 4-backtick fence). ## Residual risks and verification gaps

- **Zero margin on 0718b6abbda6** (`72 <= 72`): any perturbation of that event's grading — including F1 firing on a future second-parent merge — flips the counter to fail even when the tool is otherwise right. Fragility note, not a defect.
- Octopus merges (>2 parents) share F1's limitation; the proposed fix covers them.
