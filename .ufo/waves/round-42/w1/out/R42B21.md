# R42B21 — C2 scaling: is git-mode `cat-file --batch` buffering a problem at 10x the lane?

**Verdict: yes — measured, not inferred. `tools/digest-ledger.py scan --repo` holds the whole `git cat-file --batch` stream in memory twice; at the claim tip that is 469 MB for a 216 MiB history, and at 9.86x the lane (fixture C) it is 4,410 MB (4.21 GiB) for a 2,135 MiB history. The law is `peak_MiB = 2.006 * object_MiB + 24` (three-point fit, residuals 0.2%), so 10x the lane projects to 4.58 GB per scan and the same 2x applies to the C2 counting command, which peaks at 4,433 MB at 9.86x. A 20-line streaming rewrite of `scan_git` (drafted and measured here, artifacts beside this report) cuts the peak 148x to 29,872 KB with a byte-equal summary line and an unchanged 6/6 selftest. C2 itself is NOT falsified: the frozen predicate reproduces at the claim tip (`met=True`, seed 42, live-reference byte-equal to `c2/candidate.out`); the buffering is a latent operability defect at the lane's current size, not a wrong result.**

Seat R42B21 (executor, leaf), lane kama, round 42, axis operability. Read-only toward `/fast/scratch/kama-r42/clone`, `/home/vgpnk/Projects/shokuknow`, sibling lanes and the fleet repo. The only lane files written are this report and its sibling artifact directory `out/R42B21/`. Fixtures live under `/fast/scratch/kama-r42/seats/R42B21/` and were removed after measuring (`gen.py` rebuilds them byte-for-byte).

## 1. The lane at 1x, and what sets the peak

```
$ git -C /fast/scratch/kama-r42/clone count-objects -v        # claim-tip pack, repo-wide
count: 126  size: 1652  in-pack: 15985  packs: 1  size-pack: 31129  garbage: 0
$ git -C clone rev-list --objects 3d9bd8d | wc -l                    -> 16043
$ git -C clone ls-tree -r --name-only 3d9bd8d | wc -l                -> 17642 tracked files
$ # documents the tool scans (md/tsv, not .ufo/, not the ledger)     -> 130
$ git -C clone rev-list --objects 3d9bd8d | awk '{print $1}' | \
    git -C clone cat-file --batch-check | awk '{s+=$3} END {print s}'
226852785            # blobs 225,023,259 + trees 1,738,543 + commits 90,983
```

`size-pack` is 31,129 KiB but the tool reads **uncompressed** object bodies: 226,852,785 B (216.3 MiB), a 7.3x pack-to-buffer expansion. Pack size is therefore not a usable proxy for the tool's memory; reachable-history bytes are.

```
$ TMPDIR=$PWD/tmp python3 sample.py python3 clone/tools/digest-ledger.py scan --repo clone
wall_s=0.652 self_peak_kb=473244 tree_peak_kb=469960 exit=0
stdout: tokens=96 blob=86 external_ok=4 external_absent=0 unverifiable=5 wrong_flagged=1 \
        ledger_bad=0 wrong_unflagged=0 unknown=0
```
(three `run.py` runs: 0.668 / 0.651 / 0.642 s, peak 468,720 / 468,688 / 469,140 KB.)

469 MB for 216 MiB of history = **2.12x**, and the parent's own `VmHWM` (473,244 KB) is the peak — the `git cat-file --batch` child never exceeds it. That is `subprocess.run(..., capture_output=True)` at `tools/digest-ledger.py:143-144` plus the full-buffer walk at `:147-155`: `communicate()` accumulates the whole stdout in a chunk list and then `b"".join(chunks)`, so the entire history is live twice at the peak.

## 2. Fixtures: the law

| fixture | files | docs | reachable objects | object bytes | `scan --repo` wall | `scan --repo` peak RSS | `scan --dir` wall | `scan --dir` peak RSS |
|---|---|---|---|---|---|---|---|---|
| A (`pad=0`) | 20,000 | 201 | 20,254 | 1,268,365 | 0.321 / 0.300 s | 34,352 / 33,552 KB | 0.420 s warm (14.211 s cold) | 27,152 / 28,740 KB |
| B (`pad=18,200`) | 20,000 | 201 | 20,254 | 361,628,365 | 1.145 / 1.084 / 1.165 s | 734,788 / 734,648 / 736,204 KB | 13.535 / 11.978 s | 27,680 / 27,036 KB |
| C (`pad=113,000`) | 20,000 | 201 | 20,254 | 2,238,683,804 | 2.267 s (8.922 s cold) | **4,410,344 KB** | 39.442 s | 27,384 KB |
| lane | 17,642 | 130 | 16,043 | 226,852,785 | 0.652 s | 469,140 KB | 0.351 s (export) / 9.767 s (clone) | 47,504 / 51,292 KB |

Fixture C is **9.86x the lane's reachable-history bytes** with the same 20,000-file / 201-doc shape. Every fixture scan returns `tokens=1000 blob=1000 ... unknown=0 exit=0` in both modes.

Fit over lane (216.3 MiB, 458.1 MiB), B (344.9, 717.6), C (2135.0, 4307.0):

```
peak_MiB = 2.006 * object_MiB + 24.2        # B residual 0.2%, C residual 0.2%
slope alone: lane 2.12x, B 2.08x, C 2.02x   # the 2x is the capture_output double buffer
```

The two other scaling axes are **not** problems, measured:

- **object count.** A set of 160,000 64-hex digests (10x the lane's 12,352 blobs) costs **+28,764 KB**. Count is negligible; bytes alone set the peak.
- **per-document subprocesses.** `scan_git` spawns one `git cat-file -p rev:path` per document (`tools/digest-ledger.py:156-162`). 201 spawns = 0.128 s = **0.64 ms each**; 10x the lane (1300 docs) = ~0.8 s, against the counter's 300 s live-leg timeout. (An earlier 4.79 ms reading was taken while fixture C was being built; 0.64 ms is the clean number.)
- **time.** git-mode wall at C is 2.267 s warm: sha256 over 2.24 GB through a pipe at ~1 GB/s. 10x the lane ≈ 2-3 s. Time is not the constraint; memory is.

## 3. 10x the lane: projection and empirical cross-check

10 x 226,852,785 B = 2,268,527,850 B = 2163.4 MiB:

```
peak = 2.006 * 2163.4 + 24.2 = 4,364 MiB = 4.26 GiB = 4.58 GB decimal
```

Empirical cross-check at 9.86x (fixture C): measured 4,307 MiB, predicted 4,317 MiB, **-0.2%**. The extrapolation is a measured law, not a guess.

Concurrency, using the 16,555 MB that was available on this 30,978 MB host while 89 peers were live: **one** 10x `scan --repo` needs 4.58 GB, so three concurrent runs (a wave runs many seats against the same clone) would need ~13.7 GB and four would OOM. At the lane's current 1x, the same three runs need 1.4 GB — comfortable. The hazard is therefore latent, and the lane is ~1,400 rounds from 10x at its measured ~1.4 MB/round of history growth (`0b606b03` 225,459,575 B -> `3d9bd8d` 226,852,785 B -> `595b65f` 227,195,304 B), but the fix is a 20-line local change and the growth is dominated by multi-MB `.ufo` wave artifacts, so it can jump.

## 5. Findings

### F1 (defect, measured) — `scan_git` buffers the whole `cat-file --batch` stream twice

`tools/digest-ledger.py:143-147` at the claim tip:

```python
143    p = subprocess.run(["git", "-C", repo, "cat-file", "--batch"], input="".join(i + "\n" for i in ids).encode(),
144                       capture_output=True)
...
147    blobs, buf, i = set(), p.stdout, 0
```

Command that shows it: `python3 sample.py python3 clone/tools/digest-ledger.py scan --repo <repo>` on fixture C -> `self_peak_kb=4409928` for 2,238,683,804 B of reachable objects (2.02x), and on the lane -> `self_peak_kb=473244` for 226,852,785 B (2.12x). `capture_output=True` makes `communicate()` hold the chunk list and the joined bytes at once, and `:147` keeps the joined copy live for the whole walk.

**Proposed fix (drafted, measured, artifacts `R42B21/draft-digest-ledger-stream.py` + `R42B21/digest-ledger-stream.diff`):** replace the buffered call with a batched `Popen` stream — write 256 ids, drain the 256 matching replies, hash each body in 1 MiB chunks, never hold an object body whole:

```
$ python3 draft-digest-ledger-stream.py selftest                -> selftest pass=6 fail=0   (original: 6/6)
$ python3 sample.py python3 draft-digest-ledger-stream.py scan --repo <fixture C>
wall_s=1.303 self_peak_kb=29872 tree_peak_kb=28984 exit=0   tokens=1000 blob=1000 ... unknown=0
$ python3 sample.py python3 draft-digest-ledger-stream.py scan --repo clone
wall_s=0.451 self_peak_kb=29052 tree_peak_kb=106320 exit=0
tokens=96 blob=86 external_ok=4 external_absent=0 unverifiable=5 wrong_flagged=1 ledger_bad=0 wrong_unflagged=0 unknown=0
```

4,410,344 -> 29,872 KB at 9.86x (**148x**) and 473,244 -> 29,052 KB at 1x (**16x**), summary line byte-equal to the claim-tip tool, selftest unchanged. The residual 106,320 KB tree peak on the lane is the `git cat-file --batch` child, bounded by git's per-object buffering and independent of history size (28,984 KB at 9.86x).

### F2 (defect, same cause) — the counting command buffers three more times

`tools/round42-digest-audit.py` at the claim tip:

- `:86` `git()` helper: `subprocess.run([...], capture_output=True)` — every caller buffers.
- `:177-178` `ref_git`: the same full `cat-file --batch` capture as F1, on the same 226 MB of history.
- `:292` and `:327`: `subprocess.run(["tar","-x","-C",export], input=git(repo,"archive","--format=tar",tip,binary=True), ...)` — the **whole tip tree as a tar** is buffered in the parent, and this happens **twice** (live/contract export, then the hygiene export).

Command that shows it: `python3 sample.py python3 clone/tools/round42-digest-audit.py --repo <fixture C> --tip HEAD --seed 42` -> `self_peak_kb=4433840` at 9.86x, versus `maxrss_kb=503712` at 1x. Nothing here is wrong at the lane's size (492 MB), but it is the C2 counting command and it doubles every byte it touches.

**Proposed fix:** (a) port the F1 stream into `ref_git` (`:177-183`) unchanged in output; (b) stop buffering the export — `git archive --format=tar --output=<file>` (or `Popen(["git",...,"archive",...], stdout=PIPE)` piped into `tar -x -f -`) keeps the 226 MB / 2.27 GB tar out of the parent. Neither changes a single leg's value; both are verifiable by re-running the counter at the claim tip and requiring the same receipt.

### F3 (finding, not a tool-docstring violation) — dir mode cannot see history-only digests, so the same commit exits 0 under `--repo` and 1 under `--dir`

The blob set is "every blob reachable from REV" in git mode but "every regular file under DIR" in dir mode (module text, `tools/digest-ledger.py:17-18`), and the lane's documents cite digests of **older versions** of tracked paths. At the claim tip:

```
$ python3 clone/tools/digest-ledger.py scan --repo clone      # git mode
tokens=96 blob=86 ... unknown=0 exit=0
$ python3 clone/tools/digest-ledger.py scan --dir export-lane  # plain `git archive` export of the same commit
tokens=96 blob=79 ... unknown=7 exit=1
```

`whois.py` resolves all 7 to historical blobs (`registry/history/DELTA.md`, `.ufo/waves/round-18/c2/survivors.py` twice, `.ufo/waves/round-18/runs/commands.json`, `tools/kama-llamacpp-live.py`, `.ufo/round-10/SEAT-PROTOCOL.md`, `registry/history/latest.tsv` — each `at_HEAD=HISTORICAL`). The 7 are listed in `R42B21/measurements.txt`.

Consequence: the lane's green ledger is a property of the **clone's history**, not of its documents. A consumer with an export (`git archive`, a source tarball, a CI checkout with `--depth 1`) gets `exit=1` with 7 "unexplained" digests that are in fact explained. The C2 counter cannot see this: its `contract` leg compares the tool against a reference that uses the same dir semantics, and its `live` leg only ever uses `--repo`.

**Proposed fix (L1 decision; not implemented here):** state the asymmetry where a user meets it — one sentence in the module text next to the blob-set paragraph (`tools/digest-ledger.py:24-26`) and a `note` in the `digest-ledger` capability row — and optionally add a counter leg `mode_parity` that dir-scans the tip export and requires the unknown set to be exactly the history-only digests the counter derives from `rev-list --objects`. Adding the 7 as `external` ledger rows would **not** work: their paths now hash differently, so they would land in `ledger_bad`.

### F4 (finding, usability trap) — `--dir` on a working clone also hashes `.git/`

The docstring says "every regular file under DIR" and `scan_dir` (`tools/digest-ledger.py:112-122`) walks without pruning, so `.git/` (156 files here, including the 31 MB pack) joins the blob set. Measured on the same commit: `--dir clone` 20.697 s cold / 9.767 s warm versus `--dir export-lane` 0.351 s — a 28x wall penalty for a directory a reader is likely to point at. Not a correctness defect (both return the same token classification), but the module text should say "point DIR at an export", or `scan_dir` should skip `.git/`.

## 6. What this seat confirms and what it does not

- **Confirmed:** C2's frozen predicate at the claim tip `3d9bd8d` — `tool=1 contract=1 live=1 hygiene=1 capability=1 met=True`, seed 42, live-reference byte-equal to `c2/candidate.out`, private `TMPDIR` empty after the run. The tool's `selftest` is 6/6 at the claim tip and 6/6 on the drafted stream.
- **Not falsified, not in scope:** C1 and C3. I did not re-run `round42-selfdesc-reconcile.py` or `round42-capacity-audit.py`; other seats hold those.
- **Not claimed:** the 2x buffering does not change any classification or exit code at any size tested (A, B, C, lane all agree between the buffered and streaming implementations). It is a resource defect, and its size is now measured.
- **Fixture limits:** the fixtures approximate the lane's *file/commit/doc shape* and its *history byte volume*, not its history shape (the lane's bytes are 12,352 blobs with a 18.2 KB mean and a 2.9 MB maximum; the fixtures use 20,000 uniform blobs). Because the peak is driven by total bytes and not by the largest object, this does not affect the law; it would matter only for a per-object streaming fix, and F1's draft hashes in 1 MiB chunks, so it is bounded by the chunk size rather than the largest blob.

## 7. Risks and hygiene

- The lane's history is at 216.3 MiB and the buffered peak is 469 MB; a wave that runs the C2 counter from several seats concurrently is fine today and is not fine at ~10x. Nothing about the claim's verdict changes; the exposure is memory, on a host that is shared with 89 live peers.
- A SIGKILLed counter still leaks its export (already recorded as a known gap in the round-42 lesson); the two `TemporaryDirectory` exports at `:291` and `:326` are 226 MB each at 1x and 2.27 GB each at 10x, which makes that known gap 10x more expensive. Fixing F2(b) also bounds it.
- Fixtures A (316 KB), B (360 MB) and C (2.24 GB) and the private clone were removed from `/fast/scratch/kama-r42/seats/R42B21/` after measuring; `/fast` usage was unchanged (223 GB -> 224 GB peak during the run, back after cleanup). `gen.py`, `run.py`, `sample.py`, `whois.py`, the draft tool and its diff are copied into `out/R42B21/`. `GNU time` was not installed and no package manager was run.
