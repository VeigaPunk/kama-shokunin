FINDING: bind loopback yes (counter and every logged launch argv); foreign port touched no (none observed in the checked measurement records); teardown proven yes (DataA04 records exit 0 and a refused post-stop connection).
LIMITS: “No foreign port touched” means none is evidenced in these receipts, not a proof against a port race: DataA13 records port 47999 and loopback argv but no PID/free-before/exit/free-after fields. The counter's free-port check is not a reservation and it does not authenticate the responding socket to its child PID. One manual-probe note (RevCounterFair, port 47980) says “exact pinned argv” but does not reproduce the host argument. A prior SentinelLive process census reported an unrelated PID on 47777 and explicitly says it was not touched. I ran no live server, counter, or external network check.

## Severity
Medium local-only process-ownership/cleanup caveat; no off-host bind is evidenced.

## Exploit path
`port_free()` releases its probe socket before `Popen`; another local listener could win the port in between. The counter accepts any `/health` 200 and checks `/props` only for the expected model path, not that the listener belongs to `self.proc`. Separately, `Server()` is constructed before the `try/finally`; readiness or `/props` failure during construction can bypass `close()` and leave the child alive.

## Evidence

Frozen counter code (quoted from `.ufo/waves/round-31/count-c1.py`):

131: def port_free(port: int) -> bool:

133:         return s.connect_ex((HOST, port)) != 0

The normal counter path is `server = Server()` before `try` (`389-390`), then `finally: server.close()` (`578-579`). `close()` sends SIGTERM to the child and waits 15 seconds; on error it tries `kill()`, then checks port freedom for up to 10 seconds (`206-219`). It does not wait/reap after `kill()` or raise if the port remains occupied.

Recorded wave-1 launches use only loopback in their explicit argv and use ports in 47900-47999: DataA01 `47908`; DataA02 `47900`; DataA04 `47901`; DataA13 `47999`; DataA14/DataA17 `47900`; CriticIgnoredClass `47956`; and the RevCounterFair manual probe `47980`. The scoped live-record search found no measurement launch using 8080 or 34113. The 47777 process is only the separate pre-existing process noted by SentinelLive, not a measurement target.

Teardown evidence: DataA04 says, verbatim, `Port 47901: server process exit 0; post-stop connect_ex returned 111 (connection refused; no listener).` DataA01 records `port_free_after_close: true`; DataA02 records `exit_code: 0` and `port_free_after: true`; CriticIgnoredClass records PID 4103564, `server_exit: 0`, and `port_free_after: true`. CriticClaimSize's prior receipt records an empty `ss` result before and after all three C1 counter runs. These are historical seat receipts, not commands run in this audit.

## Impact
The available evidence supports loopback-only listeners, so it does not show off-host exposure. A local port collision could instead make a measurement consume a different local service, invalidating the result. On startup failure or abrupt parent termination, the counter can leave its own loopback service running; no such failure is shown in the inspected receipts.

## Smallest remediation
Keep the explicit loopback bind. Tie readiness to the spawned process/socket owner (or reserve and pass an inherited listening socket if supported), make construction exception-safe, and require successful wait/reap plus a hard failure if the port remains bound after teardown.
