# R06C1Fields — C1 `ld_audit` field binding

## Finding

**Low-severity robustness gap: detection is derived by substring, although the reported field and battery assertion use exact values.** In `tools/round56-env-leg-test.py:25-29`, the driver sets `detected` with `any("LD_AUDIT" in x for x in probs)`, then emits only `ld_audit=detected|missed`. The battery `tools/round56-env-leg-battery.py:27-31` parses the `ld_audit` token and requires `fields.get("ld_audit") == expected` plus exit 0; therefore that final field/value assertion is exact, not a substring/presence check. However, any unrelated problem string containing `LD_AUDIT` would make the driver report `detected`, so the field does not unambiguously attest that `env_leg` reported the exact variable name. Proposed fix: derive detection from exact problem equality (`"env: server environment carries LD_AUDIT" in probs`) or, preferably, expose/check the exact environment-key set in the test driver. Keep the frozen expected values and exit assertion unchanged.

The frozen counter's own `env_leg` (`tools/round56-replay-code-audit.py:430-441`) is exact at variable-name level: `environ_keys` extracts names before `=`, and the leg tests `bad in keys`, with `LD_AUDIT` in `BAD_ENV`. Thus `LD_AUDIT_EXTRA` does not match. The concern is specifically the test driver's subsequent substring scan over diagnostic strings.
