## Actionable findings

1. **[Medium] HTTP response headers and truncation metadata are captured but not graded or integrity-bound.** `tools/kama-completion-live.py:91-98,120-127` stores status, headers, only the first 65,536 response bytes, and `body_truncated`, but `_cap` drops headers and `body_truncated` and hashes only the retained decoded body. `tools/round62-c1-counter.py:94-99` re-hashes only `body`; `grade` makes decisions from status/body but never requires `body_truncated is False` or any header contract (`:100-158`). Thus changed headers or a receipt marking a truncated body are invisible to recomputation; a response whose decisive JSON happens to be in the prefix can grade despite undisclosed trailing response bytes. Existing log control mutates body without updating its digest (`:393-395`), not these fields.

2. **[Medium] The checked timing surface accepts invalid/implausible values and is not checked for presence as an actual object.** Live tool `tools/kama-completion-live.py:346-352` grades only that `predicted_n` is an `int`, matches usage count, and `predicted_ms` is numeric. Counter repeats this at `tools/round62-c1-counter.py:139-144`. Python `bool` passes both `isinstance(..., int)` checks; negative/non-finite predicted_ms also passes `(int, float)`. Missing `timings` falls back to `{}` and fails, but no bounds/finite/nonnegative constraints exist. The 16 controls do not mutate timing values (`:395-423`), so this accepted surface has no targeted control.

3. **[Medium] Completion response second-order fields are largely ungraded.** `tools/kama-completion-live.py:312-352` and counter `tools/round62-c1-counter.py:113-144` check a narrow envelope plus finish reason, model alias, fingerprint shape, token arithmetic, and a timing relation. They do not constrain completion text to nonempty/usable, validate every choice, require choice index/choice count semantics, or validate other response fields such as `id`, `created`, `object` relationships, token count against requested `n_predict`,/ fingerprint consistency with the separately observed build. `completion2` similarly grades only equal text and 200 (`counter :145-153`; tool `:353-371`). The fingerprint check is shape-only (`counter :127-129`); the outside witness independently checks shape (`:199-200`) but never requires equality between the two fingerprints. The existing controls alter envelope/model but do not target these fields (`:395-423`).

4. **[High] Witness nonce binding is self-asserted rather than derived from observed request bytes or response.** `tools/round62-c1-counter.py:247-269` sends `nprompt`, then sets both `sent_prompt` and `nonce_prompt` to that same local variable without retaining/validating the actual HTTP request bytes; score accepts equality and presence of nonce in those two witness strings (`:201-204`). The live response text is only required to be a string (`:199-202`), not nonempty or demonstrably related to the nonce request. Consequently a response with arbitrary/empty text still satisfies the witness's alleged nonce binding, and the two fields cannot detect a disconnect between the claimed prompt and the request that reached the server. Current fake controls do set differing prompt fields, but do not establish that witness fields are evidence rather than duplicate constants (`:445-472`).

5. **[Medium] Live witness omits response-envelope and fingerprint cross-binding checks.** In `tools/round62-c1-counter.py:254-272`, the witness pulls `model`, `system_fingerprint`, and `choices[0].text` with defaults; `score` checks status 200, alias, fingerprint regex, and string text (`:194-206`) but not `object == text_completion`, nonempty text, or fingerprint equality with the tool's completion capture. The completion capture is bound only on `model` and server digest (`:207-212`). Thus mismatched build fingerprints / non-completion JSON responses can pass the “live answer bound to ... build fingerprint” condition provided those extracted fields look plausible.

6. **[Medium] One recomputed check is not recomputed from independent evidence.** `grade` assigns `listener_owned` directly from the stored receipt check's own `passed` bit (`tools/round62-c1-counter.py:159-160`); the subsequent consistency comparison compares this derived value back to that same stored bit (`:173-183`). This makes the receipt's recorded listener-ownership assertion self-validating at the `listener_owned` check layer. `score` separately requires `witness.listener_owned` (`:204`), which is stronger independent evidence for the held child, but does not repair the receipt's claimed first-answer listener check; the two measurements occur at different times. No control targets changing only `checks.listener_owned.passed` (`:395-435`).

7. **[Low] Receipt fields outside captured body bytes have no integrity coverage.** `grade` verifies each captured body hash (`tools/round62-c1-counter.py:94-99`) and checks select receipt `model/server.sha256`, hold released, teardown fields, nonce, and verdict (`:159-171,189-218`), but there is no canonical receipt digest/signature. Unused capture members (`headers`, `body_truncated`) and metadata (`at`, `request`, `argv`, `port`, `child_pid`, paths/log location) are not generally bound together. Some critical relationships are separately checked by `score` (witness pid/port and fixture digests), but `request`/argv values are not checked against the claimed defaults. In particular changing request metadata does not alter the graded checks; the counter's fixed witness prompt and constants provide no receipt-request binding.

## Conditional checks / control coverage

- In the producer, `completion_finish_reason`, model/fingerprint/usage/timings and deterministic repeat are emitted only inside `if ok_env` (`tools/kama-completion-live.py:323-371`). If the envelope fails, those producer checks are absent. The counter does derive these outcomes from captured completion bytes regardless (`tools/round62-c1-counter.py:116-153`) and requires the expected check-name set (`:173-182`), so this conditional is not by itself a demonstrated bypass for the live counter. It does mean the receipt can omit downstream check records on the failure path and rely on `missing-checks` rather than a complete evaluated record; no control specifically exercises a failed envelope with these checks omitted.
- `hold_released` is only recomputed if the stored checks include it (`tools/round62-c1-counter.py:165-166`), although the fixed expected set later demands it (`:174-182`). Missing it is rejected via `missing-checks`; it is not independently evaluated on that path.
- The response-surface gaps above are not represented among the controls: controls cover stale nonce, body hash/body mutations, teardown/hold, verdict/digests, outside model mismatch, and two fake-server cases (`tools/round62-c1-counter.py:386-472`), but not headers, truncation flags, timing plausibility, choice/metadata semantics, or witness fingerprint/response-envelope consistency.
