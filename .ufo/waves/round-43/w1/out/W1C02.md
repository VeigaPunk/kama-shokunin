## 4. What each readiness route queries
- **#46811 (engine, idle probe):** "`/ready` calls `EngineClient.check_health_gpu()`. In `AsyncLLM` it does three things: 1. Runs the existing `check_health()` liveness check. A dead engine returns 503. 2. Sends one EngineCore utility call, `check_ready()`, which runs on the engine-core thread between steps: if the engine is sleeping or paused it returns not ready…; if no request … is in flight … it runs `execute_dummy_batch()` to confirm a forward pass still works; otherwise it returns ready without adding GPU work. 3. Waits at most `VLLM_HEALTH_CHECK_GPU_TIMEOUT` seconds (default 20)." DP: "With the internal LB, `DPLBAsyncMPClient` sends the probe to every rank it manages"; MoE-with-DP `check_ready()` never runs the dummy batch. Rust frontend does not serve it. Its own body lists #59179 as the later, overlapping PR (#59179 "adds the same `/ready` endpoint"), and proposes a split in which #46811 lands first.
- **#59179 (engine, progress + idle probe):** "`AsyncLLM.check_health_gpu()` first performs the existing liveness check. It then returns not ready if any managed rank reports `SLEEPING` or remains `BUSY` without model-step progress for longer than `VLLM_READY_STALL_TIMEOUT_S`. This path only reads state already broadcast to the frontend." Idle probe only for deployment-wide DP size one.
- **#59179 (DP supervisor / children — the `/readyz` sentence):** "The DP supervisor's `/ready` and `/readyz` handlers concurrently query every child `/ready` endpoint and return 503 if any child is not ready or cannot be queried. A readiness failure does not change supervisor lifecycle state or trigger shutdown by itself." Patch confirms (`check_ready`, `asyncio.gather` over `child_ports`, `"/ready"`).
