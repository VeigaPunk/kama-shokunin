## The boundary

The pinned README describes a router that directs requests to model instances. It can discover entries from a cache, a configured model directory, and presets. Its model-list response includes per-model status. **An entry appearing in a list is evidence of a listed entry, not by itself evidence that an instance is loaded or that inference will succeed.** A status of `loaded` in a particular captured response is evidence of what that router reported at that time, not proof of model weights, inference quality, future availability, or another endpoint's state.

Three actions have different semantics in this source:

1. A preset's `load-on-startup` controls automatic loading at server startup. When a model is newly added to the presets and the list is later reloaded, the README says that it is listed but not loaded by that startup setting. A refreshed catalog therefore does **not** replay startup loading. This is a source-documented counterexample, not a historical incident.
2. Request-time autoload is separate. The README says that, by default, routing a request to an unloaded model loads it automatically; `--no-models-autoload` disables the default and a request's `autoload=true|false` query parameter controls it per request. A later routed request may change the state, so a later loaded status does not show that catalog refresh applied the startup option. The README describes an explicit `POST /models/load` for loading, also a state-changing action; none of these actions is authorized merely by this lesson.
3. `GET /models?reload=1` refreshes the catalog but **is not a passive observation**. If a running model has been updated or removed in its source, the README says refresh unloads it; a non-running model is added or updated according to the source. Do not assume every refresh unloads every model, nor that a running model is automatically loaded again. Do not issue refresh just to inspect state without appropriate authorization and consideration of its consequences.

The same README says to restart the server after adding a new model to the cache, while separately describing list refresh. It does not establish a universal promise that refresh replaces a restart for every source, version, or deployment; retain that qualification rather than flattening the two statements. It describes status values including `unloaded`, `loading`, `loaded`, and `sleeping`, and documents a failed unloaded example. Record the status and any failure details rather than turning all listed states into “ready.”

## Evidence to keep distinct

- Identify the actual responder and role: router versus a direct model server, proxy, or another process. Bind the base URL, endpoint and any intermediary to that identity. A health response from one process is not a per-model loading observation from another.
- Bind version/build and configuration provenance to the relevant process. The pin supports an interpretation only if applicable; absent that match, treat this as a candidate explanation, not a diagnosis. Note effective source and request-time autoload settings as known or unknown.
- Record the requested model name, advertised ID or alias, source entry, and the basis for connecting them. The router routes on the model name; aliases are API names, and the README warns that the router controls or overwrites some instance arguments including alias. An alias alone is not evidence of the underlying weights, and the existence of two labels does not by itself prove whether they refer to one instance.
- Preserve timestamps and ordering for startup, source edits, list captures, reload, routed requests and any explicit loads. A pre-change status is not current evidence. Record whether a capture used a reload parameter; a method named GET is not enough to establish non-mutation.
- Loading, refresh, inference and restart all require their own authorization and operational assessment. A request that routes to a model may autoload it even if the request is framed as a check. Assess permissions and operational impact before taking any such action.

## Twelve hypothetical manual evidence cases

These are independent constructed exercises, not observations, execution results, or requests to run. Each answer is limited to the stipulated evidence and the pinned documentation. Unless otherwise stated, build, responder, authorization and timestamps are unknown.

1. **New preset after startup.** A hypothetical operator says a new preset with `load-on-startup` was added after router startup and the list was refreshed. The entry is now visible, and no other action is stipulated. **Assessment:** the documented refresh makes the entry visible but does not run that startup setting to load it. Do not conclude inference is ready; a later routed or explicit load would be a separate possibility, not an observed event.
2. **Listed versus loaded.** A hypothetical catalog capture lists `alpha` with status `unloaded`. **Assessment:** the entry is advertised and reported unloaded at capture; listing alone is no evidence of loaded readiness. A model-specific request might change that state via autoload, so do not send one as a supposedly passive check.
3. **Loading is not loaded.** A hypothetical capture lists `alpha` with status `loading`. **Assessment:** report the stated transitional status at that time, not a completed load or failed model. Neither time to completion nor eventual success follows from this evidence.
4. **Loaded status is bounded.** A hypothetical identified router at the applicable pin reports `alpha` as `loaded` at 10:00. **Assessment:** that router reported a loaded state at 10:00; it does not establish a successful generation, identity of weight bytes, or state at 10:10. No diagnostic inference or current-state claim is warranted.
5. **Router process versus direct server.** A hypothetical direct server answers at base URL A, while an alleged router catalog is captured at base URL B, with no ownership mapping. **Assessment:** do not transfer a status or health conclusion across A and B. Resolve responder, role, and time first; even a matching model name is insufficient.
6. **Changed source and running model.** A hypothetical record says `alpha` was running, its source entry was updated, and the same applicable router subsequently processed `GET /models?reload=1`. **Assessment:** the pinned README documents unload in that condition. Refresh is consequential; this is not evidence that any real deployment was touched, nor a basis to assume the model subsequently reloaded.
7. **Removed source and running model.** A hypothetical record says `beta` was running when removed from its source, followed by refresh on the applicable router. **Assessment:** the documentation likewise specifies unload. Do not call a reload merely to see whether this happens; the exercise itself sends nothing.
8. **Non-running source update.** A hypothetical source adds a non-running `gamma`, and a refresh is recorded on the applicable router. **Assessment:** the documented catalog behavior is to add or update the non-running entry according to the source; this alone does not establish a loaded instance or successful inference. The special newly added preset startup case in case 1 has the further explicit not-loaded qualification.
9. **Alias versus weights.** A hypothetical requester asks for `friendly`, while a list shows `canonical`; no reliable mapping is supplied. **Assessment:** neither name similarity nor the word alias establishes their relationship or model-file identity. Preserve both names and ask for evidence linking the requested name, catalog entry, source and process before an identity claim.
10. **Request-time autoload.** A hypothetical applicable router has the documented default enabled; an unloaded listed model receives a routed request, without a per-request override. **Assessment:** default request-time autoload is the documented mechanism for loading it; that does not prove completion or success. Do not attribute a later load to `load-on-startup` without evidence of a relevant startup, and do not make the request without authorization.
11. **Override and inference authorization.** A hypothetical applicable router is configured with default autoload disabled and an operator proposes a model-targeted inference request using `autoload=true`. **Assessment:** the documented per-request control is separate from the startup option and could trigger loading. Inference and its possible load are consequential, so require the appropriate authorization; no inference or load has occurred in this exercise.
12. **Stale, cross-version evidence.** A hypothetical screenshot shows `loaded` at 09:00 at base URL A, a source edit at 09:05, and a purported reload at 09:06 at base URL B; the build and process relationships are unknown. **Assessment:** the screenshot does not establish present status at either URL, that B is the same router, or that the pinned refresh semantics apply. Obtain version, process and timestamp evidence before interpreting a later capture; do not guess a live failure or fix.
