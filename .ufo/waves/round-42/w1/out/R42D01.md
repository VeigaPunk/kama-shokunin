```
git -C /fast/scratch/kama-r42/clone cat-file -t b92ad324b52e251e41cea0c3449c3e24028c6119
  → fatal: git cat-file: could not get object info          (exit 128)
git -C /fast/scratch/kama-r42/clone log --all --format='%H %s' | grep -i '^b92ad32'
  → (no match)
git -C /home/vgpnk/Projects/shokunin/kama-shokunin cat-file -t b92ad324…
  → fatal: git cat-file: could not get object info          (exit 128)
```

Cause: `controls/build_controls.py:14-16` builds the controls in `tempfile.mkdtemp(prefix="r42-controls-", dir="/fast/scratch/kama-r42")` and commits there; that sandbox is gone, so the recorded tip is dangling. A verifier cannot re-run "the freeze control" at the tip its receipt names.

```

  → entry=0 rows=0 coverage=0 gate=0 census=1 met=False   exit=1
```

All three summary lines equal the committed `freeze.c1.out` / `freeze.c2.out` / `freeze.c3.out` character-for-character (only the `tip=` field differs; `diff` of everything after line 1 and the `exit=` trailer is empty). The freeze tree's `corpus/SOURCES.md` is byte-identical to base (`git diff --stat 0b606b0 0bfd47a -- corpus/SOURCES.md` → empty). So the *content* of the freeze control is reproducible at `0bfd47a`; only the recorded tip id is not.

Proposed fix (L1's call, since the contract freezes the controls): either add one provenance line to the three receipts mapping the sandbox tip to `0bfd47a` (with the `git diff --stat` above as the content-equality proof), or re-emit the three freeze receipts at `0bfd47a` — for every leg I could check the summary is unchanged.

### F3 — MED (confirms the C2 red state; fixed at the tip, with a caveat)
The freeze tree leaks its temp export. `tools/round41-scorecard-reconcile.py:184` (freeze) calls `tempfile.mkdtemp(prefix="r41c1-")` with no cleanup; my freeze-bytes C1 run left `r41c1-zhb3fwtu` = **259 MB** in my private `TMPDIR` (observed at 19:06, removed by me). The tip registers cleanup — `tools/round41-scorecard-reconcile.py:186-187` and `tools/round41-pinwatch-audit.py:210-211`:

```
186:                export = tempfile.mkdtemp(prefix="r41c1-")
187:                atexit.register(shutil.rmtree, export, True)  # round 42: remove the export (R41A10-10)
```

This is positive evidence that `hygiene=0` at base/freeze is a real property of those trees, not a counter artifact: the same defect in the second counter (`tools/round41-pinwatch-audit.py:208` at freeze, bare `mkdtemp`) leaked `r41c2-g44e3n5t` inside the C2 counter's private hygiene directory during my freeze-bytes `digest-audit` run — observed as `rm: cannot remove '…/r42c2-hyg-kxj3_rxk/r41c2-g44e3n5t/.ufo/waves/round-28/w1/out/DataG05': Directory not empty`, which is exactly what `freeze.c2.out`'s `hygiene=0` records.
Caveat for the C2 leg's wording: `atexit` does not run on SIGKILL, so "leaves the private TMPDIR empty" holds for clean exits only — a run killed by a job cap leaves the export behind (I saw exactly that with a killed `digest-audit` run: `r42c2-src-*` 210 MB).
