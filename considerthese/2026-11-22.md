## Lessons from last 3 days

1. **`/v1/realtime` now has a third mode, chosen by a model capability, not by the request.** `c622f623f` (#32491, 2026-11-21 10:25 BRT) adds full-duplex support for Hibiki. In `server-context.cpp` (~6135) the realtime route now enters `server_realtime_conversation` when `mtmd_cap.audio_duplex` is set, even if the model has no chat capability and even with `?intent=transcription`. In `server-realtime.cpp` (+220/-25) a duplex session has no turns: the first `input_audio_buffer.append` opens a response that runs until `response.cancel`, and `input_audio_buffer.commit`, `conversation.item.create` and `response.create` are rejected with new error texts. The README documents a 120 s attention window with the first 3 rows kept and 1/6 of the window dropped at a time. The lesson: the same endpoint and the same client events now behave differently depending on which model is loaded, so any realtime claim has to name the model capability it assumes.

2. **`reasoning_effort: "none"` now depends on the chat template.** `afe77e18f` (#32763, 2026-11-21 18:27 BRT) changes `oaicompat_chat_params_parse` in `server-common.cpp` (~1641). `"none"` still sets `enable_thinking = false`, but if the template lists `none` in `reasoning_effort_levels` it is now passed to the template as `reasoning_effort` instead of being erased. Same request, different template input depending on the model. The `invalid_argument` 400 for rejected levels is unchanged (only the `levels` lookup moved up). Together with `6aee50801` (UI thinking-effort picker, 2026-11-20), this is now a client-visible knob with model-dependent semantics.

3. **A scheduling fix for non-causal models, with a test that pins it.** `225a5345b` (#32713, 2026-11-22 00:25 BRT) makes slots that cannot split check against `min(n_batch, n_ubatch)` when attention is non-causal (`server-context.cpp` ~4288), because `llama_decode` needs a non-causal batch in one ubatch. The new `test_systemone_noncausal_parallel` (vllm-d3, `n_batch=2048`, `n_ubatch=512`, 4 slots) checks that 4 parallel decision requests give the same answers as one. Before this, concurrent long prompts on a decision/embedding model with `n_batch > n_ubatch` could be packed into a batch that does not fit. Stability check at HEAD: `server-context.cpp` is 7286 lines (+2 vs yesterday's 7284, from this commit) with `GGML_ASSERT=86, GGML_ABORT=7` (lines containing each token), unchanged; `server-realtime.cpp` is 1486 lines with 1 `GGML_ASSERT`. `"models_autoload"` is still at `server-models.cpp:2064` (6 days unchanged, +34 vs the cited 2030). ## Self-improvement suggestions

These are proposals only; I'm not acting on them. They avoid repeating `2026-11-05.md` to `2026-11-21.md`.

1. **Realtime mode dispatch table:** keep one small table of how `/v1/realtime` picks its handler (capability flags `audio_duplex`, `audio_stream`, `chat`, `asr_prompt`, and the `intent` query param) and which client events each mode accepts or rejects. Lesson 1 added a branch in a single `if`; a table makes such a change a one-row diff I can't miss.
2. **Tag claims with the model capabilities they assume:** add a `requires:` field (for example `template:reasoning_effort_levels`, `attn:non-causal`, `mtmd:audio_duplex`) to knowledge files and r101 cells. Lessons 1 to 3 are all "same request, different behavior per model", which a claim without that field can't express or test.
3. **Add a batch-shape axis to r101 cells:** for any slot or concurrency claim, run once with `n_batch == n_ubatch` and once with `n_batch > n_ubatch`, and once with a non-causal model. Upstream's new test in lesson 3 uses exactly that shape, which my cells never varied.
