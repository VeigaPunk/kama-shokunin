## Source interpretation

1. **The bound is on a channel, not all work.** At scheduler initialization the value returned by `MaxQueue()` sets the buffer capacity of `pendingReqCh`; other scheduler channels are constructed with that capacity too. The config source defines `OLLAMA_MAX_QUEUE` with a default of 512; its unsigned parser falls back to the default for invalid input. A configured value is not evidence of the value actually read by a particular scheduler instance. The pending channel is not a count of all active inference, and an item already taken by the pending loop is no longer in its buffer.
2. **There is a bypass.** `getRunner` looks up the scheduler key in the loaded map and, if a runner exists and `needsReload` is false for the request, calls `useLoadedRunner` directly. Otherwise it tries a nonblocking send to the pending channel. If the send cannot proceed immediately, the default branch returns `ErrMaxQueue`. Thus a full pending buffer does not establish that a request using an eligible loaded runner encounters this admission error. It does not prove immediate generation, an available inference slot, a successful answer, or that all same-name requests qualify: the decision uses the scheduler key and reload check.
3. **Admission is not completion.** Successful channel send admits work to the pending path, not successful model loading, execution, response, or completion. One pending loop takes and works on a request, rechecks the loaded map, may reuse a now-usable runner, load, or arrange expiration and wait for unload. Its source notes that pending processing blocks other pending requests while working on the current one. The separate completion loop handles finished requests and expiration; loaded-runner requests can take the fast path while pending work is in progress. No fairness, latency bound, or global concurrency cap follows from the buffer size alone.
4. **Cancellation is not immediate queue removal.** When the pending loop takes a request whose context is already done, it skips scheduling it. The cited code does not establish that cancellation removes a buffered request at the instant of cancellation, nor that all possible downstream work ends immediately. The loaded-runner helper also arranges a finished notification when the request context ends; that notification is lifecycle bookkeeping, not proof of a successful answer.
5. **Error mapping is path-specific.** The FAQ describes overload as a 503 and `OLLAMA_MAX_QUEUE` as the configurable queue limit. In the pinned native generate path, `scheduleRunnerForModel` selects the scheduler error, the handler passes a scheduling error to `handleScheduleError`, and `scheduleError` maps the actual scheduler `ErrMaxQueue` value to HTTP 503. Its other earlier checks take precedence for an error that matches more than one category. This is a conditional code path, not a converse: a client-observed 503 alone does not establish `ErrMaxQueue`, this scheduler branch, this process, or even that the response originated in Ollama. A gateway, proxy, another handler, middleware, upstream service, or different version may be responsible. Other error mappings and routes must be checked separately; no universal route mapping is claimed.
6. **Three settings govern different ideas.** `OLLAMA_MAX_QUEUE` bounds the pending channel buffer, `OLLAMA_MAX_LOADED_MODELS` concerns resident model capacity, and `OLLAMA_NUM_PARALLEL` concerns parallel requests per model, subject to implementation and model restrictions. The FAQ describes memory requirements and queued model-loading behavior; read its broad wording alongside the code's loaded-runner fast path rather than treating it as proof that every request joins `pendingReqCh`. Raising a queue limit may allow more pending admissions under particular conditions but does not itself create execution capacity, memory, or a latency guarantee. No configuration change is recommended without measuring the actual bottleneck and risk.

## Twelve adversarial hypothetical cases

All cases below are invented manual judgments, **not actual tests or incidents**. For every case that adjudicates a code path, assume the cited pin applies hypothetically; this asserts nothing about an actual deployment. Case 9 leaves the responding version and origin unknown. Times, channel readiness, route and identities are facts of each hypothetical, not measurements made here.

1. **Cold request, buffer cannot accept.** A request reaches `getRunner`; no eligible loaded runner exists, and the pending send cannot proceed at that instant. **Decision:** the default branch gives that request `ErrMaxQueue`. The pending send is an admission attempt, not an inference attempt or proof that a prior request completed.
2. **Cold request, space available.** A request takes the pending branch and the send succeeds. **Decision:** it entered that channel; outcome and response time remain unknown. The active pending item and work outside the channel are not measured by the buffer occupancy.
3. **Saturated buffer, eligible loaded runner.** While the pending buffer is full, an incoming request's exact scheduler key resolves to a loaded runner and its reload check is false. **Decision:** it takes the direct helper rather than this pending send. Do not infer that inference finishes promptly or succeeds.
4. **Same displayed model, reload required.** The same model label is presented, but the actual key resolves to a loaded runner and `needsReload` returns true; the pending send cannot proceed. **Decision:** it takes the pending branch and receives `ErrMaxQueue`. A label match alone does not establish fast-path eligibility or the reason reload was required.
5. **Runner appears after admission.** A request entered the pending channel while its runner was not eligible; by the time it is processed the source's recheck finds a usable matching runner. **Decision:** pending processing can use it. Initial admission does not establish a new model load occurred.
6. **Pending item already removed.** The loop has taken one request and is waiting for an unload; all N buffer positions are occupied by other requests, with N greater than zero. **Decision:** the active item is separate from the N buffered items. A further non-fast-path send that cannot proceed gets the admission error; N is not the total number of outstanding requests.
7. **Cancelled while buffered.** A request is admitted and then its context ends before the pending loop receives it. **Decision:** on receipt, the cited loop sees the done context and skips scheduling. The source does not promise instant removal at cancellation; do not count a slot as freed until supported by observation.
8. **Direct helper, later failure.** A request passes the loaded-runner check and is handed the runner, but its later inference fails. **Decision:** those facts are consistent; runner allocation was not completion or output validation. Diagnose the later failure separately rather than relabeling it a queue rejection.
9. **Observed 503 behind proxy.** A client sees a 503 but the responding component, route, response body, request correlation, and server version are unknown. **Decision:** the origin and cause are unresolved. Collect hop-by-hop evidence; do not conclude the scheduler queue was full or change its limit on this evidence.
10. **Mapped native error.** A correlated native `/api/generate` request on the pinned build reaches its scheduling error handler with the actual scheduler `ErrMaxQueue` error, and the handler's response is observed before intermediaries alter it. **Decision:** this branch maps it to 503. The established branch supports an admission failure for that request, not a universal explanation for other 503s.
11. **Invalid configured text.** The scheduler starts with an invalid unsigned `OLLAMA_MAX_QUEUE` value and the pinned parser behavior applies. **Decision:** the parser uses 512 rather than the intended text. Establish the value and instance lifetime; do not assume a later environment edit changed the existing channel's capacity.
12. **Zero capacity and ready receiver.** `OLLAMA_MAX_QUEUE=0` is read at initialization, and a pending-loop receive is ready precisely when the non-fast-path send is selected. **Decision:** an unbuffered channel can hand the request directly to that receiver; zero buffer does not mean every such request is rejected. If the send cannot proceed at that moment, the default branch returns the admission error. Neither outcome says whether inference completes.

## Practical diagnosis and limits

For a future authorized investigation, first bind the request's timestamp and correlation identifier to the responding hop, exact endpoint, process lifetime, binary build/commit, and effective configuration at scheduler initialization. Preserve the status, error body, proxy and server logs if available, and distinguish locally generated from forwarded or rewritten responses. Establish whether a particular request reached the native handler and whether it received the actual scheduler `ErrMaxQueue` error and, for other errors, account for earlier error checks; absence of an available log is not evidence of the branch taken. Avoid collecting prompts, personal data, credentials or request bodies unless needed and appropriately authorized.

Next separate channel admission from processing and response completion. Gather existing evidence of model key, reload eligibility, resident runners, pending activity, cancellation, unload/wait, execution capacity and memory, without assuming a queue length can be reconstructed from a status code. Compare contemporaneous observations from the same instance; different servers, restarts and stale configuration can invalidate a join. Before any operational change, evaluate workload, available memory, expected latency and where backpressure should occur. Larger buffers may trade rejection for longer waits and resource pressure; they do not prove increased throughput. These are diagnostic questions, not a command to run tests, restart, tune, or deploy.
