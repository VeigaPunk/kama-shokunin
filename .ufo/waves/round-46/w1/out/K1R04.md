## 3. Attack on the frozen C1 counter for these rows

**3a. Range choice drops the condition — accepted.** `cited()` (counter, `def cited(c)`) scans only `c[1]` (source cell) and `c[5]` (anchor cell). For S114 the only STRONG number there is `5366`; the guard is named only in the *teaches* cell (`server-context.cpp:5365-5367`, `corpus/SOURCES.md:126`), which `cited()` never reads. `fragment-guardless.tsv` uses `pin_lines=5366` / `release_lines=5687` and is `VALID`: C1 certifies the row while never looking at `if (!params.endpoint_slots)`. Because a `holds` pair only has to be *text-equal*, the same acceptance holds if b11906 had flipped the condition to `if (params.endpoint_slots)` while leaving the message: the lane's claim (501 when slots are off) would be false, the ledger would say `holds`, and C1 would print `VALID`. The same gap covers S115 (`5407-5409` named in teaches, only `5408` cited) and the two further conditions the row's sentence needs but no ledger range can reach — the default `common.h:688`, the flag/env `arg.cpp:3654-3661`, the 501 mapping `server-common.cpp:117-119`, and the caller `server.cpp:213-214`. None of those files is in `path`; the counter never opens them.

**3b. Notes are unconstrained for `holds` — accepted.** `check_row` enforces `len(note) >= 40` only for `holds-reworded`/`drifted`/`removed`. `fragment-wrong-note.tsv` keeps the true text-equal pair but writes a note asserting "guard now reads `if (params.endpoint_slots)`, so `GET /slots` returns 200 without `--slots` … 501 is gone" — `VALID`. The ledger's human-readable reason is therefore not evidence: a reader auditing the ledger can be told the opposite of the truth by a row C1 certifies.

**3c. What the counter does bound.** The witness leg is sound for these rows: the message text is unique in the release file (one occurrence each of `if (!params.endpoint_slots)`, `does not support slots endpoint`, `if (params.slot_save_path.empty())`, `does not support slots action`) and it survives, so every substring of the pin ranges is also in RF; `fragment-wrong-drifted.tsv` (pin `5366`, release range taken from the unrelated mtmd hunk at 1399, `drifted`) is correctly rejected by the `witness_pin` rule. No pin range covering `5366` can reach changed pin text (no hunk between pin lines 4999 and 5607), so a false `drifted`/`removed`/`holds-reworded` cannot be assembled here. The exposure is one-directional: under-verification, not a fabricated witness.

**Smallest safe correction** (counter is frozen — proposed, not applied): make `cited()` read `c[1] + c[5] + c[6]` (or every cell except note/status) so the guard lines the row states must lie inside `pin_lines`, and apply the `>= 40`-char note rule to `holds` as well, requiring the note to name the condition checked. Effect on these rows: `pin_lines` become `5365-5367` and `5407-5409` (already what `fragment-correct.tsv` / `verdicts.tsv` propose), and the rest of the frozen population is unaffected unless a row's teaches cell cites lines outside its own pin ranges — worth checking lane-wide before adopting.

**Marginal note on the ledger's own reach (no action):** the b11889 ledger rows for S114/S115 (`registry/release-recheck-b11889.tsv:22-23`) used release lines 5684/5726, the error lines at b11889; the b11906 equivalents are 5687/5729.
