## Findings

### M1 — heading match is substring, not line-anchored (medium)
`block_names` line 62 tests `HEADING in readme` and line 63 splits on the first occurrence
anywhere in the file. Measured:
- README prose `Note: read the section ## Coverage map — round 37 addition below.` followed
  by one entry row -> `named 1 files_exist 1 cited_new 1 met False` (named already 1);
- a longer heading `## Coverage map — round 37 addition (draft, rejects)` -> `named 1`.
Neither is a heading in the sense the kill rule names ("a name outside the heading '## Coverage
map — round 37 addition' does not count"), so a name that sits under no heading at all can be
counted. This is the one clause under review whose implementation is weaker than its prose.
Fix would be anchoring (`^` at line start, exact line equality) plus terminating on any
heading level; **not applied** per the assignment (do not edit the counter). Residual risk is
low in practice: the lane's README block is generated by the scribe seat and a mid-paragraph
copy of the heading is deliberate malformation, not an accident.

### M2 — a bad `--tip`/`--repo` is scored as a failed claim, not as usage error (medium)
`git_show` (49-59) returns `None` for any non-zero git exit, and `main` (lines 162-164) maps
every non-`--selftest` outcome to exit 1. Measured:
```
--tip deadbeefdeadbeefdeadbeefdeadbeefdeadbeef  -> named 0 files_exist 0 cited_new 0 met False  exit=1
--repo /nonexistent --tip <valid base>          -> named 0 files_exist 0 cited_new 0 met False  exit=1
```
Both are indistinguishable from the genuine base-arm false in answer 2, yet the module
docstring promises "2 on usage". A one-character tip typo therefore records C2 as a claim
failure instead of an operator error, which is the only way this round's C2 line can be wrong
without any content being wrong. Suggested guard (not applied): verify the rev with
`git rev-parse --verify <tip>^{commit}` in `load` and raise, letting the existing
`except Exception` boundary print `error:` and exit 2.

### L1 — the scored invocation does not re-derive two of the three base clauses (low)
The predicate's final clause is "none of those three holds at that base". In the scored path
`load` (103-108) reads the base tree only for `corpus/SOURCES.md`; `score` uses it only to
build `base_ids` (line 91). Neither "the base README has no round-37 block" nor "the base tree
lacks the three entry files" is computed in that path — they are exercised only by
`--selftest` (lines 125-160) and by the frozen `controls/c2-base.out` receipt. I verified both
independently: the heading is absent from `6a4afdfe:corpus/README.md`, and
`git cat-file -e 6a4afdfe:corpus/knowledge/{kv-cache-reclamation-models.md,
prefix-cache-reuse-models.md, prefix-cache-reuse-models-amendment-2026-10-23.md}` reports
absent for all three. So the base arm is genuinely false today; the gap is that the printed
line the claim is scored on carries no base evidence, and a reader of that single line cannot
tell the base arm was checked at all.

### L2 — an in-block reject/prose line satisfies "names each" and "cites an S-id" (low, by design)
`block_names` counts any occurrence of the entry path in the block body, and `cited_ids`
(line 70) takes every `S\d{3,}` in the *entry file*, not just a `source:` line. A block row
reading `rejected: knowledge/prefix-cache-reuse-models.md (S942)` would count for naming, and
an entry file that mentions a new id anywhere counts for `cited_new`. The frozen predicate
says only "names each" / "cites an S-id", so this is within the letter of the claim; flagged so
the verdict is not read as "three adopted rows exist".

### I1 — docstring claim "identical … and the receipt" (informational)
The docstring asserts the predicate is identical in three places. It is byte-identical in the
preregistration and the `PREDICATE` constant; in the module docstring it is re-wrapped prose
(normalised equal), and no C2 artifact contains the predicate text — `controls/c2-base.out`
holds only the counter line. Docstring-only inconsistency; no scoring effect.

## Residual risk
- State at lane HEAD `873c5d7774b97e7c633052456f13595a2ea5775f` (a sandbox `mut4` commit):
  `named 0 files_exist 0 cited_new 0 met False`, exit 1. Nothing has landed yet: no round-37
  heading and no `kv-cache`/`prefix-cache` entry in `git ls-tree HEAD corpus/knowledge`,
  and the working tree also has neither the README block nor the three files. C2 can only be
  met by committed bytes, so the counter will stay at `met False` until the scribe's README
  block and the three entries are committed at the scored tip — an uncommitted working-copy
  entry scores zero, by design.
- The registry parser (`registry_ids`, 73-80) only accepts `| Sxxx |` table rows; base
  SOURCES parses to 203 ids (S001-S329) and a prose-only `S999` mention is not counted. This
  is the strict direction, so no false new ids can arise from prose in `SOURCES.md`.
- `files_exist` uses `git show`, so an entry that exists but is empty (empty-string stdout,
  not `None`) counts as present; harmless, since `cited_new` would then be 0.
