## Findings

- **Observed source behavior:** `status_by_exit_code` maps 1 and 3 to `killed`; the default for unlisted codes is `suspicious`; 36, -24, 24, 152 and 255 map to `timeout`; -11 and -9 map to `segfault`. The browse UI describes killed as “Mutant caused a test to fail”, unknown as an unknown pytest exit code, and gives timeout/segfault separate labels. `calculate_summary_stats` counts every bucket separately. `badge()` scores `(killed + timeout) / (total - skipped)`.
- **Executed mapping:** the official PyPI `mutmut==3.8.0` environment returned `{0: survived, 1: killed, 2: check was interrupted by user, 3: killed, 4: suspicious, 5: no tests, 7: suspicious, -6: suspicious, -9: segfault, -11: segfault, -24/24/152/255: timeout}`. A child run of `os._exit(-1)` returned 255 and mapped to `timeout`.
- **Executed pytest probe:** the test passed (`1 passed`) but a deliberate exception in `pytest_runtest_logreport` made pytest exit 3 (`INTERNALERROR`); mutmut recorded that mutant as `killed`. In a 10-mutant toy run (process isolation `fork`), `results --all` classified a silent `os._exit(1)` and a pytest exit-4 usage error caught by mutmut's harness as `killed`; SIGABRT/exit -6 and exit 7 were `suspicious`; SIGSEGV/-11 was `segfault`; SIGKILL/-9 was also `segfault`; the spin was `timeout`; and the ordinary assertion failure was `killed`. CI stats were killed=4, timeout=1, suspicious=2, segfault=2, survived=1; badge said 50.0%. In `forkserver`, the usage-error mutant instead became exit 255/`timeout`; same badge score. This makes process-isolation mode part of the observed limitation.
- **Sourcing decision:** this is a useful independent counterexample to error-versus-verdict calibration, not affirmative precedent to adopt: mutmut has distinct buckets for some errors but also promotes pytest INTERNALERROR and silent exit 1 to a kill. The output status `partial` means the requested taxonomy and row draft are complete, but mutmut does not substantiate C1 as a clean precedent.
