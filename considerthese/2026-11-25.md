## Lessons from last 3 days

1. **The prompt-cache series now has a third step: a failed restore is retried after clearing idle slots (unified KV only).** `40fe9164f` (#30997, 2026-11-24 10:13 BRT, fixes #30961) adds `cache_idle_slots(id_slot_keep)` in `server-context.cpp` (~1827): each idle slot other than the kept one is saved to the prompt cache, and with `kv_unified` it is also cleared (`[TAG_IDLE_SLOT_CLEAR]`). `update_prompt_cache()` now, when `prompt_load` fails and both `kv_unified` and `cache_idle_slots` are on, frees the other idle slots and retries the restore once. The commit message says it builds on `c212d25ad` (yesterday's lesson 2: the entry is kept when a restore fails), which itself followed `82dd97047` (yesterday's lesson 1). So in three days the `--cache-ram` path changed when the cache is asked, what a failure does to the entry, and what happens after a failure. Practical consequence: with a unified KV cache, a cache hit on one slot can now evict other idle slots' KV (they go to RAM cache), so per-slot `cache_n` numbers for *other* slots measured before `40fe9164f` may not repeat. New test: `test_kv_keep_only_active.py` (+38). The lane still has no knowledge file for this cache (see 2026-11-24 idea 1).

2. **`tool_choice` now accepts the OpenAI object forms, with new 400s.** `5bd90fa0e` (#31564, 2026-11-25 05:39 BRT) turns `common_chat_tool_choice` from an enum into a struct (`mode` + `allowed` names) and changes `oaicompat_chat_params_parse` (`server-common.cpp` ~1501) to read `tool_choice` as JSON, not only a string. In `common/chat.cpp` (339-383 at HEAD): `{"type":"function","function":{"name":...}}` becomes `required` restricted to that tool (and the commit sets `parallel_tool_calls` false for it); `{"type":"allowed_tools","allowed_tools":{"mode":"auto"|"required","tools":[...]}}` restricts the set; an empty `allowed_tools` with `auto` becomes `none`, with `required` it throws; and every named tool must match **exactly one** supplied tool or the request fails with "tool_choice function name must match exactly one supplied tool". Before this commit an object `tool_choice` was not read as a named choice at all. The realtime path (`server-realtime.cpp` ~100) now calls the parser with an **empty tool list**, so if an object ever reaches it, any named choice would fail the exactly-one check; I did not read the lines before the `try` there, so whether realtime still rejects non-strings first is unverified. Any lane cell that sends a named `tool_choice` to llama-server should be re-run: results before `ab16df399`-era HEADs reflect the old behavior.

3. **MCP image/audio results now enter the tool result as base64 text, and `/props` gained a field.** `66a3b01b0` (#32064, 2026-11-24 12:23 BRT) changes `mcp_result_to_response` in `server-mcp.cpp`: image and audio content parts were dropped before; now each is rendered as a one-line `data:<mime>;base64,...` string (whitespace stripped) in the text the model gets back. From the hunk I read, this is text, not a multimodal part, so a screenshot-returning MCP tool can put a very large base64 string into context (hypothesis: token cost scales with image bytes; not measured). Separately, `e8906e6b0` (#33004, 2026-11-25 03:08 BRT) adds `--ui-agent` / `LLAMA_ARG_UI_AGENT` (agent mode in Llama Chat with browser-side tools only, no server tools, no MCP proxy) and a new `"ui_agent"` key in `get_res_props` (`server-context.cpp` ~5684), which touches the `/props` surface that `router-props-autoload.md` reasons about (candidate sixth item for the r101 re-measure list). `48ac73696` (2026-11-25 08:29 BRT) makes Windows `CTRL_BREAK_EVENT` a clean shutdown like Ctrl-C (only relevant to Windows harnesses).
