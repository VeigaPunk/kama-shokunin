## 1. Cross-Source Relation: S478/S479 vs Held K05 Ground (S106–S113, Measured Cells)

The lane's held K05 ground in `corpus/knowledge/context-capacity.md` (anchored by S106–S113 at commit `704366d7` / release `b11755`) establishes that a single-model `llama-server` operates with two distinct context numbers:
1. The **KV pool** (`llama_context: n_ctx`, the entire buffer), logged only at startup with `-v` (`llama_context: n_ctx = N`, S113).
2. The **per-slot ceiling** (`n_ctx_slot`), returned by `/props`, `/slots`, and `/v1/models` (`meta.n_ctx`, S060).

The 14 measured fixture cells (K1–K8, X1–X3, L1–L3) proved:
- **K1 vs X2**: Two configurations can return identical per-slot values (`n_ctx=2048`, `total_slots=4`) while their physical KV pools differ fourfold (2048 vs 8192).
- **L1**: Two concurrent 1000-token requests on a shared 2048 pool abort mid-generation with HTTP 500 `server_error: Context size has been exceeded` at token 1025, because $2 \times 1025 > 2048$, even though each request was well below its 2048 per-slot ceiling.
- **K5**: A pool of 4096 capped per-slot context to 2048 (`n_ctx_train`), logged via `n_ctx_seq (4096) > n_ctx_train (2048)`.
- **X1 / X3**: S106 (`common/fit.cpp`) resolves an unset split context to `n_ctx_train * n_streams` (8192 for 4 slots), which `--fit off` disables (falling back to 512 per slot).

### How S478 and S479 map to this ground:
- **S478 (`vllm/v1/core/kv_cache_utils.py` @ v0.32.0)**:
  - Memory allocation derives block count: `num_blocks = available_memory // bytes_per_block` (line 1627).
  - Maximum concurrency is computed across block groups: `get_max_concurrency_for_kv_cache_config` (lines 1195–1227) evaluates `limits = [kv_cache_config.num_blocks / num_blocks_per_request]`.
  - Token capacity is derived: `get_kv_cache_capacity` returns `int(max_concurrency * max_model_len)` (line 2308).
  - One startup log publishes all three quantities together: `logger.info_once("%s KV cache size: %s tokens, Maximum concurrency for %s tokens per request: %.2fx", ...)` (line 2328).
  - *Relation*: vLLM exposes the KV pool and concurrency ratio explicitly in its startup log, whereas llama.cpp's startup log reports only raw pool cells (`llama_context: n_ctx`), leaving concurrency limits uncalculated.
- **S479 (`tools/server/server-models.cpp` @ commit `704366d7`)**:
  - Router listing handler `get_router_models` (line 2329) publishes declared context: `if (meta.n_ctx_train > 0) { model_info["context_length"] = meta.n_ctx_train; }` (lines 2378–2379).
  - `max_model_len` appears 0 times in `server-models.cpp`.
  - *Relation*: Confirms that in router mode, llama.cpp publishes declared training context under its own key name (`context_length`), whereas the single-model fixture measured in `context-capacity.md` uses `/v1/models` which nests `meta.n_ctx` and `meta.n_ctx_train` under `meta`.

## 3. Analysis: Where the New Entry Understates or Overstates Relative to Measured Cells

### A. Understatements in `context-capacity-engine-sides.md`
1. **Single-model HTTP declared capacity**:
   - `context-capacity-engine-sides.md:7` asserts: *"The lane's measured entry, `corpus/knowledge/context-capacity.md`, is llama.cpp b11755 on a lane-owned fixture: two capacity numbers (the KV pool and the per-slot ceiling), with the API reporting only the second."*
   - And the summary table at line 29 states: *`llama.cpp 704366d7 | declared side: context_length = n_ctx_train (router listing, only when > 0) ... where it is printed or returned: router listing (server-models.cpp:2379)`*.
   - **Fact**: This understates single-model llama.cpp HTTP output. In the measured cells of `context-capacity.md` and on live servers (corroborated by kengaku's `:34113` capture `models-34113.json`), single-model `/v1/models` *does* report the declared training context (`meta.n_ctx_train`), nested inside `data[0].meta` alongside `meta.n_ctx`. Declared capacity is therefore not restricted to router mode.
2. **Physical KV pool vs derived token count**:
   - Lines 12–13 state that vLLM's `kv_cache_size_tokens` equals `int(max_concurrency * max_model_len)`.
   - **Fact**: The entry understates the discrepancy between physical block memory (`num_blocks * block_size`) and reported token capacity: because `max_concurrency` is bounded by whole request blocks (`cdiv`), `kv_cache_size_tokens` represents the integer-quantized capacity for requests of length `max_model_len`, not the total physical KV cell pool.

### B. Overstatements in `context-capacity-engine-sides.md`
1. **Cross-mode transfer between router mode and single-model measured cells**:
   - The table at line 29 pairs router-mode `server-models.cpp:2379` (`context_length`) with the measured cells of `context-capacity.md`.
   - **Fact**: `context-capacity.md:224` explicitly specifies under "Does not establish": *"Other builds, other engines, router mode..."*. Single-model launches (`llama-server -m ...`) do not execute `get_router_models` and do not emit top-level `context_length`. Presenting `context_length` as the declared side corresponding to the measured single-model cells overstates cross-mode transfer.
2. **Concurrency / saturation semantics equivalence**:
   - The entry pairs vLLM's `Maximum concurrency` and `kv_cache_size_tokens` side by side with llama.cpp's pool.
   - **Fact**: This overstates runtime equivalence. In vLLM, `max_concurrency` guides upfront scheduling and admission budgeting (chunked prefill / queueing). In llama.cpp, as demonstrated by cell L1, no upfront concurrency admission check exists: the server accepts concurrent requests up to `total_slots` and crashes mid-execution with HTTP 500 when the shared pool is exceeded.
