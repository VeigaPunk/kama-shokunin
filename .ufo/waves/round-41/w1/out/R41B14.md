**Digest semantics (calibration note).** The claim's digest is over the **decompressed**
page bytes, not the wire bytes: with `Accept-Encoding: gzip` the wire body is 7481 bytes
whose raw sha256 is `3665a30a…` — a different hash for the same resource. The frozen value
is the decompressed-page digest (what `curl` without `--compressed` writes, and what
`curl --compressed` writes after inflating). A re-checker who saves raw gzip bytes would
report a false mismatch; the correct reproduction is `curl -sS -o f URL` (or `gzip -dc`).

**Page-chrome sensitivity (calibration note, not a defect).** The digest covers the whole
rendered page, including site chrome — not just the manual text. Demonstration: the
archived copy at `https://git-scm.com/docs/git-ls-remote/2.48.0` has a *different* digest
(`da44a5a6b87ddb4be4c001bb75f6af0057686d412f691c48bf9a4b51df93f800`, 41894 bytes) while its
**rendered text is byte-identical** to the live page's rendered text (diff of the
tag-stripped text: empty). The single differing HTML line is site chrome:

```

---
>           <div id="main" data-pagefind-filter="category:reference" data-pagefind-meta="category:Reference" data-pagefind-weight="0.05" data-pagefind-body>
```

i.e. the site's search-index attributes. Consequence for the row: the digest is a
**page-identity** anchor, so it will change the next time git-scm.com alters any template,

## 5. Behavioural corroboration of the taught rule (local, throwaway fixture)

The row teaches that a watcher must skip the `<ref>^{}` line. Reproduced with local git
2.56.0 in a throwaway repo (`D=$(mktemp -d) && git -C "$D" init -q`, toplevel verified equal
to `$D`, removed afterwards):

```
$ git -C "$D" ls-remote --tags "$D"
9dc6cd91…  refs/tags/lightweight          <- lightweight tag: one line
6974ebf8…  refs/tags/v1.0                  <- annotated tag: the tag object
9dc6cd91…  refs/tags/v1.0^{}               <- the peeled line: the tagged object

$ git -C "$D" ls-remote --tags --refs "$D"
9dc6cd91…  refs/tags/lightweight
6974ebf8…  refs/tags/v1.0                 <- no peeled line
```

This matches the manual's OUTPUT paragraph exactly and matches `tools/pin-watch.py:82`
(`… or ref.endswith("^{}"): continue`) — the row's `teaches` cell ("a release-tag watcher
skips the `<ref>^{}` line: for an annotated tag it names the tagged object, not a second
release, so counting it double-counts releases") is accurate.

The two *anchors* are greppable in the raw HTML; the *quote* is not, because the page wraps
`<ref>` in `<span class='synopsis'><em><span class="hover-term" data-term="ref">&lt;ref&gt;</span></em></span>`
and hard-wraps the sentence across three source lines (1919–1921). A verifier who re-checks
S475 by grepping the frozen evidence file for the quoted sentence alone gets a **false
negative** and could wrongly report the quote as absent.

Two consequences for the lane's own machinery:
- `corpus/lessons/round-41.md:18` records the access method as "curl" but not the *render*
  step. The rendered-text reproduction (tags stripped, entities unescaped, whitespace
  normalised) is the step that makes the quote match; that step is nowhere written down.
- The upstream AsciiDoc is the stronger anchor for a future round and is also
  digest-stable: `Documentation/git-ls-remote.txt` at `v2.48.0` and
  `Documentation/git-ls-remote.adoc` at `v2.56.0` both hash to
  `9739be01b44da924ebec94ee658d5c080627ee65a2cd7d711fd83d6a081ba4da` and carry the passage
  at line 113. After backtick-stripping and whitespace normalisation the upstream source
  contains the lesson's exact 22-word string too (verified True), so the quote is
  reproducible from a *content-addressed* upstream file — not only from a rendered page.

Whether this is a defect in the S475 row: the row's own anchor cell does not promise
greppability, it promises "§OUTPUT and §OPTIONS `--refs`", the header strings, and the page
digest — all of which hold. I record it as an operability/calibration observation for the
