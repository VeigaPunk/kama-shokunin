## Lessons from last 3 days

1. **Upstream now returns 403 on `/props` for a cross-origin request, and has a test pinning it.** llama.cpp `a1a68eb79` ("explicit opt-in tools via non-loopback addr, check cors host port", #32113, 2026-11-12 08:16 BRT) edits `tools/server/server-http.cpp` and `tests/unit/test_security.py`. The new tests send `GET /props` with `Origin: http://localhost:5173` and assert **403**, while a same-origin `Origin: http://127.0.0.1:{port}` gets 200. So a probe's result on `/props` now depends on which `Origin` header it sends (browsers and some HTTP clients send one), not only on server readiness. The corpus rule in `corpus/knowledge/router-props-autoload.md` (read the body only on a final HTTP 200) still holds, but "not 200" no longer means "not ready".

2. **Router child instances now refuse browser-like requests outright.** `e182fdad4` ("disallow direct access child instance from browser", #32120, same morning) makes a server that is `managed_by_router` return 403 when the request carries `Origin`, `Sec-Fetch-Site`, or `Sec-Fetch-Mode`; `test_router.py` asserts 403 on a child's `/health` with those headers. This is the router topology the lane's `/props` autoload work measures. A probe aimed at a child port instead of the router can now get 403 from a perfectly healthy child, which is a new killer-cell candidate next to yesterday's 403-on-foreign-Host from `2cbe0ec42`.
